Most Xamarin.Forms apps lean on a dozen or more plugins. Moving to .NET MAUI is mostly about finding where
each of them went. Some are now part of MAUI itself, some have a MAUI release of their own, and the ones
that ran work in the background (BLE, GPS, geofencing, jobs, push, transfers) are the ones most worth
replacing rather than porting.

This page maps the common ones. Use it as a checklist: go through your `.csproj` `PackageReference`s and
find each one below.

:::tip[Start with the background work]
Foreground features (a camera picker, a connectivity check) port in an afternoon. Code that has to keep
running when the app is suspended is where migrations stall: iOS background modes, Android foreground
services and OEM battery killers all behave differently on MAUI's lifecycle. Move those first, onto
libraries built for it.
:::

## Built into .NET MAUI

These need no package at all. The APIs live in `Microsoft.Maui.*` and ship with the MAUI workload.

| Xamarin package | On .NET MAUI |
| :--- | :--- |
| `Xamarin.Essentials` | Built in (`Microsoft.Maui.Devices`, `Microsoft.Maui.Storage`, `Microsoft.Maui.Networking`, …) |
| `Plugin.Connectivity` | `Connectivity` (built in) |
| `Plugin.Permissions` | `Permissions` (built in). Shiny libraries request their own permissions. |
| `Plugin.Media` | `MediaPicker` (built in) |
| `Plugin.FilePicker` | `FilePicker` (built in) |
| `Plugin.Settings` | `Preferences` / `SecureStorage` (built in), or [Shiny Stores](/stores/) for strongly-typed, bindable settings |
| `Plugin.TextToSpeech` | `TextToSpeech` (built in), or [Shiny Speech](/speech/) for speech-to-text and cloud voices |
| `Xamarin.Forms.Maps` | `Microsoft.Maui.Controls.Maps` |
| `Xamarin.CommunityToolkit` | `CommunityToolkit.Maui` |
| `SkiaSharp.Views.Forms` | `SkiaSharp.Views.Maui.Controls` |

## Device and background features → Shiny

These are the plugins that touched the OS beneath the app. Shiny's libraries do the same jobs on MAUI and
keep working in the background, which is usually what the Xamarin plugin couldn't do reliably.

| Xamarin package | On .NET MAUI | Why switch |
| :--- | :--- | :--- |
| `Acr.BluetoothLE` | [`Shiny.BluetoothLE`](/client/ble/) | Shiny.BluetoothLE is what Acr.BluetoothLE became: same author, with background scanning and connections, reconnect handling and managed peripherals |
| BLE peripheral/GATT server code (hand-rolled) | [`Shiny.BluetoothLE.Hosting`](/client/blehosting/) | Advertising and GATT services from the phone, without platform code |
| `Plugin.Geolocator` | [`Shiny.Gps`](/client/locations/gps/) | MAUI's `Geolocation` covers one-off foreground fixes; Shiny covers continuous and background tracking |
| Geofencing (hand-rolled, or `Plugin.Geofencing`) | [`Shiny.Geofencing`](/client/locations/geofencing/) | OS-managed geofences that fire with the app closed |
| `Plugin.FirebasePushNotification` / `Plugin.PushNotification` | [`Shiny.Push`](/client/push/) | Native APNs and Firebase, or Azure Notification Hubs, behind one API |
| Background jobs (`Matcha.BackgroundService`, hand-rolled WorkManager / BGTaskScheduler) | [`Shiny.Jobs`](/client/jobs/) | Runs on the OS schedulers on iOS and Android |
| Background downloads/uploads (hand-rolled `NSURLSession` / `DownloadManager`) | [`Shiny.Net.Http`](/client/httptransfers/) | Transfers that survive the app being suspended or killed |
| iBeacon code | [`Shiny.Beacons`](/client/beacons/) | Ranging and background monitoring |
| `Plugin.InAppBilling` | [`Shiny.Mobile.InAppPurchases`](/client/inapppurchases/) | Store purchases with server-side verification |
| `Plugin.Contacts` | [`Shiny.Contacts`](/client/contactstore/) | Read and write device contacts with a query builder |
| `Plugin.Calendars` | [`Shiny.Calendar`](/client/calendarstore/) | Device calendar and event CRUD |
| Offline data + sync (hand-rolled, or Azure Mobile Apps offline sync) | [`Shiny.Data.Sync`](/client/datasync/) | Background-capable bidirectional sync over HTTP |

## Coming from Shiny on Xamarin

If the app already used Shiny 1.x or 2.x on Xamarin, most of the API carries over. The main changes:

- **Startup.** The Xamarin `ShinyStartup` class and the per-platform `ShinyHost.Init` calls are gone. Add
  `UseShiny()` to `MauiProgram.cs` and register services on `builder.Services`. See
  [MAUI hosting](/foundation/hosting/maui/).
- **Locations split in two.** GPS and geofencing are separate packages:
  [`Shiny.Gps`](/client/locations/gps/) and [`Shiny.Geofencing`](/client/locations/geofencing/).
- **Platform boilerplate is gone.** `UseShiny()` wires the Android lifecycle callbacks and iOS app delegate
  methods that used to be pasted into `MainActivity` and `AppDelegate`.

The [v3 announcement](/blog/2023/09/v3/) covers what changed between the Xamarin and MAUI generations in
more detail.

## Before you start

1. **List every package.** `dotnet list package` on each project, including the platform heads. The
   platform projects are where forgotten plugins hide.
2. **Sort them into the three groups above.** Built-in ones are a rename; the background ones are the real
   work; anything left over needs a check for a MAUI release, or a replacement.
3. **Check custom renderers.** Xamarin.Forms renderers become MAUI handlers. Effects and renderers are
   usually the second-largest piece of work after background features.
4. **Test on real devices, early.** Background behaviour on a simulator tells you very little. Test on the
   oldest OS version you support and on at least one aggressive Android OEM.
