---
title: Widget Extension (iOS)
---

iOS renders a Live Activity from a **WidgetKit widget extension**, and WidgetKit requires SwiftUI. There
is no C# path around it — no library can remove this step, only make it small.

Shiny ships a **data-driven widget** that renders whatever `LiveActivityContent` you send, so most apps
add it once, unchanged, and never open Xcode again. It lives in
[`templates/WidgetExtension`](https://github.com/shinyorg/liveactivities/tree/main/templates/WidgetExtension).

## Three steps

**1. Create the extension in Xcode.** New project → iOS → Widget Extension, tick *Include Live Activity*.
Name it e.g. `MyAppLiveActivity`, bundle id `<your-app-bundle-id>.MyAppLiveActivity`, deployment target
**iOS 16.2+**.

**2. Replace the generated Swift** with the two files from the template folder:

| File | Purpose |
|---|---|
| `ShinyLiveActivityWidget.swift` | The widget — Lock Screen view + Dynamic Island, driven by the content state |
| `ShinyActivityAttributes.swift` | The shared activity type. Must stay identical to the library's copy |

Delete the template's own attributes/bundle files so the target has exactly one `@main`.

**3. Reference it from your app csproj:**

```xml
<ItemGroup Condition="$([MSBuild]::GetTargetPlatformIdentifier('$(TargetFramework)')) == 'ios'">
  <XcodeProject Include="../ios/MyAppLiveActivity/MyAppLiveActivity.xcodeproj">
    <SchemeName>MyAppLiveActivity</SchemeName>
    <Kind>AppExtension</Kind>
  </XcodeProject>
</ItemGroup>
```

The .NET iOS SDK builds the Xcode project and embeds the resulting `.appex` in your app's `PlugIns/`.

Then add to the **app's** `Info.plist`:

```xml
<key>NSSupportsLiveActivities</key>
<true/>
```

Add `NSSupportsLiveActivitiesFrequentUpdates` too if you update more than a handful of times an hour —
without it the system throttles you harder.

## Why one shared attributes type

ActivityKit needs a concrete Swift `Codable` type at compile time, which would normally mean every app
hand-writes its own — and a general-purpose .NET API becomes impossible. Shiny declares exactly one,
`ShinyActivityAttributes`, whose `ContentState` has a fixed schema:

```swift
public struct ContentState: Codable, Hashable {
    public var title: String?
    public var body: String?
    public var shortStatus: String?
    public var progress: Double?
    public var progressStart: Date?
    public var progressEnd: Date?
    public var indeterminate: Bool?
    public var data: [String: String]?
}
```

That one schema is shared by three codebases: `LiveActivityContent` in C#, this struct in Swift, and the
`content-state` a server pushes over APNs. It is also why a push-to-start payload always names
`"ShinyActivityAttributes"` as its `attributes-type`.

:::caution
If you change `ShinyActivityAttributes.swift`, change every copy — the library's, your widget's, and the
matching field names in `LiveActivityContentSchema`. A mismatch doesn't throw; the activity just stops
updating.
:::

## Customizing

Everything in `ShinyLiveActivityWidget.swift` below the top is ordinary SwiftUI — restyle freely. To
render different layouts per activity type, set `LiveActivityRequest.Kind` in C# and branch on
`context.attributes.kind`; read your own values from `context.state.data`.

```swift
ActivityConfiguration(for: ShinyActivityAttributes.self) { context in
    switch context.attributes.kind {
        case "delivery": DeliveryView(state: context.state)
        case "match":    ScoreView(state: context.state)
        default:         LockScreenView(state: context.state)
    }
} dynamicIsland: { context in
    // …
}
```
