title: Architecture

Version 3 of `Shiny.AiConversation` is built around **sessions**. A session is one conversation with the AI: it is persisted, it never ends, and any number of screens or services can pick it up again. This page covers how the pieces fit together and why.

## The shape

```
   App code ──► IAiSessionManager ── Start / Get / GetLatest ──► IAiSession
                       │                                             │
                       │                                   Send ─────┤──► IAiTurn (one active)
                       ▼                                             │
                IAiSessionStore  ◄──── header + messages ────────────┘
                (only source of truth)                               ▲
                                                                     │
   IChatClientProvider ──► IChatClient          ISessionInterceptor ─┘ (tools, system prompts)
```

| Piece | Role |
|---|---|
| `IAiSessionManager` | starts, loads, queries and deletes sessions. Stateless |
| `IAiSession` | one loaded instance of a session: sends input, streams events, pages history |
| `IAiTurn` | one exchange: the user's input, the model's reply and any tool calls in between |
| `IAiSessionStore` | persists session headers and messages |
| `ISessionInterceptor` | adds tools and system prompts, reacts to turns |
| `IChatClientProvider` | hands out the `IChatClient` for each turn |
| `IAiAttachmentStore` | stores images referenced by messages |

The core package depends only on Microsoft.Extensions.AI. It doesn't reference Shiny.Speech or Shiny.Audio, so text chat needs no audio packages. Voice sits on top of the session API in its own package and talks to the session only through `Send`, `Interrupt`, events and `PendingQuestions`.

## The manager is stateless

`IAiSessionManager` holds no sessions, no registry and no "current" pointer.

- `Start(settings)` writes a new header to the store and returns an instance.
- `Get(id)` and `GetLatest()` always read the store and return a **new instance every call**.
- Whoever asked for the instance owns it and disposes it. Disposing releases that instance, never the session.

Because everything is rebuilt from the store, a session survives app restarts, and a deleted session disappears everywhere immediately.

### What is persisted

`AiSessionSettings` lives in the session header: `Profile`, `ContextWindow`, the pressure thresholds, compaction settings, `ExcludeFromSearch`, `Tags` and `Metadata`.

Tools, system prompts and the chat client are runtime pieces. They are never persisted, so they can't be passed to `Start` directly; they come from interceptors, which run again on every load. An interceptor can look at `Profile` to decide what applies (a `"cooking"` session gets recipe tools, a `"support"` session gets ticket tools).

## Turns

A session has at most one active turn. `Send` returns an `IAiTurn` right away and queues the work, so:

- Sending while a turn is running **supersedes** it. The running turn is cancelled, ends with `AiTurnOutcome.Superseded`, and its partial reply is stored as interrupted before the new turn starts.
- `turn.Interrupt(spokenText)` stops the turn because the user interrupted. The reply is stored with `SpokenText`, and the next prompt sends the model **what was actually heard** followed by `[interrupted by user]`, not the full text it generated.
- Calling `Interrupt` after the turn completed (the reply finished streaming but was still being spoken) updates the stored reply the same way.
- Cancelling the token passed to `Send` ends the turn as `Interrupted`. Cancellation is never reported as an error.

`turn.Completion` never faults. A failed request ends with `AiTurnOutcome.Failed` and the exception in `AiTurnResult.Error`.

## Persistence: write early

The store is written as the turn happens, not after it succeeds:

1. The **user message** is appended before the model is called, so a failed or cancelled request never loses what the user said.
2. The **assistant message** is appended as `Streaming` when the model is called.
3. When the turn ends, the assistant message is finalized as `Complete`, `Interrupted` or `Failed`, with its tool calls and results as parts.
4. The header (pending questions, usage, context size) is saved.

Each turn produces one assistant message whose ordered parts can hold text, tool calls and tool results. The persisted schema is the library's own (`AiMessageDocument` and `MessagePart`, each with a `SchemaVersion`), never serialized Microsoft.Extensions.AI types, which change between versions and carry provider-specific data. Mapping to and from `ChatMessage` happens in one place.

Only display text is stored as `Text`; protocol noise never becomes content. Each part carries an `Audience` (`Spoken`, `Displayed`, `ModelOnly`), so a voice driver speaks only spoken parts and a chat UI shows only displayed ones.

## Two instances of one session

Since `Get` returns a new instance each time, two instances of the same session can be alive at once, for example a chat page and a voice driver. The rules:

- The header has a `Version`. Every header save is conditional on the version the instance last read (`SaveSession(doc, expectedVersion)`).
- Message `Sequence` is allocated by the store at append time, so two writers can never produce duplicate ordering.
- Before each turn, the instance checks the stored version. If another instance changed it, the instance **reloads its messages first**, so it builds the prompt from the latest history.
- Two turns running at the same time on one session: the second header save fails the version check and that turn ends `Failed` with a `SessionConflictException`.

Sharing one instance avoids all of this, and is the recommended approach when two parts of an app work on the same session.

## Crash recovery is lazy

There's no start-up sweep. Every process run has its own `RunId`, stamped on each message it writes. When a session is loaded, a `Streaming` message written by a **different** run belongs to a process that died mid-turn, so it is marked `Interrupted`. One from the current run belongs to another live instance and is left alone.

## Prompt assembly

Each request is built in a fixed order:

1. System prompts from interceptors (`OnSessionLoaded`, then `OnBeforeTurn`), in one system message.
2. Mode instructions: when the input came from voice, the model is told its reply is spoken (plain prose, no markdown, at most one question).
3. The [memory](/aiconversation/memory) index (paths and descriptions, wrapped as data), when memory is on.
4. The rolling summary from [compaction](/aiconversation/compaction), when there is one. Summary messages in the history are markers for the UI and aren't sent again.
5. Non-compacted history in sequence order. Failed and still-streaming messages are skipped, interrupted replies are sent as what was heard, and a tool call whose result never arrived is dropped (providers reject an unanswered tool call). User images are sent as image content when they arrived in this turn or are kept in context, otherwise as an "[image: …]" mention (see [Images](/aiconversation/images)).
6. The new user message.

The tools sent are the session's tools, the turn's tools, the built-in [`ask_user`](/aiconversation/structured-turns) tool and, when memory is on, the `memory` tool.

Before a turn is sent, the session checks the [auto-compaction](/aiconversation/compaction#automatic-compaction) threshold and compacts first if it's over. After a turn completes it checks again and compacts in the background, on the same queue as turns, so compaction never overlaps a turn.

## Interceptors

`ISessionInterceptor` has four hooks, all optional:

| Hook | Runs | Use for |
|---|---|---|
| `OnSessionLoaded(SessionLoadedContext)` | on `Start` and every `Get` (`IsNew` tells them apart) | tools and system prompts for the whole session |
| `OnBeforeTurn(TurnContext)` | before each turn | per-turn context: RAG, time, location, extra tools |
| `OnAfterTurn(TurnContext, AiTurnResult)` | after each turn, whatever the outcome | titles, analytics, follow-up work |
| `OnCompacted(CompactionContext)` | after older messages were folded into a new summary | reacting to the new summary |

The contexts expose the `IAiSession` itself, so a tool can close over the session it belongs to instead of reaching for a global service. Tools can be flagged `AiToolFlags.Silent` so a voice driver never says "one moment" for them.

Interceptors degrade instead of failing: an exception is logged (and reported as a `SessionError` event before a turn), and the turn continues.

## Usage and context size

Two numbers are tracked separately:

- **`SessionUsage`** is everything billed: input, output, cached and reasoning tokens and the request count, summed over every request including each tool-loop round trip.
- **`ContextSnapshot`** is how full the context window is now. `CurrentTokens` is the input plus output of the **last** request of the turn.

Why the last request: Microsoft.Extensions.AI's function-invoking client sums usage across the tool loop, which overstates the context size. While streaming, each request reports its own usage, and the session reads them one at a time. When the provider reports no usage, the size is estimated (about four characters per token, plus overhead per message and per tool) and `IsEstimate` is true. A freshly loaded session also starts with an estimate.

`Pressure` (`Normal`, `Warning`, `Critical`) comes from the session's thresholds against `MaxTokens`. The library only **reports** it, with a `ContextPressureChanged` event when the level changes; the app decides how to warn the user.

## The voice driver

`Shiny.AiConversation.Voice` sits on top of a session and owns only the audio: the microphone, the speaker and the recognition loop. It never reaches into the session; it uses the same public API as any app code:

- a final utterance becomes `session.Send(AiInput.Voice(text))` (with `WithInstructions` for brief replies),
- the reply is spoken from the turn's `TextDelta` events, sentence by sentence,
- when the user interrupts, `turn.Interrupt(spokenText)` records the sentences that actually played, so the next prompt says what was heard,
- after the turn, `AwaitingUser` (from `ask_user` or a trailing `?`) opens the follow-up listen.

Only one session is attached to the voice driver at a time, because the microphone is a single resource. Text sessions can run alongside it. A realtime backend (OpenAI Realtime, Gemini Live) could later replace both the turn pipeline and the voice driver while producing the same events and persisting through the same store. See [Voice](/aiconversation/voice).

## Rounds within a turn

A turn is usually one model round (one streamed request, with any tool loop inside it). A tool added in
`OnBeforeTurn` can queue more input with `TurnContext.QueueFollowUp(...)` and end the round; the session then
stores that input as a user message and runs another round **in the same turn**: the same `IAiTurn`, events and
completion, with a new assistant message for the new round. The [camera tool](/aiconversation/camera) uses this to
deliver photos to providers that can't take images in tool results. Images themselves are stored as attachments
and referenced from messages, never inlined.

## The MAUI adapter

`Shiny.AiConversation.Maui` is another client of the public API: `AiChatView` maps `MessageAdded` /
`MessageUpdated` to bubbles 1:1, updates a streaming reply in place from `TextDelta`, pages history by sequence,
renders choice chips from `PendingQuestions` and answers with `AiInput.Answer`. Bind the same `IAiSession` instance
the voice driver is attached to, and typed and spoken turns show up in one conversation. See
[MAUI Chat UI](/aiconversation/chat-view).

## Events: `IAsyncEnumerable` only

There is no Rx and there are no C# events in the API.

- **Turn events** (`turn.Events`) are buffered for the turn's lifetime, so enumerating again replays them from the start. The stream ends after `TurnCompleted`, `TurnInterrupted` or `TurnFailed`.
- **Session events** (`session.GetEvents(ct)`) are a hot broadcast. Each call registers its own subscriber, and the first item is a `Snapshot` taken atomically with the subscription, so nothing is missed between reading state and listening. The stream ends when the token is cancelled or the instance is disposed.

Each subscriber has its own bounded queue (256 items), so a slow UI never blocks the conversation or other subscribers. When a queue is full, the oldest streamed `TextDelta` is dropped to make room. Lifecycle events (messages, state, turn completion) are never dropped; a subscriber that can't take one is disconnected with a `BroadcastOverflowException` rather than stalling the session.
