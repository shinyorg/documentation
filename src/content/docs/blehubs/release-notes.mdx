## v1

### 1.2 - October 10, 2026

<RN type="fix">`Discover()` no longer lists the app's own host. An app that hosts hubs and scans at the same time saw its own advertisement. It is now matched by the service UUID and the advertised local name while the host advertises, so give hosts distinct names</RN>

<RN type="enhancement">Every new BLE connection asks for the largest ATT MTU (517, was 512), and the negotiated size is logged. Android negotiates it; Apple platforms negotiate on their own</RN>
<RN type="fix">Frames now fill the link. Shiny's `IPeripheral.Mtu` is the payload size (ATT MTU minus 3), and blehubs treated it as the ATT MTU, so every write and notification was 3 bytes smaller than the link allowed. `BleHubConnectedClient.Mtu` now reports the ATT MTU (3 more than before). Wire compatible</RN>

### 1.1 - October 9, 2026

<RN type="feature">Clients can rename themselves without reconnecting: `IBleHubConnection.Rename(name)` and `ClientName`. The host checks the new name with `ValidateClient`, then runs the new `BleHub<T>.OnRenamedAsync(previousName)`, either of which can refuse (`BleHubRemoteException.RenameRefused`). `IHubContext<THub>.ClientRenamed` is raised, and `BleHubConnectedClient.Name` follows renames</RN>
<RN type="feature">`IBleHubHost.Rename(localName)` renames the host without stopping anything. It re-advertises under the new name and tells every connected client, whose `HostName` updates and `HostRenamed` event is raised in order with hub events</RN>
<RN type="enhancement">The transport seams carry renames: `IBleHubTransportEndpoint.Rename`, `IBleHubPeerChannel.HostRenamed`, `IBleHubClientTransport.Rename` and `IBleHubClientTransportEvents.HostRenamed`. New members have default implementations, so existing transports keep compiling</RN>
<RN type="enhancement" breaking>One service UUID per host: every hub is a characteristic inside one service, and it is the only UUID advertised. Set it with `server.ServiceUuid(...)` on the host and `o.ServiceUuid` on each client (both default to `BleHubProtocolOptions.DefaultServiceUuid`). Hubs no longer take a service UUID, and neither does `BleHubRegistration`. Hubs on separate services overflowed the 31 byte advertisement: Android hosts failed to advertise, and iOS hosts were invisible to Android scanners</RN>
<RN type="enhancement" breaking>One registration call per side. Hosts use `AddBleHubServer(server => server.ServiceUuid(..).Host(..).Protocol(..).AddHub<THub>(characteristicUuid, ..))`, called once; it refuses duplicate hubs, duplicate characteristics and malformed UUIDs at registration. Clients use `AddBleHubClient<T>(characteristicUuid, o => ...)` with the new `BleHubClientOptions` (`ServiceUuid`, `Protocol`). `AddBleHub`, `ConfigureBleHubHost` and `ConfigureBleHubProtocol` are removed</RN>
<RN type="enhancement">The host and client packages now target Android, iOS and Mac Catalyst as well as `net10.0`, and register the platform BLE stacks for you (`AddBluetoothLeHosting()` / `AddBluetoothLE()`). On Apple the client turns off iOS's background connect, disconnect and notification alerts, because hubs are foreground only; register your own `AppleBleConfiguration` first to change that</RN>
