## v1

### 1.5 - November 6, 2026

Initial Release. Shiny.UniversalHubs and Shiny.BluetoothLE.Hubs now ship from one repo with one version, so the first release follows BluetoothLE Hubs' 1.4 as 1.5.

<RN type="feature">Media channels over Wi-Fi: a WebSocket at `{Endpoint}/media`, opened with the `mediaToken` from the handshake reply and handed to the hub like an L2CAP media channel. Wire compatible: the reply's new fields are optional</RN>
<RN type="chore">Requires Shiny.BluetoothLE.Hubs 1.4 (media channels)</RN>
<RN type="feature" platform="iOS">New `Shiny.UniversalHubs.Multipeer` package: hubs are also served and joined over Apple's MultipeerConnectivity (iOS, Mac Catalyst, macOS), so Apple devices reach each other at Wi-Fi speed with no shared network. `server.Multipeer("mygame-mc")` on the host, `o.Multipeer("mygame-mc")` on the client. Clients share the hub, groups and `MaxClients` with BLE and Wi-Fi clients; files, media channels and renames work over it</RN>
<RN type="feature">`HubTransports.Multipeer`, included in `HubTransports.All`. It only runs once the Multipeer package is set up and is skipped quietly where MultipeerConnectivity doesn't exist, so one registration works in a cross-platform app. `HubHostInfo.Multipeer`, `HubConnection.Multipeer` and `mc:` connection ids say when a host or client is on it</RN>
<RN type="feature" platform="Android">New `Shiny.UniversalHubs.Nearby` package: hubs are also served and joined over Google's Nearby Connections (Android with Google Play services, iOS, macOS), so Android phones reach each other with no shared network, and Android and Apple devices on the same Wi-Fi. `server.Nearby("com.mycompany.mygame")` on the host, `o.Nearby("com.mycompany.mygame")` on the client, one service id per app. Every hub session is a channel inside one Nearby connection per pair of devices, so two hubs on one host, or two devices visiting each other, share it. Files, media channels and renames work over it. See [Nearby](/universalhubs/nearby)</RN>
<RN type="feature">`HubTransports.Nearby`, included in `HubTransports.All` and skipped where Nearby Connections doesn't exist. `HubHostInfo.Nearby`, `HubConnection.Nearby` (`NearbyPeer`) and `nb:` connection ids say when a host or client is on it. A hub client can use Multipeer and Nearby side by side</RN>
<RN type="enhancement">`HubConnectOptions.Prefer` is tried first, then Wi-Fi, Multipeer, Nearby and BLE in that order</RN>
<RN type="fix">Connecting to a host that restarted (it listens on a new port) no longer fails until the client app restarts. When none of a discovered host's addresses answer, the client looks it up again by name over mDNS and retries where it is now. `UniversalHubClientOptions.HttpRediscoverTimeout` (3 seconds) sets how long it looks</RN>
<RN type="feature">Dynamic hubs: hubs defined while the app runs, by a downloaded web app or a script, served over BLE, Wi-Fi and Multipeer beside the compiled ones. `AddUniversalServer(server => server.AllowDynamicHubs(o => o.ServiceTypes.Add("_myapp._tcp")))` fixes the service types they may use and how many there may be (`DynamicHubOptions.MaxHubs`, 6), and a server may start with no compiled hubs. `IDynamicHubs.Add(new DynamicHubDefinition(name, characteristicUuid, serviceType), handler)` returns an `IDynamicHub` to start, stop, push to (`DynamicHubPush.Send`) and group like a compiled one. An `IDynamicHubHandler` answers methods by name, with values as the caller serialized them. They share one Switchboard at `{Endpoint}/{hub}` with no protocol change. A hub added while the GATT service is up rebuilds it when it first starts, and the other hubs' BLE clients are asked to reconnect then. With dynamic hubs on, a tunnel reaches only hubs that allow it. See [Dynamic Hubs](/universalhubs/hosting#dynamic-hubs)</RN>
<RN type="feature">Dynamic hub clients: join a hub with no compiled contract. `services.AddDynamicHubClients(o => …)` registers `IDynamicHubClients`, whose `Create(characteristicUuid, mdnsServiceType)` returns an `IUniversalHubClient<IDynamicHubCalls>` that discovers and connects like any client. `IDynamicHubCalls` has `Invoke(method, args)`, `Stream(method, args)` and a `Pushed(name, args)` event, with values as serialized bytes (JSON with the default serializer). It works against compiled and dynamic hubs. See [Dynamic Hub Clients](/universalhubs/client#dynamic-hub-clients)</RN>
<RN type="enhancement">An error a hub relays keeps its type: throwing a `BleHubRemoteException` from a hub method sends the caller its `RemoteErrorType` rather than the exception's class name, over Wi-Fi and Multipeer as over BLE</RN>
