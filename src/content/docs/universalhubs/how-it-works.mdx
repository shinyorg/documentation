Universal Hubs adds a second transport to [BluetoothLE Hubs](/blehubs/how-it-works). The hub logic (dispatch,
`Clients`, groups, ordering, `MaxClients`) stays in BluetoothLE Hubs, and Universal Hubs carries calls through its
transport seams:

- **Host:** each hub's `IHubContext<THub>.TransportEndpoint` accepts clients from another transport, so BLE and Wi-Fi
  clients are registered in the same hub.
- **Client:** `BleHubClient.ConnectExternal` runs the same generated proxy over a Switchboard line instead of GATT.

[Multipeer](#multipeer) and [Nearby](#nearby) plug into the same seams and share one peer-to-peer wire.

## Wire Protocol

Each hub is one [Switchboard](/httpserver/switchboard) at `{Endpoint}/{characteristicUuid}`, `/hubs/...` by default.
The hub's own methods are not Switchboard methods. Reserved methods carry them by name, exactly like the BLE frames do:

| Call | Arguments | Returns |
|---|---|---|
| `hub.handshake` | `{protocol, name, appVersion, properties}` | `{accepted, reason, hostName, hostId, fileToken}` |
| `hub.invoke` | `method`, `[args...]` | `{"result": value}`, `{}` for `Task`, or `{"error": {type, message}}` |
| `hub.stream` | `method`, `[args...]` | a stream of `{"item": value}`, possibly ending with one `{"error": ...}` |
| `hub.push` (host → client) | `event`, `[args...]` | – |

- **Values.** Each value is the exact JSON that `IBleHubSerializer` produced. It's re-framed between BLE's argument
  format and a JSON array, and never re-serialized. A serializer that doesn't produce JSON fails with an explanatory
  error.
- **Errors** travel in envelopes, not as Switchboard errors, so the remote exception type and message survive as
  `BleHubRemoteException`, the same as over BLE.
- **Handshake.** It is the first call on a line. The host refuses other protocol versions, any handshake while the hub
  isn't running over Wi-Fi, and whatever the hub's own rules refuse.
- **Disconnect.** A host-initiated disconnect is a Switchboard hang-up that carries
  `{"reason": <HubDisconnectReason>, "message": ...}`, so the client reads the exact reason. `Context.Abort` hangs up
  after the reply has been sent.
- **Resume.** Switchboard's resume window means a dropped line that comes back keeps its connection id, so the hub
  sees nothing. `OnDisconnectedAsync` runs only when the line is gone for good.
- **Versioning.** `UniversalHubProtocol.Version` (currently 2) covers the reserved method names, envelopes, handshake
  records, TXT keys and file routes. The handshake refuses a mismatch.
- **[Dynamic hubs](/universalhubs/hosting#dynamic-hubs)** share one Switchboard at `{Endpoint}/{hub}`, mapped behind
  the compiled hubs' literal routes, and each line's handshake picks its hub from the path. Clients reach a dynamic hub
  at the same path as a compiled one, with no protocol change; an unknown one refuses the handshake with "Hub not
  found". With dynamic hubs on, a tunnel can't reach any other path under the endpoint.

## Discovery

**mDNS** advertises one instance per service type per host, named after the host's `LocalName`. Hubs that share a
type share one advertisement. Its TXT record carries:

| Key | |
|---|---|
| `proto` | The protocol version |
| `hostId` | `UniversalHubHostOptions.HostId` |
| `name` | The host's name |
| `path` | The endpoint (base path) |
| `hubs` | The running hubs' characteristic UUIDs, comma separated |

A TXT record fits about six hubs.

**BLE** advertises the one service UUID while any hub runs, so a BLE result says "a hub host", not which hubs.

**The client** merges the two by name, and fills in `hostId` from TXT and from the handshake reply.

## Files

Files are plain HTTP, not Switchboard:

- `PUT` / `GET {Endpoint}/files/{name}`, with the `X-Hub-File-Token` header set to the token from the handshake.
- They follow `BleHubHostOptions.EnableFileTransfers` (the directory, uploads and downloads allowed, overwrite,
  `MaxUploadSize`) plus `UniversalHubHostOptions.AuthorizeFile`.

| Status | Meaning |
|---|---|
| 400 | A bad name or path traversal |
| 401 | A missing or unknown file token |
| 403 | Refused by the host's rules |
| 404 | The file is missing, or file transfers are off |
| 409 | The file exists and overwrite is off |
| 411 | An upload without a length |
| 413 | An upload larger than `MaxUploadSize` |

## Media Channels

A media channel is an ordered packet pipe per client, next to its hub connection. Over Bluetooth it is the
[BluetoothLE Hubs media channel](/blehubs/files#media-channels), on its own L2CAP PSM. Over Wi-Fi it is a WebSocket:

- `GET {Endpoint}/media` as a WebSocket upgrade, with the `X-Hub-Media-Token` header set to the `mediaToken` from the
  handshake reply. One binary message is one packet, of at most `mediaMaxPacketSize` bytes.
- Both reply fields are null when the host has no media channels. They're optional, so the protocol version is
  unchanged.
- Through a tunnel, the route is open when any hub allows tunnels, and the token's own hub must allow them too.

| Status | Meaning |
|---|---|
| 400 | Not a WebSocket upgrade |
| 401 | A missing or unknown media token |
| 404 | The host has no media channels |

### Using Them

The channel is yours: blehubs and this library move whole packets in order and never look inside. The
[sample](https://github.com/shinyorg/hubs/tree/v1/samples)'s calls show one way to use it. Its packets carry
signalling and media, and the host relays calls between its clients. Video is latest-wins, and audio is PCM16 over
Wi-Fi and IMA ADPCM over Bluetooth.

## Multipeer

[Multipeer](/universalhubs/multipeer) uses the same seams as Wi-Fi, with the peer-link wire it shares with
[Nearby](#nearby).

- **One `MCSession` per hub connection.** The host accepts every invitation into a new, encrypted session. No 8-peer
  limit, and clients never connect to each other.
- **Discovery.** One advertisement per host under the Multipeer service type. Its `discoveryInfo` has the same keys as
  the mDNS TXT record (`proto`, `hostId`, `name`, `hubs`) and is replaced when the running hubs change. The host's peer
  id is kept across launches, so a relaunched host isn't listed twice.
- **Messages** are reliable and ordered:

  ```
  [0] version  [1] kind  [2..5] message id  [6] name length  [7..] name  [...] payload
  ```

  | Kind | Direction | Carries |
  |---|---|---|
  | `Handshake` / `HandshakeReply` | client → host → client | the hub's characteristic UUID; the reply has the host's name and id, and whether files and media channels are available |
  | `Invoke`, `Stream`, `Cancel` | client → host | the method and its arguments |
  | `Completion`, `StreamItem`, `StreamEnd`, `Error` | host → client | results, items, and errors with their type and message |
  | `Push` | host → client | the event and its arguments |
  | `Rename`, `HostRenamed` | both | a new name |
  | `Disconnect` | both | why the hub ended the session, or that the client is leaving |
  | `FileRequest`, `FileReply`, `FileDone` | both | file transfers (the file itself is a Multipeer resource) |
  | `MediaOpen`, `MediaOpened`, `MediaPacket`, `MediaClose` | both | the media channel |

- **Values** are the bytes `IBleHubSerializer` wrote, never JSON envelopes, so any serializer works.
- **Errors** keep the same types and wording as BLE and Wi-Fi.
- **Disconnects.** Each side says goodbye before ending the session. A session that ends without one is a
  `ClientTimeout`. There is no resume.
- **Versioning.** `PeerProtocol.Version` (currently 1) covers the message layout, kinds, control records,
  advertisement keys and file resource names, for Multipeer and Nearby alike. The handshake refuses a mismatch.

## Nearby

[Nearby](/universalhubs/nearby) carries the same messages as Multipeer, over Google's Nearby Connections. What's
different is underneath them:

- **One connection per pair of devices, many channels.** Nearby allows one connection between two devices, and one
  advertisement and one discovery per app. So each device keeps one connection per remote device and carries every hub
  session as a channel inside it, opened from either end. Two hubs on one host, or two phones visiting each other, share
  one connection. It hangs up two seconds after its last channel closes.
- **Discovery.** One advertisement per host. Its endpoint info (at most 131 bytes) is the protocol version, the host id,
  a 4-byte tag per running hub (the start of SHA-256 of its characteristic UUID) and the host's name, cut to fit.
  Clients only list hosts running their hub.
- **Frames.** Each Nearby payload is one frame: a kind (`Message`, `Part`, `Last`, `Open`, `Close`, `FileName`), a bit
  for which end opened the channel, and the channel's number. A message over Nearby's 32 KB payload limit travels as
  `Part`s and a `Last`, never interleaved with another message on its channel.
- **Files** are Nearby file payloads. A `FileName` frame ties each one to its channel and name; it may arrive before or
  after the file.
- **Versioning.** `PeerProtocol.Version` covers the endpoint info and frames too. `NearbyFrameKind` values never change.

## Best Practices

- **Set your own service UUID and mDNS service types**, so other apps' hosts stay out of your scans.
- **Give hosts distinct names.** Discovery merges BLE and mDNS results by name.
- **Persist `HostId`** if clients should recognize a host across app restarts.
- **Keep BLE as the fallback.** Plane, hotel and public Wi-Fi usually block device-to-device traffic.
  [Multipeer](/universalhubs/multipeer) (Apple devices) and [Nearby](/universalhubs/nearby) work there too.
- **Test on real devices**, both ways round (an iOS host with an Android client, and the reverse), on Wi-Fi and with
  Wi-Fi off.
