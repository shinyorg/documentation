## v1.0.0 - TBD
<RN type="feature">Command-object pattern with generic return types (`IObdCommand<T>`, `ObdCommand<T>`) for compile-time safe OBD communication</RN>
<RN type="feature">9 standard OBD-II commands: Vehicle Speed, Engine RPM, Coolant Temperature, Throttle Position, Fuel Level, Calculated Engine Load, Intake Air Temperature, Runtime Since Start, VIN</RN>
<RN type="feature">ELM327 protocol handling with hex response parsing, multi-frame CAN support, and automatic error detection</RN>
<RN type="feature">Adapter auto-detection — probes via ATI to identify ELM327 vs OBDLink (STN) adapters and selects the appropriate initialization sequence</RN>
<RN type="feature">Adapter profile system (`IObdAdapterProfile`) with built-in `Elm327AdapterProfile` and `ObdLinkAdapterProfile`</RN>
<RN type="feature">Device discovery via `IObdDeviceScanner` and `ObdDiscoveredDevice` for scanning available adapters before connecting</RN>
<RN type="feature">Pluggable transport abstraction (`IObdTransport`) for BLE, WiFi, USB, or any communication channel</RN>
<RN type="feature">BLE transport (`BleObdTransport`) using Shiny.BluetoothLE v4 with auto-scan, pre-discovered peripheral, or discovered device constructors</RN>
<RN type="feature">BLE device scanner (`BleObdDeviceScanner`) with optional name filtering and UUID-based deduplication</RN>
<RN type="feature">Configurable BLE defaults (`BleObdConfiguration`) for GATT UUIDs, device name filter, and command timeout</RN>
<RN type="feature">DI extension method `AddShinyObdBluetoothLE()` for one-call BLE OBD service registration</RN>
<RN type="feature">Fully task-based async throughout — no Reactive Extensions required in consuming code</RN>
<RN type="feature">`ObdTimeoutException` (an `ObdException`) reports an adapter that went quiet, carrying the `Command` and the `Timeout` that elapsed — a polling caller can tell it apart from its own cancellation instead of mistaking one slow reply for a shutdown</RN>
<RN type="fix">BLE scanning falls back to the advertised local name when the peripheral reports none, so adapters now turn up on iOS — `CBPeripheral.Name` is null while scanning a peripheral that has never been connected to, which meant `BleObdDeviceScanner` and `BleObdTransport`'s auto-scan silently discarded nearly every adapter on that platform</RN>
<RN type="feature">`BleObdDeviceScanner` logs every advertisement it sees at `Debug` level — resolved name, `Peripheral.Name`, id, RSSI and advertised service UUIDs — before any filtering, so an adapter that never reaches the callback can still be identified and its real UUIDs read off</RN>
<RN type="fix">`BleObdTransport` drops a late reply to a command that already timed out rather than letting it complete the *next* command's wait, which used to leave every response after a single timeout off by one</RN>
<RN type="fix">`BleObdTransport.Disconnect()` fails an in-flight command immediately instead of leaving the caller to wait out the full command timeout, and `DisposeAsync()` no longer disposes the send lock out from under a pending send</RN>
<RN type="fix">Multi-frame CAN responses now drop the ELM327's leading byte-count line, so `StandardCommands.Vin` (mode 09 PID 02) and mode 03 replies carrying three or more trouble codes parse instead of failing. The count line (`014`) is framing rather than payload, but it parses cleanly as `0x14`, which shifted every byte of the response along by one and made the mode-echo check reject an otherwise good reply with "Unexpected mode response". Single-frame responses carry no such line and were never affected</RN>
<RN type="fix">Multi-frame responses parse whether or not the adapter is spacing its hex — an unspaced run (`0:490201574241`) used to fail to parse as a single token and be discarded in full, losing the whole response on clones that ignore `ATS1`</RN>
