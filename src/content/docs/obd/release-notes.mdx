## v1.0.0 - TBD
<RN type="feature">Command-object pattern with generic return types (`IObdCommand<T>`, `ObdCommand<T>`) for compile-time safe OBD communication</RN>
<RN type="feature">Standard OBD-II commands on `StandardCommands`: Vehicle Speed, Engine RPM, Coolant Temperature, Throttle Position, Fuel Level, Calculated Engine Load, Intake Air Temperature, Runtime Since Start, VIN, Odometer, Distance Since Codes Cleared, Control Module Voltage, Mass Air Flow, Engine Fuel Rate, Engine Oil Temperature, Fuel Type, Hybrid Battery Life and Monitor Status</RN>
<RN type="feature">`MonitorStatusCommand` (mode 01 PID 01) decodes all four bytes: the malfunction indicator lamp, the stored code count, the ignition type and every emissions monitor the vehicle supports, with `MonitorStatus.IsReadyForInspection` answering the question an emissions test actually asks. `MonitorStatusThisDriveCycleCommand` (PID 41) reports the same monitors for the current drive cycle. `MonitorStatusDecoder` is public and testable without a transport, like `DtcDecoder` — the bit layout it hides is worth knowing about: the completion flags are inverted (a set bit means the test is still running), and bytes C/D describe a different set of monitors on a diesel than on a petrol car. Unsupported monitors are left out of the list rather than reported incomplete, since a monitor a car does not have has no readiness state</RN>
<RN type="feature">Freeze frames (mode 02): `AsFreezeFrame()` on any mode 01 command reads that same PID out of the snapshot the ECU stored when a code was set, reusing the mode 01 scaling rather than duplicating a command per PID, and `FreezeFrameCommands.CausalDtc()` returns the code that stored the frame — or null when there is no snapshot at all, which is the check that has to come first, because an empty frame is zero-filled and reads back as a 0% engine load at -40 °C rather than as an absence</RN>
<RN type="feature">`FuelSystemStatusCommand` (PID 03) reports the loop state of one or two fuel systems, with `IsClosedLoop` as the gate a caller needs before trusting a fuel trim — in open loop the ECU runs a fixed map with no oxygen sensor feedback, so a trim figure there says nothing about a leak or a lazy sensor. A zero in byte B means the vehicle has only one fuel system and answers null, unlike a zero in byte A, which means the engine is off</RN>
<RN type="feature">Driver input, distinct from throttle plate position: `AcceleratorPedalPositionCommand.D()`/`.E()`/`.F()` (PIDs 49/4A/4B) and `RelativeAcceleratorPedalPosition` (PID 5A), plus `CommandedThrottleActuator` (PID 4C) for what the ECU is asking the plate to do. `ThrottlePosition` (PID 11) is *absolute* throttle with a 12-18% closed floor that varies by vehicle, so anything measuring how hard a car is being driven from it has to discover that floor first; PID 5A is already normalised and needs no such correction</RN>
<RN type="feature">`IntakeManifoldPressure` (PID 0B) and `BarometricPressure` (PID 33) — the speed-density pair, for the many vehicles that report no MAF at all, and the ambient reference that turns manifold pressure into boost or vacuum</RN>
<RN type="feature">`TimingAdvanceCommand` (PID 0E) in degrees before top dead centre, negative for retard — a vehicle persistently running less advance than it used to at comparable load is pulling timing, which is what a knock sensor does on poor fuel or carbon build-up</RN>
<RN type="feature">`AmbientAirTemperatureCommand` (PID 46) — the air outside the vehicle, which is not `IntakeAirTemperature` (PID 0F): intake air is measured after the engine bay has warmed it and a turbo has compressed it</RN>
<RN type="feature">`DistanceWithMilOn` (PID 21), `TimeRunWithMilOn` (PID 4D) and `TimeSinceCodesCleared` (PID 4E) — how far and how long a fault has been ignored, and the denominator for anything trended since the last reset. Note both timers are whole **minutes**, unlike `RuntimeSinceStart`'s seconds</RN>
<RN type="feature">`CalibrationIdCommand` (mode 09 PID 04) returns the ECU software calibration identifiers as 16-byte ASCII blocks — the one thing on OBD-II that reveals a manufacturer reflash or an aftermarket tune. The leading count byte is detected by block remainder rather than assumed, since not every ECU sends one</RN>
<RN type="feature">`FuelTrimCommand` covers short and long term trim on both banks (PIDs 06/07/08/09) with static factories per bank. 128 is zero correction, so the parsed value is a signed percentage and sustained drift either way reads directly</RN>
<RN type="feature">`FuelTypeCommand` (PID 51) with `FuelTypes.Describe` naming the SAE J1979 table. An unlisted code and `0x00` both answer **null** rather than "Unknown", so a caller storing or displaying the result can tell an absent answer from a claim about the vehicle</RN>
<RN type="feature">`SupportedPidsCommand` reads the mode 01 bitmask blocks (`SupportedPidsCommand.BlockPids`) and returns the PIDs the vehicle actually answers, so a caller can poll only what is really there and surface the rest as missing rather than zero</RN>
<RN type="feature">Diagnostic trouble codes: `DtcReadCommand.Stored`/`.Pending`/`.Permanent` (modes 03/07/0A) return SAE J2012 strings such as `"P0301"`, and `ClearDtcCommand.Instance` (mode 04) clears them. These modes carry no PID, so they implement `IObdCommand<T>` directly rather than extending `ObdCommand<T>`</RN>
<RN type="feature">`DtcDecoder` is public and usable on its own. It distinguishes a CAN reply (`43 <count> <pairs>`) from a pre-CAN one (`43 <pairs>`) by payload parity rather than by assuming a transport, and drops the `0x0000` padding that fills out a fixed-size frame</RN>
<RN type="feature">ELM327 protocol handling with hex response parsing, multi-frame CAN support, and automatic error detection</RN>
<RN type="feature">Adapter auto-detection — probes via ATI to identify ELM327 vs OBDLink (STN) adapters and selects the appropriate initialization sequence</RN>
<RN type="feature">Adapter profile system (`IObdAdapterProfile`) with built-in `Elm327AdapterProfile` and `ObdLinkAdapterProfile`</RN>
<RN type="feature">Device discovery via `IObdDeviceScanner` and `ObdDiscoveredDevice` for scanning available adapters before connecting</RN>
<RN type="feature">Pluggable transport abstraction (`IObdTransport`) for BLE, WiFi, USB, or any communication channel</RN>
<RN type="feature">BLE transport (`BleObdTransport`) using Shiny.BluetoothLE v4 with auto-scan, pre-discovered peripheral, or discovered device constructors</RN>
<RN type="feature">BLE device scanner (`BleObdDeviceScanner`) with optional name filtering and UUID-based deduplication</RN>
<RN type="feature">Configurable BLE defaults (`BleObdConfiguration`) for GATT UUIDs, device name filter, and command timeout</RN>
<RN type="feature">DI extension method `AddShinyObdBluetoothLE()` for one-call BLE OBD service registration</RN>
<RN type="feature">Fully task-based async throughout — no Reactive Extensions required in consuming code</RN>
<RN type="feature">`ObdTimeoutException` (an `ObdException`) reports an adapter that went quiet, carrying the `Command` and the `Timeout` that elapsed — a polling caller can tell it apart from its own cancellation instead of mistaking one slow reply for a shutdown</RN>
<RN type="fix">BLE scanning falls back to the advertised local name when the peripheral reports none, so adapters now turn up on iOS — `CBPeripheral.Name` is null while scanning a peripheral that has never been connected to, which meant `BleObdDeviceScanner` and `BleObdTransport`'s auto-scan silently discarded nearly every adapter on that platform</RN>
<RN type="feature">`BleObdDeviceScanner` logs every advertisement it sees at `Debug` level — resolved name, `Peripheral.Name`, id, RSSI and advertised service UUIDs — before any filtering, so an adapter that never reaches the callback can still be identified and its real UUIDs read off</RN>
<RN type="fix">`BleObdTransport` drops a late reply to a command that already timed out rather than letting it complete the *next* command's wait, which used to leave every response after a single timeout off by one</RN>
<RN type="fix">`BleObdTransport.Disconnect()` fails an in-flight command immediately instead of leaving the caller to wait out the full command timeout, and `DisposeAsync()` no longer disposes the send lock out from under a pending send</RN>
<RN type="fix">Multi-frame CAN responses now drop the ELM327's leading byte-count line, so `StandardCommands.Vin` (mode 09 PID 02) and mode 03 replies carrying three or more trouble codes parse instead of failing. The count line (`014`) is framing rather than payload, but it parses cleanly as `0x14`, which shifted every byte of the response along by one and made the mode-echo check reject an otherwise good reply with "Unexpected mode response". Single-frame responses carry no such line and were never affected</RN>
<RN type="fix">Multi-frame responses parse whether or not the adapter is spacing its hex — an unspaced run (`0:490201574241`) used to fail to parse as a single token and be discarded in full, losing the whole response on clones that ignore `ATS1`</RN>
