## 1.0 - TBD

Initial Release

<RN type="fix">**FrostedGlass (Blazor): `CssClass` is applied again.** The parameter was declared and documented, but the root element's class attribute was hard-coded to `shiny-frosted-glass`, so anything you passed was silently dropped — there was no way to hang your own styling on the glass surface. The class list is now `shiny-frosted-glass` plus whatever you supply. See [FrostedGlassView](/controls/frostedglass/)</RN>

<RN type="feature">**MediaElement — audio and video on every target, with a transport bar you can take apart.** New `Shiny.Maui.Controls.MediaElement` and `Shiny.Blazor.Controls.MediaElement` packages (plus `Shiny.Maui.Controls.MediaElement.Linux` for the GTK4 head) play local and remote media on iOS, Android, Windows, Mac Catalyst, macOS AppKit, Linux and Blazor, each on the platform's real player — AVPlayer, Media3/ExoPlayer, `Windows.Media.Playback`, `GtkMediaFile`, HTML5. **The transport bar is drawn by Shiny rather than handed to the platform**, and that is the whole reason `ShowPlayPauseButton`, `ShowSeekBar`, `ShowVolumeControl`, `ShowFullScreenButton`, `ShowTimeLabels` and `ShowPictureInPictureButton` are six independent properties: native transport UI is all-or-nothing on every platform except Windows — iOS has a single `showsPlaybackControls`, HTML5's `controlsList` can only subtract download/fullscreen/cast and only in Chromium, and GTK's `GtkMediaControls` has no options at all. Drawing it also means one look everywhere, themed from your theme pack (the scrubber follows `Shiny.Color.Primary` unless you set `SeekBarColor`), and a purpose-built `MediaSeekBar` that shows buffered-ahead as a second track and reports drag start/stop so the playhead stops fighting your finger. Commands on MAUI (`PlayCommand`, `PauseCommand`, `StopCommand`, `TogglePlayPauseCommand`, `SeekCommand`, `MuteCommand`, `ToggleFullScreenCommand`, `PictureInPictureCommand`), methods on Blazor. `SeekCommand` takes a `TimeSpan`, seconds, or a string of either — `CommandParameter="30"` is thirty *seconds*, because XAML can only pass a string and `TimeSpan.Parse` would have read that as thirty days. The architectural bet is that **an `IMediaPlayerBackend` owns the player and the *view* gets pushed into it**, which is what makes the two hard features real rather than approximations: entering fullscreen hands the same running player to a second surface on a modal page, so nothing re-buffers and your layout is untouched; and **background audio** detaches the video surface entirely while the sound keeps going. `EnableBackgroundPlayback` + `Metadata` drive the OS transport UI — `MPNowPlayingInfoCenter` + `MPRemoteCommandCenter` on Apple, a Media3 `MediaSession` behind a `mediaPlayback` foreground service on Android (the service and its permissions are contributed to your merged manifest), SMTC on Windows, `navigator.mediaSession` on Blazor. **Picture-in-Picture** covers the case background audio cannot: `AVPictureInPictureController` on iOS/Catalyst, `EnterPictureInPictureMode` on Android 8+, `requestPictureInPicture()` on Blazor. Two opt-ins remain **the app's** and a library cannot make them for you — iOS needs `audio` in `UIBackgroundModes`, and Android needs `SupportsPictureInPicture = true` on the activity plus the `POST_NOTIFICATIONS` runtime grant. Because support genuinely differs, `Capabilities` reports what the current backend will actually honour and the bar hides the rest: WinUI has no per-element PiP (a compact-overlay `AppWindow` shrinks the whole window, which is a different thing, so it is not offered as PiP), GTK has no rate control and no buffered figure, and iOS Safari refuses programmatic volume — which the Blazor backend detects by writing a value and reading it back, then drops the volume slider rather than leaving a dead control. See [MediaElement](/controls/mediaelement/)</RN>

<RN type="breaking">**`Shiny.Blazor.Controls.Kiosk` is gone — docking now ships in `Shiny.Blazor.Controls`.** The add-on existed to pair with the MAUI-side `Shiny.Maui.Controls.Desktop`, on the theory that it would carry both docking *and* a kiosk on-screen keyboard. Only docking was ever built, which left a whole package, its own README section and its own NuGet listing standing up one feature — and a "Kiosk" name that told you nothing about what was inside it. It is now part of the main Blazor controls package. **To migrate:** drop the `Shiny.Blazor.Controls.Kiosk` package reference (`Shiny.Blazor.Controls` already carries it) and change `using Shiny.Blazor.Controls.Kiosk.Docking` to `using Shiny.Blazor.Controls.Docking` — the namespace loses the `.Kiosk` segment because the concept it named no longer exists. Nothing else changes: `DockHost`, `IDockHost`, `AddShinyDocking()`, `AddDockPanel<T>()`, the layout schema and its JSON round-trip are all identical. The bundled script moves with it, from `_content/Shiny.Blazor.Controls.Kiosk/docking.js` to `_content/Shiny.Blazor.Controls/docking.js` — relevant only if you referenced it directly rather than letting `DockHost` load it. MAUI is untouched: docking there still ships in `Shiny.Maui.Controls.Desktop`, which remains a separate add-on because it genuinely carries three features and a desktop-only TFM matrix. The on-screen keyboard is still unimplemented on both hosts; when it lands on Blazor it will live in `Shiny.Blazor.Controls` too. See [Docking](/controls/docking/)</RN>

<RN type="feature">**TableView's EntryCell borrows TextEntry's input behaviour — masks, the keyboard accessory bar, and the autocomplete opt-out.** Deliberately *only* the input behaviour: no tool slots, no floating label, no hint text, no character count, because the cell already supplies a title, description and hint of its own and stacking a second set inside it would be nonsense. `Mask` works exactly as it does on `TextEntry` — `#` is a digit slot, everything else is a literal inserted as you type, `ValueText` stays the **raw digits** so what you bind and validate is never punctuation, and `FormattedValueText` is what is on screen — with the keyboard and max length set from the mask. `Accessory` / `AccessoryPreset` dock a bar to the top of the soft keyboard on iOS and Android, and `FieldGroup` scopes its prev/next arrows to one section rather than every input on the page. `IsAutoCompleteEnabled="False"` switches off autofill, autocorrect, prediction and spell check together — settings forms being exactly where the OS likes to overwrite a half-typed serial. Because `TableView` is a plain scroller rather than a virtualized list, every cell is realized and prev/next reaches all of them. Making this shareable meant lifting the accessory's platform plumbing out of `TextEntry` into a binder both controls drive, and generalizing the bar's owner behind a new `IKeyboardAccessoryHost` — the two controls differ in exactly two ways the bar cares about: which element the navigator treats as "this field" (a `TextEntry` is collected as its wrapper, an `EntryCell` as the input inside it) and how the keyboard is dismissed. Masking is shared through one `MaskedInput` helper so the two cannot drift on the fiddly bits — over-length input clipped to the mask's slot count, and where the caret lands once the literals are re-inserted. On Blazor, `EntryCell` gains `Mask` and `IsAutoCompleteEnabled`; there is no accessory bar there, for the same reason `TextEntry` has none. See [EntryCell](/controls/tableview/cells/#entrycell)</RN>

<RN type="feature">**TextEntry: a keyboard accessory bar (iOS + Android).** A bar docked to the **top edge of the soft keyboard** while a field has focus — it belongs to the keyboard, not to the entry, so it arrives with the keyboard and leaves with it, and nothing is drawn inside the field. The reason it exists is blunt: **the iOS numeric keypad has no return key**, so a numeric field without a Done button cannot be dismissed at all. `AccessoryPreset="Done" | "Navigation" | "NavigationAndDone"` gets a stock bar with no markup; `Accessory` takes a `KeyboardAccessoryView` built from `KeyboardAccessoryItem`, `KeyboardNavigationItem`, `KeyboardDismissItem` and `KeyboardAccessorySpacer` (which flexes, so it is how items get pushed apart), or a `BarContent` view for something that is not a row of buttons. Prev/next resolve through `KeyboardFieldNavigator` — every enabled, visible, non-read-only field under the page in depth-first visual-tree order, since MAUI has no `TabIndex` to honour — and `FieldGroup` narrows that to a subset. **iOS uses the real `UIResponder.InputAccessoryView`**, so the OS owns it and it rides the keyboard animation exactly. **Android has no accessory API at all** (the IME is a separate process; only an IME app can draw in it), so the same bar is rendered in the activity's content view and pushed up by however much the IME *actually* overlaps it — measured rather than assumed, so `adjustResize`, `adjustPan` and forced edge-to-edge on API 35+ are all correct — frame-synced to the IME animation through `WindowInsetsAnimation` on API 30+. Because it tracks the IME insets rather than focus, a device with a hardware keyboard attached correctly shows no bar. Windows/macOS/Linux have no soft keyboard and the property compiles to nothing; **there is no Blazor version on purpose** — iOS Safari draws its own bar and will not let a page remove it, so ours would stack on top and the user would see two. Not to be confused with [On-Screen Keyboard](/controls/onscreen-keyboard/), which draws keys. See [Keyboard Accessory](/controls/textentry/keyboard-accessory/)</RN>

<RN type="fix">**TextEntry: the floating label no longer lands on top of the text you are typing.** The old `Variant="Floating"` translated the placeholder up by a fixed 14 units and scaled it about its own centre while it was still parented inside the field — so on any font size, tool arrangement or platform where those numbers did not happen to line up, the label sat off-centre at rest and overlapped the first line of input once floated. `Floating` is now a proper **Material 3 outlined notch**: the label overlays the border rather than living inside it, and floats up **onto the top stroke**, where it paints the field colour behind itself and sits in a gap cut out of the outline. It leaves the text area completely, so overlap is not something that can happen. The geometry is measured rather than assumed — rest position from the field's height, float position from the label's own height, horizontal offset from the leading tools — so a leading icon shifts the notch past it and the control reserves the half-label that pokes above the border instead of overlapping whatever sits above it. Following M3, a floated-but-unfocused label now stays muted instead of accenting, so a filled form is not a wall of primary-coloured labels. Blazor matches, and gains the `Variant` parameter it never had (defaulting to `Classic`, like MAUI — previously it always floated); its label also stops switching `transform-origin` mid-animation, which was making it jump sideways as it moved.</RN>

<RN type="enhancement">**TextEntry: tools sit on the field instead of in a grey block.** Left/right tools rendered as Bootstrap input-group addons — a filled `surface-container-high` slab with a hairline separator, on a control that is otherwise a Material text field. They are **inline** by default now: a tinted glyph on the field itself, no separator, no slab, a 40pt tap target, and the field's own padding tightening on that side so a leading icon does not sit a full 24pt from the text. `ToolStyle="Addon"` brings the old look back per control. Tools also follow the theme now — `ToolColor` is nullable and falls through to the on-surface-variant token instead of defaulting to a hard-coded grey, and it tints the **glyph as well as the label** when `Icon` is a `FontImageSource` (MAUI cannot tint a bitmap `Image`, and never could). New on the tool: `FontSize` and `IconSize`. Blazor matches, and its colour parameters (`BorderColor`, `PlaceholderColor`, `TextColor`, `HintColor`, `ErrorColor`, `EntryBackgroundColor`, `TextEntryTool.ToolColor`) now default to theme tokens rather than hard-coded hex — a themed app previously got a text field that ignored its own palette. **Behaviour change:** tools default to inline, so anything relying on the addon look needs `ToolStyle="Addon"`.</RN>

<RN type="feature">**TextEntry: `IsAutoCompleteEnabled="False"`.** Autofill, autocorrect and predictive text are three separate platform switches and any one of them will happily rewrite a half-typed serial number, coupon code or SKU — MAUI exposes two of them and nothing at all for autofill, which is the one that replaces the field wholesale with a saved address. One property turns off all four (the third being spell check): on **iOS** `AutocorrectionType`/`SpellCheckingType` off plus an empty `TextContentType`, the documented opt-out from AutoFill and the strong-password sheet; on **Android** `TextFlagNoSuggestions` plus `ImportantForAutofill.NoExcludeDescendants` — password fields are deliberately left alone there, since assigning `InputType` would clear the mask and autofill on a password field is wanted. `IsSpellCheckEnabled` and `IsTextPredictionEnabled` remain individually settable for when only one of them is in the way. On **Blazor** it emits `autocomplete="off"`, `autocorrect="off"`, `autocapitalize="off"` and `spellcheck="false"` together with `data-lpignore` / `data-1p-ignore` / `data-form-type="other"`, because `autocomplete="off"` alone is widely ignored by both Chrome and the password managers.</RN>

<RN type="enhancement">**ChatView: the B/I/U formatting toolbar moved above the entry.** It sat between the text and the control row, which meant it drifted down the card line by line as the multiline entry auto-grew — the buttons were never twice in the same place, and on a tall message they ended up sitting right on top of the send row. The card now reads formatting → entry → controls, so the format buttons stay pinned to the top edge whatever the entry does. Nothing else changes: the same buttons appear per `MessageBodyPermissions`, wrapping the current selection exactly as before (the Blazor toolbar reads `selectionStart`/`selectionEnd` off the textarea, so losing focus to a button is still harmless). Both hosts match. See [The Composer](/controls/chatview/composer/)</RN>

<RN type="enhancement">**FabMenu's items are pills now.** Each action used to be two detached pieces — a small rounded label chip floating beside a coloured circle, with a gap of backdrop between them — which meant two tap targets, two shadows and two silhouettes per row. An item is now **one capsule**: the label sits inside it with a tinted circular icon chip on the edge nearest the main FAB, so the whole row is a single tap target with one shadow. The chip is inset by half its gap on every side, which puts its centre exactly `Size/2` from the pill edge — the same place a text-less item's centre sits — so **every chip lines up on the main FAB's vertical axis** whatever the labels do, and the stack reads as one column instead of a ragged edge. An item with no `Text` still collapses to a plain circle rather than drawing a circle inside a capsule. Colours now come from the theme (`SurfaceContainerHigh` body, `OnSurface` label, an `OutlineVariant` hairline) instead of hard-coded white/black, so a dark theme no longer needs every item recoloured by hand; set `FabBackgroundColor` per item to tint just its chip. Items animate in with scale as well as fade and travel, anchored on that same axis, and the main FAB **rotates 45°** while the menu is open — the classic "+" turning into an "×" — via the new `IconRotation` (0 disables it; it is skipped when the main FAB carries a `Text` label, where a rotated word reads as broken). New on `FabMenuItem`: `HasShadow` and `FontAttributes`. Blazor matches, and gains `FabSize`, `HasShadow`, `IconRotation` and `MenuAlignment` (`"start"` grows the menu from the left and flips the chip to the leading edge) plus a 2px backdrop blur and full `prefers-reduced-motion` support. **Behaviour changes worth noting**: `FabMenuItem.BorderColor`/`BorderThickness` now stroke the *pill* rather than the icon circle, and `BorderThickness` defaults to `1` — set it to `0` for a borderless pill. Also fixed on Blazor: the main FAB painted *behind* the backdrop while the menu was open, because `.shiny-fab-menu` never claimed a `z-index` above it. See [FabMenu](/controls/fab/fabmenu/)</RN>

<RN type="fix">**ImageViewer (Blazor): panning a zoomed image works again.** The overlay `<img>` was left with the browser's defaults, so a drag on it started a **native HTML5 image drag** — the browser fires `dragstart` and immediately follows it with `pointercancel`, tearing down the pointer stream two or three moves into the gesture. The pan therefore travelled a few pixels and then froze for the rest of the drag. The image now opts out of native dragging (`draggable="false"`, `-webkit-user-drag: none`, plus a `dragstart` guard for the browsers that ignore the attribute) and carries `touch-action: none` of its own — the value was set on the overlay root, but `touch-action` does not inherit, so on touch devices the browser was still free to claim the gesture as a scroll and cancel it the same way. Also fixed: a double-tap zoom captured its pan origin *before* the zoom moved the image, so continuing to drag out of the double-tap jumped the image by the zoom offset.</RN>

<RN type="feature">**ImageEditor: zoom and pan now work in every tool** — the point being that you can magnify to 8x and *then* draw, crop or place text, which is the difference between annotating an image and correcting one. Zoom used to be a native view transform available only in Move mode, and switching to any other tool animated it away; it is now a transform on the **drawing surface**, which means the image and every annotation are re-rendered at scale (crisp all the way in, not a magnified bitmap) and touch points are mapped **back through** the transform before any tool math runs. Pinch anywhere with two fingers, two-finger drag to pan without leaving the tool, double-tap to toggle, or use the new toolbar zoom cluster (out / live % / in / fit — tapping the % returns to fit). Blazor adds wheel-zoom about the cursor and middle-button pan. New members: `ZoomLevel` (TwoWay), `MinZoom`, `MaxZoom` (8 by default), `ShowZoomControls`, `ZoomIn()`/`ZoomOut()`/`ZoomToFit()`, the matching commands, and a `ZoomChanged` event; Blazor mirrors them as `ZoomLevelChanged` plus `ZoomInAsync`/`ZoomOutAsync`/`ZoomToFitAsync`/`SetZoomAsync`. Details that make it usable rather than merely present: pan is **clamped** so the image cannot be lost off-screen; crop handles, hairlines and the image border keep a **constant on-screen size** at any zoom, with the crop hit-targets shrinking in image space to match; a second finger arriving mid-stroke turns the gesture into a zoom and **discards** the partial stroke instead of committing a stray mark; dragging outside the crop box pans rather than fighting you; and entering crop returns to fit-to-view, since the crop rect is normalised against the whole image. See [Zoom & Pan](/controls/imageeditor/zoom/)</RN>

<RN type="enhancement">**ImageEditor's toolbar has been rebuilt.** It was a two-row `HorizontalStackLayout` of unicode-glyph buttons that ran straight off the edge of a phone screen — the last few tools were simply unreachable. It is now a floating rounded bar with three purposeful rows: the tool picker in a **horizontal scroller** so it never clips however many tools are enabled; a **contextual options row** that appears for the active tool only (colour swatch, pen-weight presets, font and size pickers) instead of everything competing for the same strip; and an action row with undo/redo/reset on the left, the zoom cluster centred and save on the right. Icons are **stroked vector paths on a 24x24 grid**, not unicode glyphs — those rendered at wildly different weights per platform and fell back to tofu on some Android fonts. New: `ShowToolLabels` (captions under each icon, on by default; off gives a compact icon-only bar), `ShowStrokeWidthPicker` and `StrokeWidthPresets` (2/4/8), and `ToolbarBackgroundColor`. Undo/redo/reset now toggle their enabled state **in place** rather than rebuilding the bar on every stroke. `DrawStrokeWidth` became TwoWay so the weight picker can write back to it, and `CropApplyText`/`SaveText` default to plain `"Apply"`/`"Save"` rather than a glyph.</RN>

<RN type="fix">**ImageEditor: annotations no longer come out hairline-thin when exported at full resolution.** Stroke widths and font sizes were stored in on-screen pixels and replayed verbatim at export, so a 3px pen drawn on a 400px preview exported as 3px on a 4000px image — effectively invisible. Strokes, lines and text now record the image-rect width they were captured against, and rendering scales them to whatever rect is being drawn into, so the export matches the preview (and a stroke made while zoomed in keeps the size it looked like). `DrawStrokeAction`, `LineAction` and `TextAnnotationAction` carry a new `ReferenceWidth`; zero means "unscaled", so anything constructing these by hand keeps its old behaviour.</RN>

<RN type="fix">**ImageEditor (MAUI): tool gestures and zoom no longer fight over the same touches.** Pinch/pan were `GestureRecognizer`s while draw/crop/text ran off `GraphicsView`'s interaction events, and the two cannot coexist — the recognizer swallows the touch and the tool never sees the drag, which is why zoom was restricted to Move mode in the first place. Everything is driven from the interaction events now, which carry the full touch array, so a two-finger pinch is handled directly and works in every mode. Text placement also fired twice (once from `StartInteraction`, once from a `TapGestureRecognizer`), recreating the entry and flickering focus; there is one path now.</RN>

<RN type="fix">**ChatView now actually opens at the newest message.** Two bugs stacked up here. The session load called `ApplyInfo()` — which tears the items source down and rebuilds it on a dispatch — *after* the first page had queued its initial scroll, so the rebuild landed between the two: the offset reset to the top and the `ScrollTo` then fired against a `CollectionView` that had not laid out yet and was silently dropped. `ApplyInfo()` now runs before the first page loads, and `RefreshBubbles()` both skips itself mid-reload and restores the reader's position afterwards. Separately, `ItemsUpdatingScrollMode` was never set, so the control was on MAUI's default `KeepItemsInView` — the opposite of chat semantics. It is now driven by scroll state: `KeepLastItemInView` while you are at the live edge (the handler runs that scroll *after* the layout pass, so unlike `ScrollTo` it cannot fire against an unmeasured item), and `KeepScrollOffset` the moment you scroll away or older history is being prepended. Explicit jumps (`ScrollToEnd`, `ScrollToMessage`, first-unread) re-issue across the next couple of layout passes rather than assuming the first attempt lands. Paging also no longer hangs off `RemainingItemsThresholdReached`, which fires as you approach the *end* of the list — in a chat that is the newest message, so **reaching the bottom used to load older history**; it is driven off the scroll position now, and a prepended page re-anchors on the row you were reading. On Blazor a `MutationObserver` plus an image `load` hook keep the list pinned while late-resolving images and webfonts settle, instead of a single post-render `scrollToEnd` that fired while the content was still short.</RN>

<RN type="feature">**ChatView's composer is a control of its own** — `ChatEntryView` (MAUI) / `ChatEntry` (Blazor): a rounded, auto-growing **multiline** entry with optional attach / overflow buttons, the markdown toolbar and a send button. `ChatView` builds and hosts one automatically, so existing markup is unchanged; supply your own via `ChatView.InputBar` (MAUI) or `ChatView.InputTemplate` (Blazor) to reshape it, or use it standalone as an AI prompt box or comment field. It deliberately has **no reference to `IChatSessionProvider` or `IChatSession`** — `ChatView` stays the only thing that talks to the session, pushing state in (`SetBodyPermissions`, `ShowAttachButton`, `SetInputEnabled`) and listening to events out. Properties: `Text`, `PlaceholderText`, `MaxLines` (6, computed from the live font metrics), `FontSize`/`FontFamily`, `SendButtonText`/`SendButtonBackgroundColor`/`SendButtonTextColor`, `BarBackgroundColor`, `ComposerBackgroundColor`, `BorderColor`, `BorderThickness`, `CornerRadius` (24), `ShowAttachButton`, `ShowActionsButton`; Blazor mirrors these as parameters plus `MaxRows` and `SendOnEnter`. `InputBar` reads back whichever composer is in use, so `chatView.InputBar.MaxLines = 3` works without supplying one. See [The Composer](/controls/chatview/composer/)</RN>

<RN type="enhancement">**ChatView's composer is laid out as a single card in the AI-chat idiom** — the auto-growing multiline entry spans the full width on top, and every control sits on a row beneath it, so buttons no longer compete with the text for horizontal space. **`LeftToolbar` and `RightToolbar`** are the slots on that row (`IList<IView>` on MAUI, `RenderFragment` on Blazor, surfaced on `ChatView` as `InputLeftToolbar` / `InputRightToolbar`): the left slot follows the built-in attach and overflow buttons, the right sits immediately before send — enough to drop in a mode picker, a model label or a mic button and have it read like any modern prompt box. The **formatting buttons get their own row** rather than sharing the control row: six of them plus attach, overflow and a couple of custom tools does not fit beside send on a phone, and the left group scrolls sideways if it still overflows rather than pushing send off the edge. See [The Composer](/controls/chatview/composer/)</RN>

<RN type="breaking">**ChatView: Enter no longer sends on MAUI.** The composer is a multiline `Editor` now, so Enter inserts a newline and sending is the send button's job — the convention every AI composer follows. Blazor is unchanged (Enter sends, Shift+Enter inserts a newline) and can be switched with `SendOnEnter="false"`. Also gone: the hairline rule between the message list and the input bar. It was a 0.5px `BoxView` carrying negative margins meant to offset padding on a grid it was not actually inside, so it rendered wider than the bar and bled over the message area — the rounded composer outline is the edge now. `InputBarBorderColor` survives and colours that outline instead of the removed rule.</RN>

<RN type="fix">**ChatView (Blazor): newlines in a message body render as newlines.** Now that the composer is multiline, bodies genuinely arrive with `\n` in them, and the bubble was collapsing them into a single run of text. The text span is `white-space: pre-wrap` — scoped to the span rather than the bubble, since the bubble also holds inter-element whitespace that would have become blank lines. MAUI was already correct (the renderer passes raw text into `Span`s).</RN>

<RN type="feature">**Keyframe animation** — new **`Shiny.Maui.Controls.Keyframe`** package brings the CSS `@keyframes` model to XAML: `Animate.Keyframes` attaches a `Keyframes` / `Track` / `Key` tree to any `VisualElement`, with `Duration`, `Delay`, `Iterations` (including the literal `Infinite`), `Direction` (`Normal`/`Reverse`/`Alternate`/`AlternateReverse`) and `Fill` (`None`/`Forwards`/`Backwards`/`Both`) behaving the way the web spec says they do — including easing belonging to the segment that *starts* at a key, so the curve on the last key is never used. **The thing MAUI's own `Animation` class cannot do is seek**, and everything here is built around one constraint that makes it possible: `IAnimationNode.Evaluate(t)` is a **pure function of time** and never reads the previous frame. That is what makes `SeekProgress(0.35)` exact, lets `Rate = -1` reverse mid-flight from wherever the animation currently sits without rebuilding anything, and makes offscreen export byte-identical across runs. **Easing takes CSS function syntax as well as 38 named curves** — `cubic-bezier(0.34, 1.56, 0.64, 1)`, `steps(8)` and `spring(0.35, 14)` parse straight from a string, so a curve copied out of a design tool or browser devtools pastes in verbatim; springs are a closed-form solution of the spring ODE rather than a numeric integration, so they stay seekable like every other curve. **Omit `Value` on a key** and it resolves to the target's live value when playback starts, so a re-triggered animation continues from where it is instead of snapping. Colour blends in **Oklab** by default (sRGB dips through grey at the midpoint), and `Rotation` takes the **shortest arc** — 350° → 10° turns forward 20°, with a separate `Spin` property for when multiple turns are the point. The XAML property registry (`Opacity`, `Scale`/`ScaleX`/`ScaleY`, `TranslationX`/`TranslationY`, `Rotation`, `Spin`, `RotationX`/`RotationY`, `AnchorX`/`AnchorY`, `BackgroundColor`, `WidthRequest`, `HeightRequest`, `Margin`, `Padding`) is **hand-registered delegates, not reflection or compiled `Expression` trees** — both of which work in the emulator and break on device under Native AOT — and `AnimatableProperties.Register(...)` adds your own. Targets are held **weakly**, so an infinite animation on a popped page goes inert and is collected rather than pinning the visual tree. In C#, `TimelineBuilder` composes tracks fluently and `Storyboard` sequences, overlaps, and staggers whole timelines on a shared clock (and nests, since storyboards are themselves nodes). Layout-affecting properties are the perf cliff — `WidthRequest`/`HeightRequest`/`Margin`/`Padding` run a full measure+arrange every frame and are flagged by `AnimatableProperty.InvalidatesLayout`. Everything ticks in managed code on the UI thread today; native compositor offload is designed for but not implemented. **MAUI only** — the web already has `@keyframes` natively. See [Keyframe Animation](/controls/keyframe/)</RN>

<RN type="feature">**Drawn scenes** — `KeyframeScene` runs the same timing model against a **layer tree on a canvas** rather than views in the visual tree, and `KeyframeView` (a `GraphicsView`) hosts it. Layers: `GroupLayer`, `RectangleLayer`, `EllipseLayer`, `PathLayer`, `TextLayer`, `ImageLayer`, with shared `Fill`/`Stroke`/`StrokeWidth`/dash properties and full transform (`Position`, `Anchor`, `Rotation`, `Scale`, `Skew`). `LayerAnimationExtensions` adds `AnimateOpacity`, `AnimateRotation`, `AnimateSpin`, `AnimatePosition`, `AnimateScale`, `AnimateSize`, `AnimateFill`, `AnimateStroke`, `AnimateStrokeWidth`, `AnimateStrokeDashOffset`, `AnimatePath`, `AnimateCornerRadius`, `AnimateTextColor` and `AnimateVisibility` to `TimelineBuilder` so authoring a scene doesn't mean a setter lambda per track. `KeyframeView.Progress` is **two-way bindable** — bind a `Slider` to it and you have a scrubber, with the view suppressing its own feedback writes so the slider and clock don't fight; on an infinitely repeating scene there is no end to measure against, so writes are quietly ignored rather than throwing from a property-changed callback. Since scenes and views are both `IAnimationNode`s on the same clock, one storyboard can sequence both. There is **no Lottie parser** yet, though this is the scene graph one would need. See [Drawn Scenes](/controls/keyframe/scenes/)</RN>

<RN type="feature">**Offscreen export** — optional **`Shiny.Maui.Controls.Keyframe.Export`** package samples a `KeyframeScene` at exact frame times and yields frames **lazily**, so a long export never holds more than one frame in memory, plus a **pure-managed GIF encoder** (LZW + adaptive median-cut palette, no external dependency). It is a separate package because it is the only thing in Keyframe that needs a rasterizer — SkiaSharp — and it targets plain .NET rather than the MAUI platform TFMs, so it runs headless from a console app or CI. Frame times come from `index / fps` in **ticks**, never accumulated and never through `TimeSpan.FromSeconds` (which rounds to whole milliseconds and would quantise every frame at 60fps), and the closing frame is included so a one-second export at 30fps renders 31 frames ending exactly on the final pose. **Use 25 or 50fps when timing matters**: GIF stores delays in hundredths of a second, so only divisors of 100 are exact — 30fps writes 3cs and plays at 33.3fps, and most browsers promote 0–1cs delays to 10cs, so anything above 50fps plays far slower than asked. `IFrameRenderer` is an interface if you'd rather not take the Skia dependency. MP4/video is out of scope (pipe `FrameExporter.Frames()` to ffmpeg's stdin); APNG and WebP aren't implemented. See [Offscreen Export](/controls/keyframe/export/)</RN>
<RN type="fix">**Agenda (MAUI): dragging and resizing events actually works.** Both gestures were built on a `PanGestureRecognizer` nested inside the timeline's `ScrollView`, which is a combination neither mobile platform delivers. Android's scroller takes the touch away from its children the moment it crosses the touch slop — and `ScrollOrientation.Neither`, which the drag set on arming, does not help, because `MauiScrollView` only consults it in `OnTouchEvent` and never in `OnInterceptTouchEvent`. iOS is the mirror image: `UIScrollView` cancels the touches it has already handed to a child as soon as its own pan recognizer begins, and setting `Neither` there resets the scroll offset out from under the drag. On top of that the long press was being timed from the pan, which cannot work — a pan does not begin until the finger has *already* moved, so the arming window had usually been blown before the first event arrived, and the gesture was abandoned as a scroll. The press is now taken from the **raw native touch-down**, and arming disables the enclosing scroller natively for that one gesture (`ScrollEnabled` on iOS, `requestDisallowInterceptTouchEvent` on Android) instead of going through `ScrollOrientation`. Two more things were killing the drag on Android specifically: the dragged block was raised with `ZIndex`, which MAUI implements by **removing and re-adding the native child** — dispatching `ACTION_CANCEL` to the very touch doing the dragging, on its first frame — and a cross-day drag **reparented** the block into the destination day's layer, doing the same thing again at the day boundary. The block is brought to front natively now and stays in its own layer, translating across days instead. A press that arms and then never travels is treated as the slow tap it is: nothing is saved, and the event is still selected.</RN>
