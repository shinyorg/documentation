## 1.0 - TBD

<RN type="feature">**CameraView — pluggable effects.** `CameraView.Effects` is a new ordered, live collection applied to the preview, to captured photos **and to recorded video**. It takes four kinds of effect, because there are four genuinely different mechanisms and no single interface honours all of them without lying about what a platform can do: `IColorEffect` (a `ColorMatrix4x5`, honoured on every platform and surface), `INativeEffect` (a `NativeEffectDescriptor` carrying a Core Image filter name, an AGSL shader, an SVG filter and a managed CPU fallback — described as *data*, so no platform type leaks into the public API), `IDrawEffect` (composite over the frame with an `ICanvas`), and `ICaptureEffect` (slow, async, post-capture). The existing `CameraView.Filter` enum is unchanged and is now sugar over the chain: it is always applied **first**, so setting both is well-defined rather than depending on assignment order.</RN>

<RN type="feature">**CameraView — comic, sketch and other spatial looks.** `CameraEffects.Comic`, `.Sketch`, `.Posterize`, `.Pixelate` and `.Blur` join the twelve colour grades. These need to see a pixel's neighbours, so no colour matrix can express them: each ships a Core Image filter for Apple, an AGSL shader for Android 33+, an SVG filter for the browser, and a managed CPU pass used for stills wherever none of those apply — which means a photo is never silently unfiltered even where the live preview cannot run the effect.</RN>

<RN type="feature">**CameraView — `GetEffectSupport`.** Coverage genuinely differs by platform and surface: Windows has no live-preview effect hook, Android needs API 33 for spatial shaders (Blur only 31), recorded video on Android gets draw effects but not pixel effects, and WebKit is unreliable with SVG filters on video. `CameraView.GetEffectSupport(effect)` reports what will actually happen — `Full`, `ColorOnly`, `StillOnly` or `Unsupported` — so an app can grey a control out rather than offering an effect that silently does nothing.</RN>

<RN type="feature">**CameraView — effects reach recorded video on Apple.** Previously `Filter` was baked into the preview and captured stills but recorded video always got the raw feed. On iOS, Mac Catalyst and macOS the effect chain is now rendered into every encoded frame, so what the user saw is what gets saved. Recording falls back to the fast native path untouched when there are no effects and no overlay. Android composites *draw* effects into recordings; pixel effects there still do not reach the file (see Known limitations).</RN>

<RN type="feature">**CameraView — face landmarks and face masks.** `DetectedFace.Landmarks` was declared but never populated by any backend; it now carries a typed `FaceLandmarks` (eyes, nose base, mouth corners and bottom, plus derived `EyeCenter`, `EyeDistance` and `Roll`) from Apple Vision and Android MLKit, behind a new `FaceAnalyzer.DetectLandmarks` flag that is off by default because it costs meaningfully more per frame. `DetectedFace` also gains `TrackingId` where the backend tracks faces across frames. The new `FaceMaskEffect` pins an image — or your own drawing — to every tracked face, scaled from eye distance, rotated to head roll, and smoothed: the analysis pipeline deliberately drops frames while it is busy, so a raw signal visibly judders. **Breaking:** `DetectedFace.Landmarks` changed type from `IReadOnlyList<PointF>?` to `FaceLandmarks?`. Since no backend ever populated it, only code that named the type is affected.</RN>

<RN type="feature">**Camera.Ai — AI photo stylization.** `AiPhotoStylizer` (MAUI and Blazor) redraws a captured still through a Microsoft.Extensions.AI `IImageGenerator` — the "turn my selfie into a comic" flow the photo-toy apps ship. On MAUI it is an `ICaptureEffect`: drop it in `CameraView.Effects` and `CapturePhotoAsync` returns the stylized image. Provider-agnostic, prompt-driven, and deliberately *not* a live effect — a model round-trip is seconds of latency and a per-image cost. It pairs with the procedural `CameraEffects.Comic` for a live viewfinder that costs nothing. On failure it raises `Error` and returns the original photo. `IImageGenerator` is still evaluation-only in MEAI, so consuming apps need `<NoWarn>$(NoWarn);MEAI001</NoWarn>`. The `Camera.Ai` packages are no longer document-scanner-only and their descriptions have widened accordingly.</RN>

<RN type="fix">**CameraView (Apple)** — a capture session interrupted by iOS no longer stays down silently. AVFoundation suspends the session on a phone call, another app claiming the camera, a second foreground app in Split View, or system thermal/power pressure, and raises nothing to the app — the preview holds its last frame and a running recording stops receiving any, so the clip ends there while the app carries on looking healthy. The handler now observes `AVCaptureSessionWasInterrupted` / `InterruptionEnded` / `RuntimeError`, reports the interruption through `CameraView.CameraError`, and restarts the session when the interruption ends (or after a recoverable `MediaServicesWereReset`) provided `IsActive` is still `true`. Backgrounding raises the same notification on every app switch, so it is resumed but not reported as an error.</RN>

<RN type="feature">**CameraView** — `IsPinchToZoomEnabled` (MAUI, default `false`) makes a two-finger pinch on the preview drive `Zoom`. The gesture writes through the existing `Zoom` property, so it is clamped to the device's reported `MinZoom`..`MaxZoom` and anything else bound to `Zoom` (a slider, a view model) stays in step with it. No-op where the device reports no zoom range, e.g. macOS.</RN>
