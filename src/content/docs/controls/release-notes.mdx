## 1.0 - TBD

Initial Release

<RN type="feature">**Keyframe animation** — new **`Shiny.Maui.Controls.Keyframe`** package brings the CSS `@keyframes` model to XAML: `Animate.Keyframes` attaches a `Keyframes` / `Track` / `Key` tree to any `VisualElement`, with `Duration`, `Delay`, `Iterations` (including the literal `Infinite`), `Direction` (`Normal`/`Reverse`/`Alternate`/`AlternateReverse`) and `Fill` (`None`/`Forwards`/`Backwards`/`Both`) behaving the way the web spec says they do — including easing belonging to the segment that *starts* at a key, so the curve on the last key is never used. **The thing MAUI's own `Animation` class cannot do is seek**, and everything here is built around one constraint that makes it possible: `IAnimationNode.Evaluate(t)` is a **pure function of time** and never reads the previous frame. That is what makes `SeekProgress(0.35)` exact, lets `Rate = -1` reverse mid-flight from wherever the animation currently sits without rebuilding anything, and makes offscreen export byte-identical across runs. **Easing takes CSS function syntax as well as 38 named curves** — `cubic-bezier(0.34, 1.56, 0.64, 1)`, `steps(8)` and `spring(0.35, 14)` parse straight from a string, so a curve copied out of a design tool or browser devtools pastes in verbatim; springs are a closed-form solution of the spring ODE rather than a numeric integration, so they stay seekable like every other curve. **Omit `Value` on a key** and it resolves to the target's live value when playback starts, so a re-triggered animation continues from where it is instead of snapping. Colour blends in **Oklab** by default (sRGB dips through grey at the midpoint), and `Rotation` takes the **shortest arc** — 350° → 10° turns forward 20°, with a separate `Spin` property for when multiple turns are the point. The XAML property registry (`Opacity`, `Scale`/`ScaleX`/`ScaleY`, `TranslationX`/`TranslationY`, `Rotation`, `Spin`, `RotationX`/`RotationY`, `AnchorX`/`AnchorY`, `BackgroundColor`, `WidthRequest`, `HeightRequest`, `Margin`, `Padding`) is **hand-registered delegates, not reflection or compiled `Expression` trees** — both of which work in the emulator and break on device under Native AOT — and `AnimatableProperties.Register(...)` adds your own. Targets are held **weakly**, so an infinite animation on a popped page goes inert and is collected rather than pinning the visual tree. In C#, `TimelineBuilder` composes tracks fluently and `Storyboard` sequences, overlaps, and staggers whole timelines on a shared clock (and nests, since storyboards are themselves nodes). Layout-affecting properties are the perf cliff — `WidthRequest`/`HeightRequest`/`Margin`/`Padding` run a full measure+arrange every frame and are flagged by `AnimatableProperty.InvalidatesLayout`. Everything ticks in managed code on the UI thread today; native compositor offload is designed for but not implemented. **MAUI only** — the web already has `@keyframes` natively. See [Keyframe Animation](/controls/keyframe/)</RN>

<RN type="feature">**Drawn scenes** — `KeyframeScene` runs the same timing model against a **layer tree on a canvas** rather than views in the visual tree, and `KeyframeView` (a `GraphicsView`) hosts it. Layers: `GroupLayer`, `RectangleLayer`, `EllipseLayer`, `PathLayer`, `TextLayer`, `ImageLayer`, with shared `Fill`/`Stroke`/`StrokeWidth`/dash properties and full transform (`Position`, `Anchor`, `Rotation`, `Scale`, `Skew`). `LayerAnimationExtensions` adds `AnimateOpacity`, `AnimateRotation`, `AnimateSpin`, `AnimatePosition`, `AnimateScale`, `AnimateSize`, `AnimateFill`, `AnimateStroke`, `AnimateStrokeWidth`, `AnimateStrokeDashOffset`, `AnimatePath`, `AnimateCornerRadius`, `AnimateTextColor` and `AnimateVisibility` to `TimelineBuilder` so authoring a scene doesn't mean a setter lambda per track. `KeyframeView.Progress` is **two-way bindable** — bind a `Slider` to it and you have a scrubber, with the view suppressing its own feedback writes so the slider and clock don't fight; on an infinitely repeating scene there is no end to measure against, so writes are quietly ignored rather than throwing from a property-changed callback. Since scenes and views are both `IAnimationNode`s on the same clock, one storyboard can sequence both. There is **no Lottie parser** yet, though this is the scene graph one would need. See [Drawn Scenes](/controls/keyframe/scenes/)</RN>

<RN type="feature">**Offscreen export** — optional **`Shiny.Maui.Controls.Keyframe.Export`** package samples a `KeyframeScene` at exact frame times and yields frames **lazily**, so a long export never holds more than one frame in memory, plus a **pure-managed GIF encoder** (LZW + adaptive median-cut palette, no external dependency). It is a separate package because it is the only thing in Keyframe that needs a rasterizer — SkiaSharp — and it targets plain .NET rather than the MAUI platform TFMs, so it runs headless from a console app or CI. Frame times come from `index / fps` in **ticks**, never accumulated and never through `TimeSpan.FromSeconds` (which rounds to whole milliseconds and would quantise every frame at 60fps), and the closing frame is included so a one-second export at 30fps renders 31 frames ending exactly on the final pose. **Use 25 or 50fps when timing matters**: GIF stores delays in hundredths of a second, so only divisors of 100 are exact — 30fps writes 3cs and plays at 33.3fps, and most browsers promote 0–1cs delays to 10cs, so anything above 50fps plays far slower than asked. `IFrameRenderer` is an interface if you'd rather not take the Skia dependency. MP4/video is out of scope (pipe `FrameExporter.Frames()` to ffmpeg's stdin); APNG and WebP aren't implemented. See [Offscreen Export](/controls/keyframe/export/)</RN>
