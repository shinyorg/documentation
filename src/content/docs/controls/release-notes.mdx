## 1.0 - August 14, 2026

<RN type="fix" platform="Blazor">**`SheetView` content is sized to the detent that is actually on screen.** The sheet container is always viewport-tall and translated down to its detent, so everything past the detent line was being laid out below the fold — at a Half detent the bottom half of the sheet's content, including any trailing action row or `ChatView` input bar, was unreachable and unscrollable. `sheet.js` already published the on-screen height as `--sheet-visible-height`, but no rule consumed it; a new `.shiny-sheet-viewport` now sizes itself off that variable, and the variable is refreshed on every transform so it tracks a drag and not just the snapped detents. Content taller than the band scrolls inside the sheet instead of disappearing, `height: 100%` on sheet content resolves against the visible band, and a viewport resize re-derives the offset from the stored detent rather than keeping a stale pixel offset.</RN>

<RN type="fix" platform="Blazor">The sheet container now clips to its corner radius, so a full-bleed `HeaderTemplate` no longer squares off the sheet's rounded top edge.</RN>

<RN type="fix">**Kitchen Sink demo.** The sample page worked on neither host. On Blazor the `FabMenu` was left in normal flow (it lays out `inline-flex` and expects an absolutely-positioned host) so it floated mid-panel instead of sitting in the corner, and the embedded `ChatView` had a hard-coded `450px` height that overflowed the sheet. On MAUI the `FabMenu` and its pills sat flush against the screen edge with no margin, `FitContent="True"` collapsed the panel to a single non-draggable detent sized around a fixed-height `ChatView`, and `AdjustForKeyboard="False"` left the composer under the keyboard. The page now pins the FAB, lets the chat fill the sheet at whatever detent it is resting at, and drags between Half and Full on both hosts.</RN>

<RN type="feature" platform="Blazor">**One-call registration — `AddShinyControls()`.** Blazor had grown a separate `AddShiny*` per feature while MAUI needed only `UseShinyControls()`, and the asymmetry was accretion rather than design: MAUI's single call is *mandatory* (it installs handler mappers and applies the theme before any page realizes its tree), so the service registrations rode along inside it, whereas Blazor components work from the package reference alone and no umbrella call ever got created. `builder.Services.AddShinyControls()` now registers Toast, Dialogs, SplashScreen, the Walkthrough store, Docking and the On-Screen Keyboard in one go, with a configuration object shaped like MAUI's — `ConfigureDialogs`, `ConfigureKeyboard`, `SetCustomDialogs<T>` / `SetCustomToaster<T>` / `SetCustomOnScreenKeyboard<T>` / `SetCustomWalkthroughStore<T>` / `SetCustomImageDownloader<T>`, `UseHttpImageDownloader()` and `AddDockPanel<T>`. This removes a real footgun: placing `<ToastHost />` or `<DialogHost />` in a layout and forgetting the matching registration used to throw a DI resolution exception at render time. Every individual `AddShiny*` call still exists for apps minimising the WASM payload, and every registration is now `TryAdd`, so the two styles compose in either order with the first registration winning.</RN>

<RN type="fix" platform="Blazor">**Control services are scoped, not singleton.** `ToastService`, `DialogService`, `DialogOptions` and the On-Screen Keyboard's service and options were registered as singletons while `ISplashScreen`, `IWalkthroughStore` and `IImageDownloader` were scoped. Each of the singletons owns per-user UI state — the live toast list and queue, the active-dialog list and queue, the keyboard's visibility and its live options object — so under Blazor Server one user's toast, dialog or keyboard appeared on every connected user's screen. Under WebAssembly scoped and singleton are the same thing, which is why nothing surfaced it. All of them are now `Scoped`, and the options objects are built per scope rather than captured once, so mutating them at runtime stays per-user. `DockableContentRegistry` stays singleton deliberately — it is an immutable lookup over the registered panel factories with no per-user state — and that is now asserted in tests along with every other lifetime, since no WASM test can reproduce the failure.</RN>

<RN type="fix" platform="Blazor">`AddShinyImages<T>()` and `AddShinyWalkthrough<T>()` no longer emit IL2091 trim warnings; their generic parameters now carry the `DynamicallyAccessedMembers(PublicConstructors)` annotation the DI overload requires.</RN>

<RN type="feature" platform="Blazor">**On-Screen Keyboard.** A touch / kiosk soft keyboard in `Shiny.Blazor.Controls` — register with `services.AddShinyOnScreenKeyboard(...)` and place one `<OnScreenKeyboardHost />` in the root layout. US-QWERTY plus a symbols layer, momentary `⇧` and sticky `⇪` (which raises the letters without shifting the number row), auto-repeat on held keys, and caret-aware arrows that walk lines in a `<textarea>`. It auto-shows when a text input takes focus and — the part that matters — never takes the caret off it: every key cancels `pointerdown` so the browser's focus default never runs. Typing goes in via `execCommand('insertText')` so selections are replaced and undo survives, with a value splice behind it that raises both `input` and `change` so plain `@bind` and `@bind:event="oninput"` both see the keystroke. `PushContent` pads the body out from under the keys, and the focused field is scrolled clear of the keyboard in whichever container actually scrolls. Themed entirely through `--shiny-osk-*` custom properties, with `OnScreenKeyboardTheme.Auto` (the default) following the app's theme tokens. Drive it from code with `IOnScreenKeyboardService` (`Show` / `Hide` / `Toggle` / `IsVisible` / `VisibilityChanged`); register with `AddShinyControls()` or `AddShinyOnScreenKeyboard()`. The MAUI desktop half remains planned.</RN>
