## 1.0.0 TBD
<RN type="feature">New package: **Shiny.Net.HttpServer.Grpc** serves [gRPC and gRPC-Web](/httpserver/grpc/) over the same HTTP/2 stack as everything else — unary, client-streaming, server-streaming and bidirectional methods, callable from `Grpc.Net.Client`, `grpcurl` or any gRPC client in any language, and therefore from a .NET MAUI app where ASP.NET Core cannot run at all. Serialization is supplied rather than discovered: you hand `AddMarshaller` the two functions your generated code already exposes (`m => m.ToByteArray()` and `Parser.ParseFrom`), so nothing here reflects over your message types, nothing drags a serializer into your app, and the whole path stays trim- and AOT-clean — `GrpcMarshaller.Json(...)` over a source-generated `JsonTypeInfo` is there for callers speaking `application/grpc+json`. Streams are `IAsyncEnumerable&lt;T&gt;` in both directions and each message is flushed as it is yielded, so a duplex handler can read everything then answer, answer before it has read, or interleave. `GrpcStatusException` reports an outcome the caller is meant to see; anything else that escapes a handler is `Unknown` with a generic message and a full server-side log, unless `EnableDetailedErrors` says otherwise. `grpc-timeout` becomes the handler's `CancellationToken` and a `DeadlineExceeded` when it expires, per-message gzip/deflate is negotiated from `grpc-accept-encoding`, and `MaxReceiveMessageSize` is enforced on the length prefix — and on the *decompressed* size, since a few compressed kilobytes can otherwise expand into gigabytes. gRPC-Web is on by default in both framings (binary and base64 text), which is how a browser calls in and how anything stuck on HTTP/1.1 does; it has no client-streaming or bidirectional calls, so those methods answer `Unimplemented` to a web caller and work normally for everyone else. `MapGrpcService` returns a builder that fans `RequireAuthorization`/CORS/rate-limiting across every method it mapped, each `Map` call returns its own route for anything that needs to differ, and every route carries `GrpcMethodMetadata` so middleware can name the call without parsing the path. Through a tunnel, native gRPC needs one that forwards raw TCP — SSH remote forwarding to your own host qualifies; the reference relay routes by reading HTTP/1.x request heads, quick-tunnel providers terminate HTTP/1.1, and Azure Relay does both, so those three carry gRPC-Web rather than native gRPC.</RN>
<RN type="feature">Request bodies are now format-agnostic. `IInputFormatter` is the reading half of what `IOutputFormatter` has always been on the writing side: a body's formatter is chosen from its `Content-Type`, so `[FromBody]` parameters, mediator contracts and hand-written handlers all accept whatever the app registered, and none of them changed to get it. `EndpointBinder.TryReadBodyAsync&lt;T&gt;` reports a `BodyReadStatus` rather than a bool, because "no body", "unreadable body" and "body in a format I do not speak" are three different answers and only the last is a **415** — the difference between sending a caller to fix a header and sending them hunting for a syntax error that is not there. The 415 body lists the content types that would have worked. A body with no `Content-Type` at all is still read as JSON: plenty of clients omit it, this server has always treated those bodies as JSON, and answering 415 to them would break working callers to make a point about a header. `ReadJsonAsync&lt;T&gt;()` and `TryReadJsonBodyAsync&lt;T&gt;()` are unchanged, for a handler that wants JSON and only JSON. See [Serialization &amp; Formats](/httpserver/serialization/).</RN>
<RN type="feature">**XML** and **MessagePack** formatters ship in the core package, in both directions, off by default and one line each: `AddContentNegotiation(o => o.AddXml().AddMessagePack())`. Neither adds a dependency and neither needs an attribute on your DTOs — both read the same source-generated `JsonTypeInfo` the JSON path reads, so a type gets a representation on exactly the same terms and the whole path stays trim- and AOT-clean. `XmlSerializer` could not be used for the XML side at all: it builds its mapping by reflecting over the type at runtime, which is precisely what a trimmed or AOT-published app has thrown away. Reading XML is type-directed for the same reason it has to be — XML has no types, so only the target member knows whether `&lt;postalCode&gt;01234&lt;/postalCode&gt;` is a string, a number or an enum ordinal, and guessing from the text is how a postal code arrives as the number 1234. DTDs, resolvers and entity expansion are all off, so an XML endpoint cannot be talked into reading a local file, and `MaxBodyBytes` bounds the buffer with a 413. MessagePack is typically 20–40% smaller on the wire; it requires string-keyed maps, since integer keys carry no member names and binding them would be guessing, and a `byte[]` travels as base64 because that is what the shared JSON metadata does with bytes.</RN>
<RN type="feature">**Protobuf**, and any binary format with a codec you supply, through `BinaryCodecRegistry`: `o.AddProtobuf(p => p.Add&lt;Reading&gt;(m => m.ToByteArray(), Reading.Parser.ParseFrom))`. Serialization is supplied rather than discovered — the same bargain the gRPC package above strikes, and for the same reason: protobuf cannot be produced without a schema, field numbers live in the `.proto`, and the only thing that has them is the code `protoc` already generated. That is one line per message type in exchange for no new dependency and nothing reflecting over your messages. A type with no codec negotiates away to another format rather than failing at serialization time, and a request body of that type answers 415. Nothing about the registry is protobuf-specific — the same shape carries MessagePack-CSharp's native codec, CBOR or Avro under whichever media type you register it as.</RN>
<RN type="enhancement">`ContentNegotiationOptions.NegotiateByDefault` makes `Results.Ok(value)` and `new OkObjectResult(value)` — and therefore every generated endpoint returning a value — pick their representation from `Accept` instead of always writing JSON. Off by default, and the default is the point: turning it on means an endpoint's response format depends on a request header, which is what you want for an API serving browsers, scripts and API clients alike and the last thing you want for one whose contract says JSON. `Results.Json(...)` and an `ObjectResult` with an explicit `ContentType` name a format and so are never negotiated. Both spellings move together, because `Results.Ok(x)` and `new OkObjectResult(x)` are the same response written two ways and must not disagree about what they send.</RN>
<RN type="fix">A negotiated response no longer advertises `charset=utf-8` on a binary content type. `NegotiatedResult` appended it unconditionally, which was harmless while every formatter was textual and describes bytes that are not text in any encoding now that they are not. `IOutputFormatter.Charset` is a new member defaulting to `utf-8`, so existing formatters are unaffected and the binary ones return null.</RN>
<RN type="breaking">A request body whose `Content-Type` no registered formatter reads now answers **415 Unsupported Media Type** where it previously answered **400 Bad Request**. This affects generated endpoints, mediator endpoints and anything calling the new `EndpointBinder.TryReadBodyAsync&lt;T&gt;`. JSON bodies, bodies with no `Content-Type`, and malformed bodies in a format that *is* registered all still answer 400 exactly as before — so a client sending `application/json` sees no change, and one that was sending an unrecognised content type and reading the status code will.</RN>
<RN type="feature">Responses can send **trailing headers** on all three protocol versions: `Response.Trailers`, `AppendTrailer` and `DeclareTrailer`. Unlike `Response.Headers` they stay writable for the whole response and are read at completion, which makes them the only way to report something a handler could not know before it started writing — a checksum, a row count, or the status of an RPC whose failure surfaced halfway through a stream. They ride the trailer section after the terminating chunk on HTTP/1.1, a trailing `HEADERS` frame with `END_STREAM` on HTTP/2, and a second `HEADERS` frame on HTTP/3; a response that never wrote a body folds them into its one header block instead, which is the Trailers-Only shape gRPC clients expect. Note that an HTTP/1.1 response that declared a `Content-Length` cannot carry them — the body ends at its last byte and there is no chunk to attach them to — so leave the length unset when trailers matter. Scope through a tunnel: the reference relay and the SSH provider forward response bytes verbatim, so trailers survive both; Azure Relay reconstructs the response from its own HTTP model and drops them. See [Protocols](/httpserver/protocols/#trailing-headers).</RN>
<RN type="fix">A client sending **request** trailers on HTTP/2 no longer takes down the connection. A second `HEADERS` block on a live stream is trailers, not a new request, and it was hitting the new-stream path and failing the "strictly increasing stream id" check — a `GOAWAY` over a legal frame. It now ends the request body, as it should, and its header block is still decoded so the shared HPACK dynamic table stays in step; a block skipped rather than decoded would leave the decoder reading every later request against the wrong table. Late frames for a stream that has already been torn down are ignored the same way late `DATA` already was.</RN>
<RN type="feature">New package: **Shiny.Net.HttpServer.WebDav** serves a directory as an [RFC 4918](/httpserver/webdav/) WebDAV mount, compliance classes 1 and 2 — `PROPFIND`, `PROPPATCH`, `MKCOL`, `COPY`, `MOVE`, `LOCK`/`UNLOCK` and the `If` header, alongside `GET`/`PUT`/`DELETE`. The file browser next door is a JSON API you drive with `curl`; this is the protocol every desktop already has a client for, so `app.MapWebDav("/dav", o => o.RootPath = FileSystem.AppDataDirectory)` makes a MAUI app's storage a drive in Finder or Windows Explorer with no client code at all. Class 2 is on by default and is not really optional: Finder and the Windows redirector both mount a class 1 server read-only whatever `AllowWrite` says, and a `LOCK` on a URL that does not exist yet creates an empty resource for it (RFC 4918 §7.3) because that is what a Mac does when you save a new document — answer 404 there and the mount cannot be written to at all. Writes and deletes are opt-in, and `MapWebDav` returns a `WebDavMountBuilder` that fans `RequireAuthorization`/CORS/rate-limiting/IP-filtering across all twenty-two routes, with `RequireAuthorizationForChanges` counting locking as a change. `PROPFIND` with `Depth: infinity` is refused by default with the 403 and `&lt;DAV:propfind-finite-depth/&gt;` that RFC 4918 §9.1 defines, rather than walking a device's storage into one response — note that a missing `Depth` header means infinity per the specification, so it gets the same refusal. Dead properties from a `PROPPATCH` go to a pluggable `IWebDavPropertyStore`, in memory unless you replace it. The XML is read and written with `XmlReader`/`XmlWriter` with DTDs, resolvers and entity expansion all off, so the package is trim- and AOT-clean like the rest and safe against an XXE in a body that arrived from the network.</RN>
<RN type="feature">New package: **Shiny.Net.HttpServer.DocumentDb** publishes a [Shiny.DocumentDb](/httpserver/documentdb/) document type as a complete HTTP resource — list, by-id, count, create, replace, RFC 7396 merge-patch, delete, and a live Server-Sent Events tail — plus a schema-free lane for JSON collections with no CLR type. It is a port of `Shiny.DocumentDb.AspNetCore` onto this server, so a phone can serve its own database and, through a tunnel, so can anyone else reach it. The engine underneath is the same, which means filters, cursors, scopes, ETags and merge semantics are identical on both. Two things differ deliberately: `MapDocuments&lt;T&gt;` returns a `DocumentResourceBuilder` that fans `RequireAuthorization`/CORS/rate-limiting/IP-filtering across every route the resource mapped, since this server attaches metadata per route rather than per group — so adding an operation later cannot quietly leave one unprotected; and there is no reflection fallback when `TypeInfo` is unset, because a fallback that works on a desktop and throws on a trimmed phone is worse than a clear error in both places. Server-side `Scope(...)` predicates are enforced on both sides of a write and answer 404 rather than 403 for a document outside the scope.</RN>
<RN type="enhancement">`StatusCodes` gained `Status412PreconditionFailed` and `Status428PreconditionRequired`, which the conditional-write paths above needed and which any `If-Match` handler wants, plus `Status207MultiStatus`, `Status423Locked`, `Status424FailedDependency` and `Status507InsufficientStorage` for WebDAV. The reason phrases for all of them are in `GetReasonPhrase`, so a 207 goes out as `Multi-Status` rather than `Unknown` — which some clients do read.</RN>
<RN type="feature">Route constraints gained the types that were missing and a way to bound a value: `byte`, `short`, `float`, `datetime`, `dateonly`, `timeonly`, `timespan`, plus `min(n)`, `max(n)` and `range(a,b)`. The integer widths are real filters rather than synonyms for `int` — `{id:byte}` does not match `300` — and the temporal ones parse with the invariant culture so a route means the same thing wherever the server runs. `min`, `max` and `range` compare the value, where the existing `minlength`/`maxlength`/`length` count characters, and their arguments may be negative. Both the runtime matcher and the compile-time validator in the endpoint generator learned the new vocabulary together, and the parity tests that hold those two implementations in step now cover every name. Worth restating, because the new names invite the confusion: a constraint decides whether a route *matches* and never converts anything — binding a segment to the handler's type is the binder's job and already handles every `IParsable&lt;T&gt;`, so a refused segment is a 404 while one that matched but will not parse is a 400.</RN>
<RN type="feature">New package: **Shiny.Net.HttpServer.Mediator** publishes [Shiny.Mediator](/httpserver/mediator/) requests, commands and stream requests as HTTP endpoints. It is the `Shiny.Mediator.AspNet` shape — `[MediatorHttpGroup]` on the handler, `[MediatorHttpGet/Post/Put/Patch/Delete]` on `Handle` — without ASP.NET Core, so it runs inside a .NET MAUI app. The binding is the part that had to change: the ASP.NET package uses `[AsParameters]`/`[FromBody]`, which is reflection over a delegate's parameters and is annotated `RequiresDynamicCode`. Here a source generator writes the binding out member by member at compile time, so a contract that cannot be bound is a build error rather than a 500, and the whole path survives trimming. GET and DELETE bind each member from a route token or the query string; POST, PUT and PATCH read the contract from the JSON body and then apply any route token over the top, so `PUT /widgets/{id}` behaves as expected. An `ICommand` answers with a status code and no body (204 by default, configurable per endpoint); an `IStreamRequest&lt;T&gt;` becomes a Server-Sent Events response. Per-endpoint authorization, CORS, rate limiting, IP filtering and OpenAPI metadata are all declarable on the group or the endpoint. The generator ships inside the package rather than beside it, so there is no second reference to forget.</RN>
<RN type="breaking">`QuickTunnel` now defaults to `QuickTunnelHost.Pinggy` instead of `QuickTunnelHost.LocalhostRun`, because none of the previous presets could actually produce a working link unattended. localhost.run never confirms the SSH session request that carries the assigned URL — the `ssh` binary does not wait for that confirmation, SSH.NET does, and the channel types needed to work around it are internal to SSH.NET. `tuns.sh` refuses any key not enrolled at pico.sh, and the preset sent no key at all. `serveo.net` is frequently unreachable. Pinggy needs no account and reports its address in about two seconds; the new `SshTunnelOptions.UseEphemeralKey` generates the key it asks for in memory, so nothing has to be provisioned. `LocalhostRun` remains as a preset for accounts with a known custom domain, set through `PublicUrl`. Calls that named a host explicitly are unaffected.</RN>
<RN type="fix">A quick tunnel no longer reports a URL it read out of the provider's welcome banner. `UrlPattern` defaulted to the first `https://` address in the session output, and every hosted provider greets you with links to its own documentation, dashboard and social media before announcing your address — on localhost.run that greeting arrives on the channel's error stream, ahead of the address and in the same read. The tunnel would come up reporting something like `https://admin.localhost.run/`, which an app would display as the link to share. Each preset now carries a pattern anchored to its own tunnel domain, and the captured value has surrounding punctuation stripped rather than just trailing sentence marks.</RN>
<RN type="fix">`SshTunnelProvider.BindAsync` no longer stalls for the whole connect timeout when the endpoint does not answer the session request. Opening the session channel is a blocking call inside SSH.NET that waits for the server to confirm it, and it sat outside the `UrlCaptureTimeout` window that was supposed to bound the capture — so an endpoint that never confirms one (localhost.run does not) held the caller for ~30 seconds instead of 15. `UrlCaptureTimeout` now bounds the entire capture, and the warning names the cause rather than reporting a generic timeout.</RN>
<RN type="fix">A tunnel that connects without learning a public address now says so instead of inventing one. `PublicUrl` fell back to `http://{host}:{remotePort}` whenever capture failed, which is right for a forward whose public face you already know and, for a hosted tunnel, is a link to the provider's own front page — `QuickTunnel` then reported `State = Connected` against it and a UI showed it as the address to share. When `CaptureUrlFromSession` is on and nothing is captured, `PublicUrl` stays null; `QuickTunnel.StartAsync` returns null, sets `State = Failed`, and puts the reason in `LastError`.</RN>
<RN type="enhancement">Shiny.Net.HttpServer.Mcp is now trim- and AOT-clean, like every other package in the repo. The trim and AOT analyzers are enabled on it and it publishes clean under PublishAot, so an MCP server can be hosted inside a .NET MAUI app on iOS and Mac Catalyst where trimming is not optional. The package previously opted out on the grounds that the MCP SDK discovered tools by reflection; as of MCP SDK 2.0 and Microsoft.Extensions.AI 10.8 nothing in the dependency graph requires dynamic code, and the generic `WithTools&lt;T&gt;()` overload is annotated for trimming rather than excluded from it.</RN>
<RN type="enhancement">`MapMcp()` now explains what to do when a tool's parameter or return types cannot be described in a trimmed app. Building a tool's JSON schema by reflection does not survive trimming, and the underlying failure was a bare `NotSupportedException` thrown from deep inside the container. It is now an `InvalidOperationException` naming the type and showing the `JsonSerializerContext` to add, with the original exception kept as the inner. Tools whose parameters and results are only primitives are unaffected and need no context.</RN>
