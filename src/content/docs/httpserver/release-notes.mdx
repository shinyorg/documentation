## 2.1.0 - TBD

<RN type="feature">**Host a private NuGet feed.** The new [`Shiny.Net.HttpServer.NuGet`](/httpserver/nuget/) package maps the NuGet V3 server API: `app.MapNuGetFeed("/nuget", o => { o.Store = new DiskNuGetPackageStore(path); o.ApiKeys.Add(key); })`. That gives you a service index, package content, registrations, search and autocomplete, plus push, delete and relist, so `dotnet nuget push`, `dotnet restore`, `dotnet package search`, Visual Studio and Rider work against `{prefix}/v3/index.json` with nothing else to install. Version rules come from the official `NuGet.Versioning` package. The `.nuspec` is read without NuGet.Packaging, so the package stays trim and Native AOT clean. The disk store uses NuGet's own folder-feed layout, so the directory is also a plain local source. Delete unlists by default, as nuget.org does (`DeleteBehavior.Delete` removes the files), and a duplicate push gets 409 unless `AllowOverwrite` is on. API keys are compared in constant time or checked by `ValidateApiKeyAsync`, and a writable feed with no key configured fails to map. `OnBeforePushAsync` can reject a push, and `ReadOnly` serves a folder without the write routes. `.ForReads(...)` / `.ForWrites(...)` apply authorization, rate limiting or IP filtering to either half. Tested with NuGet's client libraries and the `dotnet` CLI over HTTP/1.1 and HTTP/2; HTTP/3 and tunnels have no end-to-end test yet. Not included: symbol packages, the catalog, download counts and the V2 (OData) API.</RN>

## 2.0 - September 30, 2026

<RN type="breaking">**The relay's `Authorize` hook is asynchronous.** [`RelayServerOptions.Authorize`](/httpserver/tunneling/) is now `Func<TunnelRegistrationRequest, CancellationToken, ValueTask<string?>>`, so a relay can check a registration's token against a database or an identity service instead of an in-memory copy. Wrap an existing synchronous hook as `(request, _) => ValueTask.FromResult(...)`. The new `AuthorizeTimeout` (15 seconds by default) cancels a lookup that stalls, so it cannot hold a control connection open. An exception from the hook now refuses the registration and is logged; before, it dropped the connection without a reply. `MaxTunnels` is checked again after authorization, so registrations authorizing at the same moment cannot take the relay over its limit.</RN>

<RN type="feature">**See and close the relay's tunnels.** [`RelayServer`](/httpserver/tunneling/#watching-and-closing-tunnels) raises `TunnelConnected` and `TunnelDisconnected`. The disconnect reason is `ConnectionClosed`, `Disconnected` or `RelayStopped`, and every tunnel reported connected is reported closed exactly once, including by `StopAsync` before it returns. `Tunnels` is a snapshot of each tunnel's host, public URL, client address and connection time. `DisconnectAsync(host)` closes one tunnel, and `DisconnectAsync(predicate)` closes every tunnel the predicate matches, for example every tunnel a revoked key holds. `Authorize` can tag a tunnel through `TunnelRegistrationRequest.State`, and the tag is carried as `RelayTunnel.State`. A disconnected client with a reconnect delay goes through `Authorize` again, so refuse it there first.</RN>

<RN type="enhancement">**The relay fits behind a reverse proxy.** [`RelayServerOptions.ControlAddress` and `PublicAddress`](/httpserver/tunneling/#behind-a-reverse-proxy) bind the two listeners to different interfaces. Devices can dial the control port on a public interface while the public port stays on loopback, reachable only by the proxy in front of it. Both default to `Address`, so existing configurations are unchanged. `Authorize` can now choose one tunnel's scheme by setting `TunnelRegistrationRequest.PublicScheme`, for example `http` for a host the proxy has no certificate for yet. That scheme is used in the URL handed to the client, in the new `RelayTunnel.PublicScheme`, and in the `X-Forwarded-Proto` the relay adds.</RN>

<RN type="fix">**A relay tunnel's teardown no longer unregisters the client that replaced it.** When a client reconnected and claimed its host before the old session finished closing, the old session's cleanup removed the new registration, and the new tunnel stopped receiving traffic while its client still thought it was connected. The relay also no longer keeps a host claimed when the client disconnects before receiving its registration acknowledgement.</RN>

<RN type="feature">**Real-time, two-way calls without WebSockets: Switchboard.** Two new packages, [`Shiny.Net.HttpServer.Switchboard`](/httpserver/switchboard/) and its .NET client `Shiny.Net.HttpServer.Switchboard.Client`, bring SignalR's model to the server: a class deriving from `Switchboard` (a hub) whose public methods clients call, and `Clients.All` / `Caller` / `Others` / `Line(id)` / `Group(name)` / `User(id)` to call them back. `app.MapSwitchboard<ChatBoard>("/chat")` mounts it. Each client holds one Server-Sent Events stream for everything the server sends, and every call is a plain HTTP POST, so it gets through proxies and tunnels, shares one connection on HTTP/2, and authentication, authorization, CORS, rate limiting and telemetry apply to each call as they would to any request. `IOperator<TBoard>` reaches lines from anywhere else in the app. `ILineManager.HangUpAsync` / `HangUpUserAsync` / `HangUpGroupAsync` / `Context.HangUp()` end a line and invalidate its token so it cannot come back. `OnConnectedAsync`, `OnReconnectedAsync` and `OnDisconnectedAsync(DisconnectContext)` report why a line ended: `ClientClosed`, `Dropped`, `HungUp`, `ServerShutdown` or `Faulted`. A dropped line is held for 30 seconds: a client that comes back in time keeps its line id, groups and `Items` and is replayed what it missed, or told it missed some. That includes a server stopped and restarted by a MAUI app. Methods return values, `void` or an `IAsyncEnumerable<T>` streamed item by item. Calls from one line run in the order they were made. The server can wait for one client's answer (`Clients.Caller.InvokeAsync<bool>(…)`), which also works from inside a switchboard method. `Switchboard<TClient>` calls clients through an interface, and `[SwitchboardClient<IChatBoard, IChatClient>]` generates the typed client: calls as methods, server calls as events, answers as handler properties. `[ExportContract]` writes the contract, data types and a JSON context as one self-contained C# file for clients that cannot share an assembly. Method-level `[Authorize]`, filters, metrics and spans are included. Everything is generated at compile time, and both packages are trim and Native AOT clean. It is not wire-compatible with SignalR. In-process only (no backplane), a .NET client only, and no streaming from the client to the server. Tested over HTTP/1.1, HTTP/2 and the relay tunnel. HTTP/3 and the other tunnel providers have no end-to-end test yet.</RN>

<RN type="fix">**gRPC works through the reverse proxy.** `HttpForwarder` and `MapProxy` now relay the upstream's [response trailers](/httpserver/proxy/#grpc-and-trailers): a trailing HEADERS frame to HTTP/2 and HTTP/3 callers, and the chunked trailer section, with its `Trailer` announcement, to HTTP/1.1 callers. They also forward `TE: trailers`. Before, trailers were dropped, so every proxied gRPC call ended without `grpc-status` and failed on the client.</RN>

<RN type="fix">**`HttpRequest.HasBody` is true for an HTTP/2 or HTTP/3 request that has a body but no `Content-Length`.** Both protocols allow that, since the end of the stream ends the body, and gRPC and streamed uploads always send it that way. Such a body was invisible to anything that checks `HasBody`: the reverse proxy forwarded the request without it, and typed endpoints skipped binding it.</RN>

<RN type="enhancement">**Reverse proxy metrics.** On the server's meter: [`shiny.proxy.upstream.request.duration`](/httpserver/proxy/#metrics) (seconds to the upstream's response headers, by destination, method and status) and `shiny.proxy.upstream.errors` (by `ProxyError` kind and destination). `UseForwardedHeaders` is now documented as trusting any sender and applying to HTTP/1.1 only; its behavior is unchanged.</RN>

<RN type="feature">**Sign a desktop app or CLI in through the system browser.** The new [`Shiny.Net.HttpServer.OAuthLoopback`](/httpserver/oauth-loopback/) package is the redirect receiver for the OAuth 2.0 / OpenID Connect loopback flow (RFC 8252 §7.3), the one VS Code and the GitHub CLI use: `LoopbackCallbackListener.StartAsync()` binds an ephemeral port on `127.0.0.1` and gives you the `RedirectUri` and a generated `State`, `SystemBrowser.Open` launches the default browser on Windows, macOS and Linux, and `WaitAsync()` returns the `code` (or the provider's `error`) and shows the user a "return to the app" page. It checks `state` in constant time and turns away a callback that does not match without ending the sign-in. It accepts `response_mode=form_post`, returns 404 for anything that is not the redirect path, times out, and takes a custom page or a redirect to your own hosted one. `AuthorizeAsync` does the whole round trip in one call. It is only the receiver, so PKCE and the token exchange stay with your OAuth client, and it plugs into Duende's `IBrowser`. Plain HTTP on loopback only, as RFC 8252 specifies. Desktop only: on iOS, tvOS and Android use `WebAuthenticator` with a custom scheme.</RN>

<RN type="feature">**Send 103 Early Hints while a page is still being built.** `ctx.Response.SendEarlyHintsAsync("</app.css>; rel=preload; as=style", …)` puts an interim [103 Early Hints](/httpserver/protocols/#early-hints-and-other-1xx-responses) response (RFC 8297) on the wire before the final one, so the browser starts downloading stylesheets, scripts and fonts, or opens a connection to a CDN, while the handler is still querying and rendering. `SendInformationalResponseAsync` is the general form and sends any 1xx except 101, such as `102 Processing`. Each goes out as an interim head on HTTP/1.1, and as a HEADERS frame without END_STREAM on HTTP/2 and HTTP/3. It also works through tunnels and underneath response compression. Nothing is sent to an HTTP/1.0 client, which has no interim responses, and the call returns `false`. Calling it after the response has started throws. An output-cache hit sends no hints, and the reverse proxy does not forward a 103 from a destination, because `HttpClient` discards them.</RN>

<RN type="feature">**Refuse requests addressed to names the server does not answer to.** A server bound to `0.0.0.0` on a phone or a LAN box could be reached by DNS rebinding: a page on `evil.example` re-points its own name at the device, and the browser, still calling it same-origin, reads every response. [`AddHostFiltering()` and `UseHostFiltering()`](/httpserver/host-filtering/) check the `Host` header on HTTP/1.1 and `:authority` on HTTP/2 and HTTP/3, including WebSocket upgrades, against `AllowedHosts` (exact names, `*.example.com` wildcards and IP addresses, ports ignored) and refuse anything else with a 400 problem details. With nothing configured, it admits only names a rebinding attack cannot produce: loopback names, IP literals, and requests that came through an `ITunnelProvider`. `AllowPublicUrl(() => agent.PublicUrl)` admits a cloudflared, ngrok or Tailscale hostname, read on every request, so a quick tunnel that gets a new address keeps working. When `X-Forwarded-Host` rewrites the host, both values must pass, so a forwarded header cannot slip a rebound name past it. Unlike ASP.NET Core, an empty list is not "allow everything"; add `"*"` for that. mDNS `.local` names have to be listed.</RN>

<RN type="feature">**Run each request under the culture it asks for.** [`UseRequestLocalization("en", "fr", "de")`](/httpserver/localization/) sets `CultureInfo.CurrentCulture` and `CurrentUICulture` for that request only, so `ToString("C")` and a `ResourceManager` return the right thing without the handler doing anything. The culture comes from `?culture=` / `?ui-culture=`, then a `.Shiny.Culture` cookie in ASP.NET Core's `c=…|uic=…` format, then `Accept-Language` sorted by q-value, falling back to parent cultures (`fr-CA` gets `fr`). A `CustomRequestCultureProvider` can go first. The options are shaped like ASP.NET Core's `RequestLocalizationOptions`, `ctx.GetRequestCulture()` reports what was chosen and by which provider, and `Content-Language` is optional. Two HTTP/2 or HTTP/3 streams on one connection each get their own culture, and a kept-alive connection does not carry one request's culture into the next. Under `InvariantGlobalization`, common in AOT builds, nothing throws: cultures the runtime will not create are skipped with one warning; with `PredefinedCulturesOnly=false`, negotiation works by name for resources, though formatting stays invariant.</RN>

<RN type="feature">**Receive webhooks from GitHub, Stripe, Slack and Standard Webhooks senders, verified.** `app.MapWebhook("/hooks/github", WebhookSignature.GitHub(secret), async (WebhookContext ctx) => …)` maps a [webhook receiver](/httpserver/webhooks/) that runs the handler only for deliveries the sender actually signed. It buffers the raw body up to a limit and verifies the signature over those exact bytes with a constant-time comparison. It refuses a timestamp more than five minutes off for Stripe, Slack and Standard Webhooks, and accepts any of several secrets so a key can be rotated without refusing deliveries. A delivery that fails gets a 401 problem response that does not say which check failed; the reason goes to the log. `o.SuppressDuplicates()` acknowledges a redelivery of an id already handled without running the handler again, and forgets the id when the handler fails so the retry is processed. The handler gets the verified bytes, the delivery id and the event type, and `Request.Body` still reads. `WebhookSignature.Hmac(o => …)` covers any sender that puts an HMAC of the body in one header (SHA-1/256/512, hex or base64). `[RequireWebhookSignature("github")]` with `UseWebhookVerification()` does the same for typed endpoints and existing routes, and a `WebhookContext` parameter binds the delivery. `WebhookSigner.StandardWebhooks(secret)` signs the webhooks an app sends. Works over HTTP/1.1, HTTP/2, HTTP/3 and tunnels.</RN>

<RN type="feature">**See the real client behind a TCP load balancer.** Behind HAProxy, an AWS NLB, nginx `stream`, Traefik or fly.io, every request used to come from the balancer, so the IP filter, per-IP rate limits and access logs all saw one address. An endpoint can now accept the [PROXY protocol](/httpserver/proxy-protocol/), v1 text and v2 binary on the same port: `options.Listen(IPAddress.Any, 8080).UseProxyProtocol(p => p.Trust("10.0.0.0/8"))`. The header is read before TLS and before HTTP/2 detection, so it works with TLS passthrough, and the client it names becomes `Connection.RemoteIpAddress`/`RemotePort` for HTTP/1.1, HTTP/2 and WebSockets. `Connection.ProxyProtocol` carries the rest: the balancer's address, the address the client dialled, and the v2 TLVs (ALPN, authority, TLS details, unique id, vendor TLVs). A `CRC32C` TLV is verified. `Required` closes any connection without a header, and `Optional` serves both kinds during a migration. The header is only accepted from `TrustedProxies`, and the server refuses to start with that list empty. Malformed, oversized, untrusted and late headers close the connection. TCP listeners only: HTTP/3 (QUIC) and tunnel providers do not carry it, and the reverse proxy does not send it.</RN>

<RN type="feature">**Patch a resource with a list of operations, not just a merged object.** [JSON Patch](/httpserver/json-patch/) (RFC 6902, over RFC 6901 JSON Pointer) is in the core: `JsonPatchDocument` with add, remove, replace, move, copy and test, `ApplyTo(JsonNode)` and a typed `ApplyTo(value, AppJson.Default.Note)` that goes through the type's source-generated metadata, so it is trim and AOT clean. Merge patch cannot append to an array, remove one element, move a value, set a member to `null` without deleting it, or `test` a value first. JSON Patch can, and a patch applies completely or not at all: the document you pass in is never modified. A `JsonPatchDocument` parameter on a typed endpoint binds from `application/json-patch+json`, answers anything else with 415 and `Accept-Patch`, and is described in OpenAPI with the RFC 6902 schema. Failures are problem details naming the operation that failed: 400 for a malformed patch, 409 for a failed `test` or a missing path, 422 for a result that no longer fits the type. The [DocumentDb](/httpserver/documentdb/#patch-merge-patch-or-json-patch) `PATCH` routes accept it alongside merge patch, with the same If-Match and scope checks. Works on HTTP/1.1, HTTP/2, HTTP/3 and tunnels. HTTP/3 has no end-to-end test yet.</RN>

<RN type="feature">**Uploads that survive a dropped connection.** The new [`Shiny.Net.HttpServer.Tus`](/httpserver/tus/) package speaks the tus 1.0.0 resumable-upload protocol, so a phone that loses signal 180 MB into a 200 MB video resumes from the last byte the server kept instead of starting again. `app.MapTus("/files", o => o.Store = new DiskTusStore(path))` implements core tus plus creation, creation-with-upload, creation-defer-length, termination, expiration (`Upload-Expires` and a background sweep), checksum (sha1/sha256/md5, 460 on mismatch) and concatenation, with `X-HTTP-Method-Override`. Bodies stream to the store and are never buffered. A request cut off mid-body keeps every byte it delivered, unless it carried a checksum. The disk store's offset is the file's length, so uploads resume across restarts. Only one request touches an upload at a time, and a client that comes back asks its own stalled request to let go rather than waiting out a dead socket (`LockReleaseTimeout`, or 423 immediately). `OnBeforeCreateAsync` validates metadata and `OnUploadCompleteAsync` runs once per finished file. The mount takes `.RequireAuthorization()`, CORS, rate-limit and IP-filter policies as one, `WithTusHeaders()` sets up CORS for browser clients, and tus response headers are exposed automatically. Works with tus-js-client, Uppy and TusDotNetClient over HTTP/1.1, HTTP/2, HTTP/3 and tunnels; HTTP/3 has no end-to-end test yet. Not included: `concatenation-unfinished` and GET on an upload.</RN>

<RN type="feature">**A retried POST no longer runs twice.** A phone that loses the response to a payment cannot tell "never arrived" from "arrived and the reply was lost", so it retries, and the card is charged again. [Idempotency keys](/httpserver/idempotency/) (draft-ietf-httpapi-idempotency-key-header) fix that: `builder.AddIdempotency()`, `app.UseIdempotency()`, then `.RequireIdempotencyKey()` or `.WithIdempotency()` on a route or a whole group, or `[Idempotent]` on a typed endpoint. The first request with a key runs and its response is stored. Every retry with the same key and body gets that response back, marked `Idempotent-Replayed: true`. The same key with a different body is a 422, a duplicate that arrives while the first is still running is a 409, and a missing key where one is required is a 400, all as problem details. Keys are scoped by method, path and authenticated caller. 5xx responses and handler exceptions release the key so the retry can run. Expiry, the stored status codes and the size limits are configurable, and `IIdempotencyStore` replaces the bounded in-memory default for a store shared between instances. POST and PATCH only by default. Works over HTTP/1.1, HTTP/2, HTTP/3 and tunnels. A streamed or oversized response is served but cannot be replayed.</RN>

<RN type="feature">**Uploads and downloads that are checked end to end.** TLS stops at every relay, tunnel agent and proxy in front of an embedded server. An RFC 9530 digest does not. `app.UseContentDigest()` [checks `Content-Digest` on request bodies](/httpserver/content-digest/) (sha-256 and sha-512) as they stream, without buffering. A body that does not match, is malformed, or uses only unsupported algorithms is refused with a 400 problem and a `Want-Content-Digest`, and `.RequireContentDigest()` or `[ContentDigest(RequireRequestDigest = true)]` makes the digest mandatory. Responses answer `Want-Content-Digest` and `Want-Repr-Digest`, or always carry a digest with `.WithContentDigest()`. Bodies up to 64KB get it as a header, and larger or streamed ones as a trailer. Register it ahead of compression and decompression so it covers the bytes on the wire; registered behind compression it sends no digest rather than a wrong one. Works over HTTP/1.1, HTTP/2, HTTP/3 and tunnels. On HTTP/1.1 a streamed response with a declared `Content-Length` cannot carry a trailer, so it goes without a digest.</RN>

<RN type="feature">**Serve several versions of one route side by side.** [API versioning](/httpserver/api-versioning/) takes Asp.Versioning's shape: `builder.AddApiVersioning(o => …)` with `DefaultApiVersion`, `AssumeDefaultVersionWhenUnspecified`, `ReportApiVersions` and `ApiVersionReader.Combine(new UrlSegmentApiVersionReader(), new QueryStringApiVersionReader("api-version"), new HeaderApiVersionReader("api-version"), new MediaTypeApiVersionReader("v"))`. Two endpoints on the same method and template, which the router used to refuse as duplicates, now coexist when they serve different versions, and the requested version picks one before authorization, CORS or rate limiting see it. Versions are declared with `[ApiVersion("1.0")]`, `[ApiVersion("0.9", Deprecated = true)]` and `[MapToApiVersion]` on generated endpoints, which the source generator checks at build time (SWS030, SWS031) and emits as metadata, so nothing is found by reflection. Raw routes, version sets and `MapGroup` get `.HasApiVersion(…)`, and a `{version:apiVersion}` route constraint handles `/api/v2/…`. A version the route does not serve, or two different versions in one request, is a 400 problem details with Asp.Versioning's codes. Responses carry `api-supported-versions` and `api-deprecated-versions`, and deprecation and sunset policies add `Deprecation` (RFC 9745), `Sunset` (RFC 8594) and `Link` headers. `MapOpenApi("/openapi/{documentName}.json")` serves one OpenAPI document per version, with deprecated operations flagged. Works over HTTP/1.1, HTTP/2, HTTP/3 and tunnels. HTTP/3 has no end-to-end test yet.</RN>

<RN type="feature">**Serve an app's calendars and contacts to iOS, macOS, Thunderbird and DAVx⁵.** An app with calendars or contacts of its own had no way to hand them to the apps people already use without writing a client. The new [`Shiny.Net.HttpServer.CalDav`](/httpserver/caldav/) package is a CalDAV (RFC 4791) and CardDAV (RFC 6352) server on top of the WebDAV package. `app.MapCalDav("/dav", o => { o.CalendarStore = new FileCalendarStore(dir); o.AddressBookStore = new FileAddressBookStore(dir2); }).RequireAuthorization()` supports the whole discovery flow: `/.well-known/caldav` and `/carddav` redirects (RFC 6764), `current-user-principal`, and home sets for the signed-in user, who cannot reach anyone else's URLs. It supports `MKCALENDAR` and extended `MKCOL`, name, colour and description through `PROPPATCH`, and `PUT` validated against every RFC precondition, including `no-uid-conflict` and `If-Match` / `If-None-Match: *`. Reports are `calendar-query` and `addressbook-query`, both multigets, `free-busy-query`, and `sync-collection` (RFC 6578) with sync tokens that also see changes the app makes to its own store. Time-range queries expand recurring events: daily, weekly, monthly and yearly rules with `BYDAY`, `BYMONTHDAY`, `BYMONTH`, `EXDATE` and moved instances, in the event's own time zone. Rules it cannot expand are included rather than missed. Implement `ICalendarStore` / `IAddressBookStore` to serve data you already have, such as the device calendar, using the public iCalendar/vCard parser. Works over HTTP/1.1, HTTP/2, HTTP/3 and tunnels. No locking, scheduling, `VALARM` time ranges or custom `VTIMEZONE`s.</RN>

<RN type="feature">**Real HTTPS certificates, issued and renewed by the server itself.** The new [`Shiny.Net.HttpServer.Acme`](/httpserver/acme/) package gets certificates from Let's Encrypt, ZeroSSL or any ACME (RFC 8555) CA with no certbot, cron job or reverse proxy: `builder.AddAcme(o => { o.Domains = ["example.com"]; o.Email = …; o.AcceptTermsOfService = true; })`, and every HTTPS endpoint without its own certificate serves the result. The server answers HTTP-01 on port 80 or TLS-ALPN-01 on port 443 itself. It registers the account, including External Account Binding for ZeroSSL, stores the account key and certificate owner-only so a restart never orders again, and renews at two thirds of the lifetime or when the CA's renewal information (RFC 9773) says, with jittered backoff. Each new certificate is swapped into the running server with no restart and no dropped connections, on HTTP/1.1, HTTP/2 and the HTTP/3 listener, and the intermediate is sent explicitly. Two core hooks make this work and are usable on their own: `HttpsOptions.CertificateContextSelector` (a per-handshake certificate plus chain, also on `Http3Options`) and `HttpsOptions.ChallengeResponder` (sees the ClientHello's SNI and ALPN before the handshake). It uses only the crypto built into .NET and is trim and AOT clean. It is for desktops, servers and Linux hosts with public DNS: a phone behind carrier NAT cannot be validated. There is no DNS-01, so no wildcards, and tunnels terminate TLS elsewhere so they are unaffected. For many hosts on one server, [`AcmeCertificateRegistry`](/httpserver/acme/#many-certificates-the-registry) (`builder.AddAcmeRegistry(…)` or `server.UseAcme(registry)`) holds one certificate per named entry and picks it by SNI: exact name, then a `*.` wildcard, then an optional `FallbackCertificate`, on HTTPS and HTTP/3. Entries are added, renamed and removed while the server runs with `Set` and `RemoveAsync`, and all of them share one account, store, CA client and challenge responder. `Set` never orders anything. It loads a stored certificate if there is one, the first certificate comes only from `IssueAsync` (which throws `AcmeException`) or `ImportAsync` (PEM, PFX or `X509Certificate2`, adopted into renewal), and a failed first issuance is not retried. Issued certificates renew by themselves. `Entries` reports each one's state, expiry, next renewal and last error, and `CertificateChanged` / `IssuanceFailed` fire per entry (`AcmeCertificateManager` gains `IssuanceFailed` too). Issuance outcomes (`shiny.acme.certificate.issuances`) and days until expiry (`shiny.acme.certificate.expiry`) are reported on the server's meter.</RN>

<RN type="feature">**An interactive API reference, one line from the OpenAPI document.** `app.MapScalarApiReference()` serves a [Scalar](/httpserver/openapi/#an-api-reference-page-with-scalar) reference page at `/scalar`, where you can browse every operation and its schemas and send requests. No UI is bundled with the library. The server sends a few hundred bytes of HTML, and the browser loads Scalar from its CDN, so the app ships no JavaScript and grows by nothing. With per-version documents (`o.DocumentUrl = "/openapi/{documentName}.json"`), Scalar shows a version picker with the newest version selected. Theme, layout, dark mode, the default code sample (`("csharp", "httpclient")`), the preferred security scheme and the other options use Scalar's own names. `AdditionalConfiguration` passes through any key this library does not name, all written with `Utf8JsonWriter`, so it is AOT clean and nothing configured can break out of the page. The page excludes itself from the document and takes `.RequireAuthorization()` like any route. The browser needs to reach the CDN; on an offline LAN, serve Scalar's standalone script yourself and set `ScriptUrl`.</RN>

## 1.3 - September 21, 2026

<RN type="feature">**A WebDAV mount can serve something other than one directory.** `MapWebDav` read the disk under `RootPath` directly, so an app whose storage is not one folder — several roots side by side, folders a platform only lets it reach through its own API, a photo library that is not files — could not be mounted without copying it somewhere first. `WebDavOptions.FileSystem` takes an [`IWebDavFileSystem`](/httpserver/webdav/#serving-something-that-is-not-a-directory): nine members, stat, list, read, write, make a collection, delete, move, copy and quota, and the mount keeps everything else — the protocol, locking, the hidden-file rule, `Filter` and the limits. Entries carry the segment they are addressed by and, separately, the name a client is shown. A file whose bytes are produced on demand is served with the length of the stream it hands back, not the one its listing reported. Refusals are `WebDavException` with a status, plus the `System.IO` exceptions a file system throws anyway. `RootPath` is unchanged and is now `PhysicalWebDavFileSystem`, which is public.</RN>

<RN type="fix">**A WebDAV `PUT` under a symbolic link could write outside the mount's root.** Containment followed a link only when the path being requested was one, and a new file has no link of its own to follow — so with a link inside the root pointing elsewhere, `PUT /dav/link/new.txt` passed the check and the parent-folder check, and the file landed wherever the link led. `MKCOL` and a `LOCK` on an unmapped URL did the same. Every existing segment of a path is now checked, and a path through a link that leaves the root does not resolve.</RN>

## 1.1 - September 6, 2026

<RN type="feature">**A real reverse proxy, in a package of its own — [`Shiny.Net.HttpServer.Proxy`](/httpserver/proxy/).** `MapProxy` forwarded a route to one destination and that was the whole of it. It now sits on top of a **cluster**: several destinations, five load-balancing policies (power-of-two-choices by default, plus round-robin, least-requests, random and first-available, or an `ILoadBalancingPolicy` of your own), and **two independent health checks** — a passive one that watches real traffic and takes a destination out after a run of failures, and an active one that probes on a timer. Either can quarantine a destination and neither overwrites the other's opinion, because an active probe that passes while every real request is failing should not put a broken instance back into service. **Session affinity** pins a caller to the destination it reached first, by cookie or by header, and writes a hash of the ids rather than the destination id itself — a destination id is usually an internal host name, and putting it in a cookie publishes the shape of the backend to anyone who opens dev tools. A composable **transform pipeline** rewrites paths, queries and headers in both directions, replacing the one-callback-per-route shape that `BeforeSend` and `AfterReceive` had. And the whole thing can be **read from `IConfiguration`** in a shape a YARP configuration file can be pasted into, catch-alls written `{**rest}` and all — parsed by hand rather than bound by reflection, because the reflection binder is exactly the thing that does not survive trimming, and a proxy whose configuration silently comes back empty in a published AOT build is a worse outcome than fifty lines of parsing. Routes in this server are not frozen when it starts, so a configuration change is applied to the *running* server: routes swap atomically, clusters that keep their id keep their destinations' health state, routes you mapped in code are left alone, and a file saved half-written is logged and ignored rather than allowed to tear down a working proxy.</RN>

## 1.0.3 - August 27, 2026

<RN type="fix">**A listener that died underneath a running server used to say nothing at all.** When the listening socket went away without the server being told - the OS reclaimed it, an interface was torn down mid-accept, a platform suspended the process and took the descriptor with it - `AcceptAsync` returned null and the accept loop simply returned. No log, no state change, and a server that went on reporting `Running` forever with nothing behind it. From the outside that is the worst failure available: a toggle that reads "on", a port that refuses every connection, and no way for the user to fix it by switching it off and on because it is already in the position it should be in. The accept loop now ends quietly only for a stop. Anything else is reported at error level and drives a real transition carrying [`HttpServerStateReason.ListenerFaulted`](/httpserver/hosting/#why-the-server-stopped) with the cause attached, and by default the server rebinds - `HttpServerOptions.RecoverFromListenerFaults`, on out of the box.</RN>

<RN type="fix">**An exception out of `AcceptAsync` no longer ends the accept loop.** A transient `SocketException` - a client that vanished mid-accept, descriptor exhaustion, an interface going down - escaped the loop and faulted the accept-loop task, which nothing observed until `TaskScheduler.UnobservedTaskException` surfaced it on the finalizer thread, if ever. Transient failures are now retried with a bounded backoff (`AcceptRetryAttempts`, `AcceptRetryDelay`, `AcceptRetryMaxDelay`), and the counter resets on every connection accepted, so a flaky minute costs nothing. Failures that keep coming are treated as a dead listener. The loop counts consecutive failures rather than classifying error codes: transient-versus-fatal is not decidable from a socket error across Android, iOS and desktop, and anything that has not cleared in a few attempts is fatal whatever its code said.</RN>

<RN type="fix">**The start half of `RestartAsync` retries.** The stop would succeed and the start would fail on a bind refused because the network was half up or the old port was still in `TIME_WAIT`, leaving the server stopped for good - and both in-tree callers, the network-change rebind and the MAUI lifecycle task, only logged it. A restart is the one operation where failing leaves the server worse off than not having tried, so its start half now retries with backoff (`StartRetryAttempts`, `StartRetryDelay`, `StartRetryMaxDelay`, on by default). If the retries are spent it still throws and the transition to `Stopped` carries `BindFailed` with the exception. A start the *app* asked for is deliberately never retried: `StartAsync` reports straight back to its caller, which is louder than a toggle that looks stuck for fifteen seconds.</RN>

<RN type="fix">**A rebind after a network change no longer gives up after one attempt.** It logged the failure and left the server stopped, on the theory that the next address change would try again - but on a phone that has settled onto cellular there may not be a next change, and the server was down until something unrelated happened along. It now uses the same bounded retry as any other server-initiated start, and the transitions carry `NetworkChanged` so a subscriber can tell a rebind from a shutdown.</RN>

<RN type="fix">**A `StateChanged` handler that throws can no longer take the server down.** Handlers were invoked from inside `StartCoreAsync`'s own `try`, so an exception out of a UI binding was caught by the start's `catch`, which unbound the listeners and reported a failure for a start that had already succeeded - the server went down because something drawing a button threw. Handlers now run isolated and are logged if they throw. They are also invoked one subscriber at a time rather than through the multicast delegate, which stops at the first one that throws: a broken UI binding used to silently stop the mDNS advertiser and the background-execution task from ever hearing that the server had moved.</RN>

<RN type="feature">**`HttpServer.StateTransitioned` says *why* the server changed state.** `StateChanged` reports `Stopped` whether the app asked for it or the server fell over, which is enough to draw a toggle and nothing else. The new event carries an `HttpServerStateChange` - the state, an [`HttpServerStateReason`](/httpserver/hosting/#why-the-server-stopped) (`Requested`, `Restarting`, `NetworkChanged`, `BindFailed`, `ListenerFaulted`, `Disposed`) and the `Exception` behind it when there was one. `HttpServer.LastStateChange` holds the same record for code that arrived late: a crash reporter assembling context, a diagnostics screen opened after the fact, a background task that woke to find the server down. `StateChanged` is unchanged and still raised. `Restarting` is worth handling even when nothing is wrong - it appears on the **stop** half of a restart, so a subscriber that tears down a notification or an advertisement on every `Stopped` can tell "down for a moment" from "down".</RN>

<RN type="fix">**Every start and restart the MAUI lifecycle drives is now retried, and giving up is an error rather than a warning.** A rebind on a connectivity change unbinds a listener that was working and then binds a new one, at the exact moment the interface may not be routable yet and the old port may still be in `TIME_WAIT`. One attempt that lost that race left the server stopped, the app still showing a toggle already switched on, and nothing scheduled to try again - which is what "the server shut down randomly" turns out to be nearly every time it is reported. The connectivity rebind, the Apple resume restart and the foreground start all now retry on a bounded backoff ([`RestartAttempts`, `RestartRetryDelay`, `MaxRestartRetryDelay`](/httpserver/maui/#when-the-rebind-is-refused), three attempts five seconds apart by default), and when the attempts are spent the last line is logged at `Error` with the bind exception attached. The level is the point: the `Microsoft.Extensions.Logging` bridges crash reporters ship file an event at `Error` and leave only a breadcrumb at `Warning`, so the previous `LogWarning` was a server that stopped and told nobody. This sits outside the core's own `StartRetryAttempts` and is not redundant with it - the core deliberately never retries a start the *caller* asked for, and on this path the caller is a lifecycle callback with nobody to tell. A newer connectivity change supersedes the retry still in flight, and a stop the app asked for cancels it, so a rebind cannot bring a listener up for an app that has just decided it does not want one.</RN>

<RN type="fix">**A foreground service that never started is now reported.** `StartService` posts an intent and returns; the service comes up - or is refused - on the main looper afterwards, and Android refuses it outright when the app is not entitled to one at that moment (a background start without an exemption on API 31+, a missing `FOREGROUND_SERVICE_DATA_SYNC`, a revoked notification permission). The refusal is thrown inside the service where the caller cannot see it, so the first anyone knew was the process being reclaimed minutes later with the listener inside it. [`BackgroundServerMode.KeepAlive`](/httpserver/maui/#when-the-foreground-service-does-not-start) now checks five seconds after asking and logs at `Error` when the service is not up, naming the manifest entries to look at. The reverse case is logged too: if Android stops the service while the server is still listening - the user swiped the task away, the permission was revoked - that is the moment the process stopped being held up, and it is written down rather than left to be inferred from a listener that dies minutes later. A failure to start or stop the service around a server transition also moved from `Warning` to `Error`, for the same reason: with nothing holding the process up, the listener has minutes to live.</RN>

<RN type="fix">**The mDNS advertisement no longer blinks out and back on every restart, and a refused registration is retried.** Two fixes to the same failure - an app that is running and cannot be found. The advertiser now subscribes to [`StateTransitioned`](/httpserver/discovery/#it-follows-the-reason-not-just-the-state) rather than `StateChanged`, so a `Stopped` carrying `Restarting` or `NetworkChanged` leaves the record standing instead of sending a goodbye and a fresh announcement for a service that never actually went away; peers holding a resolved address keep it. If the start half never lands, the `Stopped` that follows carries `BindFailed` and that one does withdraw. Publishing is also retried on a bounded backoff ([`PublishAttempts`, `PublishRetryDelay`, `MaxPublishRetryDelay`](/httpserver/discovery/#when-the-responder-will-not-take-the-registration)) - the moment the advertiser publishes is the moment a responder is least likely to answer, and one refusal used to be the end of it - with an `Error` carrying the exception when the attempts are spent. A server that reports `Running` with no listen URL is logged rather than silently publishing nothing, and updates are now applied in the order the server actually moved in, so a withdrawal pushed off the lifecycle thread can no longer land on top of the publication that followed it.</RN>

<RN type="feature">**`BackgroundServerMode.KeepAlive` now restarts the server on resume on iOS and Mac Catalyst.** There is no foreground service on Apple platforms, so `KeepAlive` there left the server running as the app went away - useful, because a few seconds of background execution is often exactly enough to finish the request in flight - and then did nothing more. Both are ordinary in an app whose server is a toggle. Files roll by size, the oldest are pruned, and the counter never reuses a number — a recycled one would be deleted as the oldest while it was being written to. `IW3CLogWriter` is two methods, for sending the lines somewhere other than a file.</RN>

<RN type="feature">**Metrics and traces** ([`UseTelemetry`](/httpserver/diagnostics/)) on the in-box primitives: one `Activity` per request continuing the caller's `traceparent`, and `http.server.request.duration`, `http.server.active_requests` and `http.server.active_connections` named and shaped by the OpenTelemetry HTTP semantic conventions, so a dashboard built for ASP.NET Core reads this server without being told about it. No OpenTelemetry dependency is taken — `HttpServerTelemetry.ActivitySourceName` and `.MeterName` are what an exporter subscribes to. The span is renamed to `GET /users/{id}` once routing has chosen an endpoint; a 4xx stays `Unset` because it is the caller's fault; an unrecognised method reports as `_OTHER`, since a metric attribute the caller chooses is a memory leak in the collector. `ContinueIncomingTrace` should be turned off on a tunnel, where a caller who picks the trace id can graft spans onto someone else's trace.</RN>

<RN type="feature">**Request timeouts** ([`UseRequestTimeouts`](/httpserver/timeouts/)) bound the half of the exchange your own code is responsible for — the server already bounded how long a client may take. Named policies, an inline duration, `[RequestTimeout(2000)]` / `[RequestTimeout("reports")]` / `[DisableRequestTimeout]` on generated endpoints, and `.WithRequestTimeout(...)` on a raw route. The timeout arrives as cancellation on `ctx.RequestAborted`, so a handler that ignores its token still runs to completion — it just does so after the client has been answered. A response that has already started is aborted rather than half-finished, which is what tells the client not to trust it. Exempt anything whose job is to stay open: SSE, downloads, upgrades.</RN>

<RN type="feature">**Output caching and conditional requests** ([`UseOutputCache`](/httpserver/caching/), `TryCompleteConditionalAsync`). Static files and downloads have answered `If-None-Match` since day one; a JSON endpoint now can too, and on a device the 304 saves the serialisation as well as the bytes. `CheckPreconditions` evaluates `If-Match`, `If-None-Match`, `If-Modified-Since` and `If-Unmodified-Since` in the order RFC 9110 requires, `EntityTag.FromContent(...)` makes the tag, and `SetETag`/`SetLastModified`/`SetCacheControl`/`SetNoStore` write the response side. Output caching stores GET and HEAD 200s only, never a response carrying `Set-Cookie`, never for an authenticated caller unless the policy says so, and passes a streamed response through untouched. The in-memory store is bounded — the usual host is a phone, where a cache that grows until the OS notices is the fastest way to turn a working app into a terminated one.</RN>

<RN type="feature">**Request decompression** ([`UseRequestDecompression`](/httpserver/compression/#reading-compressed-request-bodies)) reads brotli, gzip and deflate request bodies — the mirror of response compression, and on a device the more valuable direction, since uplink is the slow, expensive, battery-hungry half of a mobile connection. It has a hard limit on the decompressed size, which is the whole reason it needs a switch: the request body limit only ever bounded the compressed bytes on the wire, and a few hundred kilobytes of gzip expands to gigabytes if it was built to. An unsupported coding is refused with 415 and an `Accept-Encoding` header saying what would have worked.</RN>

<RN type="feature">**Antiforgery** ([`UseAntiforgery`](/httpserver/antiforgery/)) with signed double-submit tokens on in-box crypto. The check applies to unsafe methods when the request carries cookies and is skipped when it does not — CSRF is an attack on ambient credentials, and a caller holding a bearer token attaches it deliberately where an attacker's page cannot. `[ValidateAntiforgery]` and `[DisableAntiforgery]` override it either way. This matters here more than it looks: this server ships a file browser and a WebDAV file manager, and putting either behind cookie authentication without antiforgery is a delete button any page on the internet can press.</RN>

<RN type="feature">**Security headers and an HTTPS redirect** ([`UseSecurityHeaders`](/httpserver/antiforgery/#security-headers), `UseHttpsRedirection`). `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Cross-Origin-Resource-Policy: same-origin` by default, applied as the response starts so they cover static files and error responses, and never overriding a header a handler set for itself. CSP is opt-in because a wrong one breaks a working page; `SecurityHeaderOptions.SelfOnlyContentSecurityPolicy` is a starting point for a UI that ships with the app. HSTS is opt-in and should stay off for a LAN or loopback server — a browser remembers it for the whole host, and a phone that serves plain HTTP tomorrow is locked out of itself.</RN>

<RN type="feature">**A reverse proxy route** ([`MapProxy`](/httpserver/proxy/)) forwards a route to another server, streaming bodies in both directions with `X-Forwarded-*` describing the original caller. It belongs in an embedded server because the device is often the only thing that can reach what the caller wants: a phone bridging its own loopback service out through a tunnel, a Pi fronting a printer that speaks HTTP with no authentication, a dev server forwarding `/api` so the browser sees one origin. An unreachable upstream is a 502 and one that will not answer is a 504. Upgrades are not forwarded.</RN>

<RN type="feature">**WebSockets** gained the three things a real deployment asks for. `permessage-deflate` (RFC 7692) is negotiated when the client offers it, with no context takeover in either direction — each message compresses on its own, so a socket costs no persistent zlib window, which on a phone serving a dozen clients is the difference between a working app and the memory budget. Keepalive pings notice a peer that has gone quiet rather than closed, which is what a phone losing signal, a laptop sleeping and a NAT dropping an idle mapping all look like. And [`IWebSocketRegistry`](/httpserver/websockets/#talking-to-every-socket-at-once) is the list, the groups and the dead-socket cleanup an app would otherwise hand-roll: `BroadcastAsync`, `SendToGroupAsync`, `SendToUserAsync`, sends running concurrently so one stalled client holds up nobody, and a dead peer dropped rather than thrown.</RN>

<RN type="feature">**OAuth discovery for a remote MCP server** ([`MapMcpProtectedResource`](/httpserver/mcp/#oauth-discovery-for-a-remote-server)) publishes the RFC 9728 protected-resource document and answers a denied request with `WWW-Authenticate: Bearer resource_metadata="…"`. Without it a protected MCP endpoint is one a client can only be pointed at by hand — which is exactly the case for a server on a phone behind a tunnel, where the address is new every time. Both well-known paths are mounted, anonymously and CORS-open, because a browser-based client fetches the document before it holds any credential at all. Leave `Resource` null to derive it from the request host; set it when the server has a fixed name, since it ends up inside issued tokens.</RN>

<RN type="feature">**Agent-backed tunnels** ([`Shiny.Net.HttpServer.Tunnels`](/httpserver/tunnel-agents/)) supervise cloudflared, ngrok and Tailscale Funnel for hosts that can start a process, reporting the public URL they produce and killing the whole process tree on the way out. They are a different shape from an `ITunnelProvider` — a provider *is* a listener and needs no bound port, an agent forwards to one — which is why these are for desktop, server and the CLI, and why on a phone the answer is still the SSH provider or the relay. A missing binary throws with what to install; an agent that dies during startup fails immediately rather than waiting out the timeout.</RN>

<RN type="feature">**An in-memory test harness** ([`Shiny.Net.HttpServer.Testing`](/httpserver/testing/)): `TestHttpServer.Create(...)` and `server.CreateInMemoryClient()` give an `HttpClient` wired to the server through a pair of pipes — no port to allocate, no listener to bind, nothing left behind when a test fails half way through. Only the socket is replaced, so the request still goes through the real parser, router, middleware and response framing, and the client is `HttpClient`, so keep-alive, chunked bodies and content negotiation are all exercised as they are over TCP. HTTP/2 by prior knowledge with one flag. Use a real socket for the things that are actually about the socket — TLS, connection limits, framing.</RN>

<RN type="enhancement">The endpoint generator emits metadata for `[RequestTimeout]`, `[DisableRequestTimeout]`, `[OutputCache]`, `[NoOutputCache]`, `[ValidateAntiforgery]` and `[DisableAntiforgery]`, exactly as it already did for `[Authorize]`, `[EnableCors]`, `[EnableRateLimiting]` and `[RequireIpFilter]` — a method's attribute replaces the class's, and a `Disable` anywhere wins. So the four tiers stay level: everything a raw route can ask for with an extension method, a generated endpoint asks for with an attribute.</RN>

<RN type="enhancement">`Http3Options` now documents what HTTP/3 here cannot do: HTTP Datagrams (RFC 9297) and WebTransport both need QUIC's unreliable datagram frames, and `System.Net.Quic` exposes no API for them at all. Nothing in this library can add one without reimplementing the QUIC layer, so the endpoint speaks reliable HTTP/3 request streams and stops there. WebSockets and SSE remain the streaming answers.</RN>

<RN type="feature">A middleware can now see a request or response **body** it did not write, which is what a traffic recorder, a request logger or an audit trail needs and what nothing outside the assembly could do before. `HttpRequest.Body` is settable, so a middleware can read the body once and hand the handler a rewound copy of it - assigning also discards any `BodyReader` already handed out, so the two never disagree about where the body starts. On the way out, `IResponseBodyControl` and `HttpResponse.Bind`/`HttpResponse.BodyControl` are public, so a middleware can wrap the control the response is bound to and watch every byte on its way to the wire - the same seam [response compression](/httpserver/compression/) has always used, which means a handler writing to `Body`, to `BodyWriter` or through any of the convenience helpers is covered without knowing the wrapper exists. A wrapper must forward `StartAsync` and `CompleteAsync` to the control it wrapped, and flush whatever it buffered before the pipeline unwinds: the connection completes its own producer rather than whatever the response ended up bound to.</RN>

<RN type="feature">A browser `GET` on a WebDAV collection now serves a **file manager** rather than a bare list of links: sizes and modification times, a breadcrumb back to the mount root, drag-and-drop upload with a progress bar (a dropped folder is walked and its collections recreated), new folder, rename and delete, and a download button beside each file while the name itself still opens what it points at. Every action is one of the mount's own verbs — `PUT`, `MKCOL`, `MOVE` with `Overwrite: F`, `DELETE` — so the page offers exactly what the options allow and nothing more: a read-only mount renders the listing with no buttons at all, `AllowWrite` adds uploading and new folders, `AllowDelete` adds deleting, and renaming needs both. The page is one self-contained response with no scripts, styles or fonts fetched from anywhere, and the listing is rendered server-side, so a browser with no scripting still gets every link. `DirectoryBrowsing = false` turns the whole thing off as before.</RN>
<RN type="feature">`shinyhttpserver` now serves the directory over [WebDAV](/httpserver/webdav/), which makes the address two things at once: the [file manager](/httpserver/cli/#the-file-manager) above when a browser opens it, and a drive that Finder, Windows Explorer and the GNOME and KDE file managers can mount at the same URL. `-m` maps onto the mount unchanged — `create`, `update` and `delete` are still told apart before the handler runs, now across `MKCOL`, `COPY` and `MOVE` as well as `PUT`, with a `MOVE` judged by where it lands and renaming needing `update` **and** `delete`. `--user`, `--auth-changes-only`, `--https`, `--tunnel`, `--max-upload`, `--hidden` and `--prefix` all behave as they did.</RN>
<RN type="breaking">`shinyhttpserver` mounts WebDAV where it previously mounted the [file browser](/httpserver/file-browser/), so a `GET` on a directory answers with the file manager's HTML instead of a JSON `DirectoryListing`. A script that read those listings should ask for `PROPFIND` with `Depth: 1` instead, which answers `207` with a `DAV:multistatus` document. `GET` on a file, `PUT` and `DELETE` are unchanged, except that a `PUT` over a file that already exists now answers `204` rather than `200`, and a directory is created with `MKCOL /path` rather than `PUT /path/`. <RN type="feature">`shinyhttpserver --tunnel` opens a [pinggy.io quick tunnel](/httpserver/ssh/) and shares the public HTTPS address it hands back, so the directory is reachable from a phone that is not on this network — the banner prints it as `Tunnel`, and the QR code carries it instead of the LAN address. It is the same `QuickTunnel` the library exposes, so the tunnel feeds connections straight to `HttpServer.ServeAsync` and needs no inbound port: `--tunnel -a localhost` shares the directory publicly while binding nothing on the LAN, and because a tunnelled connection counts as encrypted transport, `-u` works over it without `--allow-insecure-auth`. Anonymous tunnels stop after 60 minutes; `--tunnel-token <token>` passes a pinggy access token and implies `--tunnel`. The tunnel is public and the traffic passes through pinggy.io, which the banner says on startup — loudly when writes are allowed with no `--user`. A tunnel that will not open is reported and the tool keeps serving on the local network. The tool now carries `Shiny.Net.HttpServer.Ssh`, and with it SSH.NET.</RN>
<RN type="feature">`shinyhttpserver` ends its startup banner with a scannable QR code of the address another device can reach, with the same URL spelled out in full underneath it — point a phone at the terminal and the [file browser](/httpserver/cli/) is on the phone. It is drawn in half-block characters, two module rows to a text row, so it fits an ordinary window, and always black on white so a dark themed terminal does not hand the reader the negative of the code. `--no-qr` leaves it out, and it is skipped anyway when the output is redirected, the window is too narrow, or the server is only listening on loopback.</RN>

Serving a directory that only the machine serving it can reach is not what the tool is for, and it is what makes the QR code worth scanning. `-a localhost` still keeps it to this machine.
