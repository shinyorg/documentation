`HttpServerOptions` is the whole surface. Defaults are chosen to be safe on a phone, not maximal on
a server.

```csharp
var builder = HttpServer.CreateBuilder();

builder.Configure(o =>
{
    o.Address = IPAddress.Any;
    o.Port = 8080;
    o.Limits.MaxRequestBodySize = 200 * 1024 * 1024;
});
```

## The single-endpoint shorthand

| Property | Default | Notes |
| --- | --- | --- |
| `Address` | `IPAddress.Loopback` | An embedded server should not be LAN-reachable unless its author says so |
| `Port` | `5000` | `0` lets the OS pick one — read it back from `ListenUrl` |
| `Https` | `null` | Plain HTTP. See [TLS & Certificates](/httpserver/tls/) |

These three describe one endpoint and are what most embedded servers want.

## Several endpoints at once

`Options.Endpoints` holds any number of address/port/TLS combinations, each bound by its own listener
and accept loop. TLS is per endpoint rather than per server because that is how it is actually used
— cleartext to the device, TLS to the network:

```csharp
builder.Configure(o =>
{
    o.Listen(IPAddress.Loopback, 5000);
    o.ListenHttps(IPAddress.Any, 5001, certificate);
});
```

<Aside type="caution">
The list takes over entirely once it has anything in it — `Address`/`Port`/`Https` are **not** folded
in. A loopback endpoint you still want has to be listed explicitly. This is deliberate: adding one
endpoint should never silently mean two.
</Aside>

`ListenUrls` reports them all and `ListenUrl` the first. A partial bind failure unwinds every
endpoint that did bind rather than leaving the server half listening, and `RestartAsync` re-reads the
list.

## Limits

`Options.Limits` exists to keep a misbehaving or hostile client from exhausting memory.

| Property | Default |
| --- | --- |
| `MaxRequestLineSize` | 8 KB |
| `MaxRequestHeadersTotalSize` | 32 KB |
| `MaxRequestHeaderCount` | 100 |
| `MaxRequestBodySize` | 30 MB (`null` removes the limit) |
| `KeepAliveTimeout` | 130 seconds |
| `RequestHeadersTimeout` | 30 seconds |
| `RequestBodyTimeout` | 30 seconds (`Timeout.InfiniteTimeSpan` turns it off) |
| `ResponseWriteTimeout` | 60 seconds (`Timeout.InfiniteTimeSpan` turns it off) |
| `MaxRequestsPerConnection` | 1000 (`null` removes the limit) |
| `InputBufferSize` | 16 KB |

`KeepAliveTimeout` and `RequestHeadersTimeout` apply to HTTP/2 connections too: the first while no
stream is open, the second while a header block is unfinished. On a cleartext connection they also
cover the moment before the protocol is known — a client that connects and sends nothing is closed
after `KeepAliveTimeout`, and one that starts the HTTP/2 preface and stalls after
`RequestHeadersTimeout`.

`RequestBodyTimeout` and `ResponseWriteTimeout` are limits on the gap between bytes, not on the
whole transfer, so a large upload or download on a slow link is fine as long as it keeps moving.
A body that stalls ends with a 408. A client that stops reading the response has its connection
aborted, and the handler's write fails as a disconnect. The leftover of a body the handler never
read gets five seconds to arrive before the connection is closed instead of reused.

Both apply to HTTP/2 as well, per stream. A stream that gets no flow-control credit for
`ResponseWriteTimeout` is reset (`CANCEL`) and its handler sees `RequestAborted`; other streams on
the connection carry on. A connection whose writes stall for that long, because the client has
stopped reading it altogether, is closed. This is what frees a stream whose client vanished
without a word: a laptop sleeping or a phone changing networks sends no reset, and nothing else
would ever end it.

The chunked trailer section of a request is held to `MaxRequestHeadersTotalSize`.

A body larger than `MaxRequestBodySize` is a 413, not a truncated read. It is the default for every
route. Keep it small and give an upload route its own limit with `WithRequestSizeLimit(bytes)`,
`DisableRequestSizeLimit()` or `[RequestSizeLimit]` — see
[Uploads & Downloads](/httpserver/files/#size-limits). HTTP/3 is always held to this value.

## Connections

| Property | Default | Notes |
| --- | --- | --- |
| `MaxConcurrentConnections` | 256 | Excess connections **wait** rather than being rejected. `null` removes the cap |
| `Backlog` | 128 | Pending-connection queue depth handed to `listen()` |
| `NoDelay` | `true` | Nagle off — request/response latency beats packet efficiency |

The connection cap is for the whole server, not per endpoint, so keep it comfortably above the number
of endpoints. A cap smaller than that leaves some of them unable to accept at all until a connection
elsewhere finishes.

## Network changes

| Property | Default | Notes |
| --- | --- | --- |
| `RebindOnNetworkChange` | `false` | Restarts the listeners when the machine's addresses change |
| `NetworkChangeDebounce` | 2 seconds | One transition raises several events; this waits for them to settle |

Off by default, because a restart drops in-flight requests and a server on a fixed machine has
nothing to gain. It is for a device that moves: a listener bound to the Wi-Fi address it had at
startup is dead the moment the phone joins another network, and the socket stays open on an address
that no longer exists without anything failing loudly.

Binding `IPAddress.Any` does not need this — that socket keeps working across an address change.
Binding a specific address does.

`HttpServer.NetworkAddressesChanged` fires either way, so a QR code or an
[mDNS advertisement](/httpserver/discovery/) can be refreshed without turning rebinding on. On a MAUI
app, [`AddHttpServerLifecycle`](/httpserver/maui/) does the same thing from Shiny's connectivity,
which is more reliable on a phone than the framework's own event.

## Resilience

| Property | Default | Notes |
| --- | --- | --- |
| `StartRetryAttempts` | 5 | Attempts at a start the **server** initiated. A start the app asked for is never retried |
| `StartRetryDelay` | 1 second | Before the first retry; doubles per attempt |
| `StartRetryMaxDelay` | 10 seconds | Ceiling for the doubling |
| `AcceptRetryAttempts` | 5 | Consecutive accept failures absorbed before the listener is declared dead. Resets on every connection accepted |
| `AcceptRetryDelay` | 100 ms | Before the first retry; doubles per consecutive failure |
| `AcceptRetryMaxDelay` | 5 seconds | Ceiling for the doubling |
| `RecoverFromListenerFaults` | `true` | Rebinds when the accept loop ends while the server believed it was running |

These are on by default, which is unusual for this library and deliberate. A server embedded in an
app has nobody watching it: the failures they cover happen on a device in someone's pocket, hours
after the last line of app code ran, and an app that has to opt in to not-silently-dying will not
have opted in.

The retried starts are the ones with nobody to throw to — the second half of a
[`RestartAsync`](/httpserver/hosting/#lifecycle), a rebind after the addresses moved, a recovery from
a dead listener. `StartAsync` is left alone on purpose: its caller is usually a toggle, it gets the
exception, and retrying behind it only makes the button appear stuck. Set `StartRetryAttempts = 1` to
have the first failure be the last everywhere.

The accept loop counts consecutive failures rather than classifying them. Deciding
transient-versus-fatal from a socket error code is a losing game across the platforms this runs on —
descriptor exhaustion, an interface torn down mid-accept and a client that vanished all report
differently on Android, iOS and desktop, and the list moves with the OS. Time is the honest
classifier: what clears within a few attempts was transient, and what does not is fatal whatever its
code claimed.

Nothing here is silent. Every retry logs a warning, every give-up logs an error, and the state
transition carries the reason and the exception — see
[why the server stopped](/httpserver/hosting/#why-the-server-stopped).

## Response headers

| Property | Default | Notes |
| --- | --- | --- |
| `ServerHeader` | `"Shiny"` | `null` omits the header entirely |
| `IncludeDateHeader` | `true` | RFC 9110 asks origin servers to send `Date` |

## Forwarded headers

```csharp
o.UseForwardedHeaders = true;
```

With this on, `Request.Scheme`, `Request.Host` and the client IP come from `X-Forwarded-Proto` /
`X-Forwarded-Host` / `X-Forwarded-For`, **read from the right**.

Every proxy *appends* the address it received the request from, so the header reads from whatever the
client claimed on the left to the hop nearest this server on the right. Only the right-hand end was
written by someone you trust; the left-most entry is the one never to believe. The server takes one
entry per trusted hop from the right, up to `ForwardLimit`, and takes the scheme and host from the same
hop:

```csharp
o.UseForwardedHeaders = true;
o.ForwardedHeaders.KnownNetworks.Add(IpAddressRange.Parse("10.0.0.0/8"));   // your load balancers
o.ForwardedHeaders.KnownProxies.Add(IPAddress.Parse("192.0.2.10"));
o.ForwardedHeaders.ForwardLimit = 2;                                        // CDN → balancer → here
```

| `ForwardedHeaders` property | Default | Notes |
| --- | --- | --- |
| `KnownProxies` | empty | Peers whose headers are believed |
| `KnownNetworks` | empty | Networks whose headers are believed |
| `ForwardLimit` | 1 | Entries consumed from the right; `null` removes the limit |

The headers are only read when the connecting peer is a known proxy, and the walk stops at the first
address that is not one — so with `ForwardLimit = 2`, `X-Forwarded-For: 6.6.6.6, 198.51.100.7, 10.0.0.5`
from a balancer resolves to `198.51.100.7`, never the `6.6.6.6` the client wrote.

<Aside type="danger" title="With no proxies listed, it trusts every peer">
Until `KnownProxies` or `KnownNetworks` is set, the headers are believed from whichever peer sent them,
so a client that can reach the server directly can claim any address, scheme or host it likes, getting
past an [IP filter](/httpserver/ip-filtering/), per-IP [rate limits](/httpserver/rate-limiting/),
[host filtering](/httpserver/host-filtering/) and HTTPS-only checks. List your proxies, or only enable it
when **every** connection arrives through a proxy or tunnel you control. **Never on an edge server
facing the internet** without a list. Behind a TCP load balancer, the
[PROXY protocol](/httpserver/proxy-protocol/) with its `TrustedProxies` list is the safer choice.
</Aside>

<Aside type="caution" title="Changed behaviour">
Earlier versions took the **left-most** `X-Forwarded-For`, `-Proto` and `-Host` entries — whatever the
client sent — so a caller behind an ordinary appending proxy could choose its own address. A chain of
several proxies now needs `ForwardLimit` raised (and the inner proxies listed) to reach the original
client.
</Aside>

<Aside type="caution" title="HTTP/1.1 only">
Only HTTP/1.1 requests are rewritten. Requests arriving over HTTP/2 or HTTP/3 keep the transport's
scheme, host and address whatever this says. Behind a proxy that speaks h2 to this server, read the
headers yourself, and decide who to trust, in a middleware.
</Aside>

`ctx.GetClientIpAddress(useForwardedHeaders: true)` reads the header for a single call site — the
**right-most** entry (the address the nearest proxy saw), stripping an optional port — without a trust
list. For a chain of proxies configure `ForwardedHeaders` and read `Connection.RemoteIpAddress` instead.

Behind a TCP load balancer (HAProxy, AWS NLB, nginx `stream`, Traefik, fly.io), prefer the
[PROXY protocol](/httpserver/proxy-protocol/). It is read per endpoint, only from peers you list, and
it works when the balancer passes TLS straight through.

## Exception detail

```csharp
o.HideExceptionDetails = false;   // development only
```

On by default: an unhandled handler exception produces a 500 with no detail. Turning it off returns
the exception text instead, which is a development convenience and a production disclosure. For
anything structured, use [Errors & Problem Details](/httpserver/errors/) — `IncludeExceptionDetails`
there does the same job for RFC 9457 bodies.

## HTTP/2

`Options.Http2` configures the HTTP/2 stack; see [Protocols](/httpserver/protocols/) for what is
negotiated and how. The short version is that `Enabled` is on by default and costs nothing, because
the protocol is still chosen per connection: ALPN over TLS, the connection preface over cleartext,
and HTTP/1.1 for anything else.
