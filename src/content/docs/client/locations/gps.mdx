:::note[Packages]
GPS, motion activity and geocoding ship in **`Shiny.Gps`**; geofencing ships in **`Shiny.Geofencing`**. The two are
independent, so install only what you use. **`Shiny.Locations`** is now a meta-package with no code of its own that
references both, so existing apps keep working by updating the version. Every type kept the `Shiny.Locations`
namespace, and `Position`/`Distance` moved into `Shiny.Core`.
:::

Shiny makes realtime background location updates easy on MAUI. `Shiny.Gps` also runs on macOS (AppKit) and in
Blazor WebAssembly, and **`Shiny.Gps.Linux`** adds Linux through GeoClue2 - all behind the same `IGpsManager`.

:::note
While Shiny is built to support background operations, GPS can work in strictly a foreground perspective by simply registering
```csharp
services.AddGps();
```
without any GPS delegate.
:::

## Platform Notes

| Feature | iOS / Mac Catalyst | Android | macOS | Windows | Linux | Blazor (Web) |
|---------|-----|---------|-------|---------|-------|--------------|
| Foreground GPS | Full | Full | Full | Full | Full (GeoClue2) | Full |
| Background GPS | Full | Full (foreground service) | Full (the app isn't suspended) | Not Supported | Full (the process isn't suspended) | Not Supported |
| Geofencing | Full | Full | Not Supported | Full | Not Supported | Not Supported |

:::caution
Windows only supports foreground GPS. Background location tracking is not available on Windows.
:::

:::caution[Blazor / Web]
The browser does not expose a true background API for location, and there is no
geofencing API at all. On Blazor, `Shiny.Gps` wraps `navigator.geolocation` and
only delivers readings while the page/tab is alive and focused. `IGpsDelegate` will
be invoked, but only while the app is running in the foreground — registering a
delegate does **not** keep the app alive in the background. If you set
`GpsBackgroundMode.Standard` or `Realtime` on a Blazor request, it will be silently
treated as foreground and a warning will be logged. There is no `IGeofenceManager`
implementation on Blazor.
:::

:::caution[iOS — ask for background access from the thing that needs it]
iOS authorization escalates: *when in use* first, *always* only as an upgrade, and the
system presents that upgrade prompt **once**. So call `RequestAccess` with the
background request from the feature that actually needs background location — the
switch the user just moved — rather than at launch. That is also the only moment you
can explain why the dialog is there.

Before 7.0.0 a background `RequestAccess` with *when in use* already granted returned
`AccessState.Restricted` without showing the upgrade prompt: on iOS 18+ the `CLServiceSession`
it relied on never asks for the upgrade, and below 18 the upgrade was never requested. If your
"always" prompt never appears, upgrading is the fix.

The app gets no signal while the upgrade prompt is up, and "Keep Only While Using" changes
nothing, so the first background `RequestAccess` waits up to 30 seconds for the answer. Later
calls don't wait, because iOS won't show that prompt again until location is reset in Settings.

Note that `AccessState.Restricted` is what *when in use* reports as when a background
request asks about it — it means "granted, but not for what you asked for", not
"blocked". Treat it as a prompt-able state, not a dead end.
:::

## Setup
<LibBuilder componentName="gps" client:load />

`AddGps()` and `AddGps<TDelegate>()` have the same signature on every target, so a shared library built against
`net11.0` can call them and bind on every platform. The platform switches are separate overloads, so guard them:

```csharp
#if IOS || MACCATALYST
services.AddGps<MyGpsDelegate>(forceUseOldCLManager: true); // CLLocationManager instead of CLLocationUpdater on 18+
#elif ANDROID
services.AddGps<MyGpsDelegate>(forceLocationApi: true);     // platform LocationManager instead of Play Services
#else
services.AddGps<MyGpsDelegate>();
#endif
```

### macOS Setup

`Shiny.Gps` has a `net11.0-macos` target for AppKit apps. Register it with the same `AddGps()` / `AddGps<TDelegate>()`,
and add the usage description to `Info.plist`:

```xml
<key>NSLocationUsageDescription</key>
<string>Say why your app uses location</string>
<key>NSLocationWhenInUseUsageDescription</key>
<string>Say why your app uses location</string>
```

A sandboxed app also needs the `com.apple.security.personal-information.location` entitlement.

macOS runs on `CLLocationManager` and differs from iOS in a few ways:

- **No background modes to configure.** A Mac app isn't suspended, so there is nothing to turn on. `GpsBackgroundMode.Standard`
  uses significant location changes and `Realtime` uses continuous updates, as on iOS. `AppleGpsRequest`'s
  `PausesLocationUpdatesAutomatically`, `ActivityType` and background indicator have no effect.
- **No when-in-use level.** A grant on macOS is always *always*, so there is no upgrade prompt and a background request
  never reports `Restricted`.
- **No motion activity.** `AddMotionActivity()` is a no-op, since macOS has no `CMMotionActivityManager`.
- **No geofencing.** `Shiny.Geofencing` has no macOS target.
- `AddGeocoding()` uses the Apple geocoder, as on iOS. See [Reverse Geocoding](/client/locations/geocoding).

### Linux Setup

Install **`Shiny.Gps.Linux`** next to `Shiny.Gps` and call `AddLinuxGps()`. It talks to
[GeoClue2](https://gitlab.freedesktop.org/geoclue/geoclue/-/wikis/home), the freedesktop location service on the D-Bus system
bus, which is installed by default on GNOME, KDE and most desktop distributions. GeoClue finds the machine from Wi-Fi, the IP
address, a GPS receiver or a modem. It ships as its own package so the D-Bus dependency never reaches a WebAssembly app.

```csharp
services.AddGps<MyGpsDelegate>();          // every other platform
services.AddLinuxGps<MyGpsDelegate>(o =>   // Linux - does nothing on other operating systems
{
    // the name of your app's .desktop file without the extension - GeoClue refuses a client without one
    o.DesktopId = "com.mycompany.myapp";
});
```

`AddLinuxGps` does nothing on other operating systems, so it can sit in shared startup code. It replaces any `IGpsManager`
registered before it, so call it after `AddGps`.

| `LinuxGpsOptions` | Default | |
|---|---|---|
| `DesktopId` | Entry assembly name | The `.desktop` file name GeoClue's agent shows and remembers its answer by |
| `AccuracyLevel` | `Street` | GeoClue accuracy level when `RequestPreciseAccuracy` is false. Street is Wi-Fi positioning; `City`/`Country` are IP guesses |
| `PreciseAccuracyLevel` | `Exact` | Level when `RequestPreciseAccuracy` is true (GPS receiver or modem) |
| `DistanceThresholdMeters` | `0` | Metres moved before GeoClue sends a new location (0 = every change) |
| `TimeThresholdSeconds` | `0` | Minimum seconds between locations (0 = every change) |
| `StationaryMetersThreshold` / `StationarySecondsThreshold` | `10` / `30` | Drive `GpsReading.IsStationary` |

How Linux differs:

- **GeoClue has no permission prompt of its own.** Its agent (GNOME's location privacy setting or the location portal)
  decides whether a client may start. `RequestAccess` starts a client to find out. `GetCurrentStatus` returns what has been
  learned so far: `Unknown` until a request has been made, `Denied` when the agent or the location switch refused, and
  `NotSupported` when GeoClue or the system bus is missing. Call `RequestAccess` before starting a listener.
- **Background modes all listen continuously.** A desktop process isn't suspended, so `Standard` and `Realtime` behave like
  `None`. A background listener is still saved and restarted at startup when `AutoRestart` is set, as on every other platform.
- **Readings arrive on the D-Bus thread**, both through `GpsReadingReceived` and the `IGpsDelegate`s, so switch to the UI thread
  before you touch UI.
- Unknown altitude is reported as `0`, and unknown speed and heading as `-1`.
- No motion activity or geofencing. `AddGeocoding()` uses OpenStreetMap Nominatim.

### Blazor WebAssembly Setup

Install `Shiny.Gps` and register it in your `Program.cs` - on WebAssembly `AddGps()` uses the browser Geolocation API:

```csharp
using Shiny;

var builder = WebAssemblyHostBuilder.CreateDefault(args);
// ...
builder.Services.AddGps();
// or with a (foreground-only) delegate:
builder.Services.AddGps<MyGpsDelegate>();
```

Then inject `IGpsManager` into your component just like on MAUI:

```razor
@inject IGpsManager GpsService

@code {
    protected override async Task OnInitializedAsync()
    {
        var status = await GpsService.RequestAccess(GpsRequest.Foreground);
        if (status == AccessState.Available)
            await GpsService.StartListener(GpsRequest.Foreground);
    }
}
```

The first call to `RequestAccess` will trigger the browser's permission prompt.
A working sample lives at [`samples/Sample.Blazor/Pages/Gps.razor`](https://github.com/shinyorg/shiny/blob/main/samples/Sample.Blazor/Pages/Gps.razor).

## Starting/Stopping the GPS Service

```csharp
IGpsManager gpsManager; // injected, resolved, etc
var request = GpsRequest.Background; // or GpsRequest.Foreground, GpsRequest.Realtime(true)

var access = await gpsManager.RequestAccess(request);
if (access == AccessState.Available)
    await gpsManager.StartListener(request);

await gpsManager.StopListener();
```

`StartListener` throws if a listener is already running. Check `gpsManager.CurrentListener == null` (or the `IsListening()` extension) first.

### Surviving a process restart

A listener started with `GpsBackgroundMode.Standard` or `Realtime` is saved to Shiny's settings store. When the OS ends the process and the app starts again, Shiny restarts that listener at startup if the request has `AutoRestart` set (the default), and `CurrentListener` returns it again. `StopListener()` clears it. Foreground-only listeners (`GpsBackgroundMode.None`) are not saved, so they end with the process. If the restart fails, for example because Android won't allow a `Realtime` foreground service to start from the background, the saved listener is cleared and a warning is logged.


## Observing in the background

First, create the delegate that implements IGpsDelegate

```csharp
public partial class MyGpsDelegate : Shiny.Locations.IGpsDelegate
{
    public MyGpsDelegate()
    {
        // like all other shiny delegates, dependency injection works here
        // treat this as a singleton
    }


    public Task OnReading(GpsReading reading)
    {
        // do something with the reading
        return Task.CompletedTask;
    }
}
```

`IGpsDelegate`s receive every reading in every background mode (`None`, `Standard` and `Realtime`) on every platform, Android included.

:::note
Pay attention to the partial on the delegate above. If you want some more control on the Android side of things, the partial will be needed for the additional
setup below  
:::

### Controlling GPS Notification on Android

```csharp
#if ANDROID
public partial class MyGpsDelegate : Shiny.IAndroidForegroundServiceDelegate
{
    public void Configure(AndroidX.Core.App.NotificationCompat.Builder builder)
    {
        builder
            .SetContentTitle("MyApp")
            .SetContentText("My App is following you!!")
            .SetSmallIcon(Resource.Mipmap.youricon);
    }
}
#endif
```

Next, let's register that with your app builder/hosting/service collection

```csharp
services.AddGps<MyGpsDelegate>();
```

Lastly, start it up with a background request. On Android, `Realtime` runs the foreground service whose notification you configured above.
```csharp
IGpsManager gpsManager; // injected, resolved, etc
var request = GpsRequest.Realtime(true);

var access = await gpsManager.RequestAccess(request);
if (access == AccessState.Available)
    await gpsManager.StartListener(request);
```

## Stationary Detection

All GPS providers automatically detect when the user is stationary and set `GpsReading.IsStationary` on each reading before it reaches your delegate or the `GpsReadingReceived` event.

- **iOS 18+** uses native `CLLocationUpdater` stationary detection provided by the OS.
- **iOS legacy**, **macOS**, **Android** and **Linux** use a distance + time threshold algorithm: if the user moves less than a configurable number of meters within a configurable number of seconds, they are marked stationary.

The default thresholds are 10 meters and 30 seconds. You can configure these via the platform-specific request types:

```csharp
#if ANDROID
var request = new AndroidGpsRequest(
    BackgroundMode: GpsBackgroundMode.Realtime,
    StationaryMetersThreshold: 15,
    StationarySecondsThreshold: 60
);
#elif IOS
var request = new AppleGpsRequest(
    BackgroundMode: GpsBackgroundMode.Realtime,
    StationaryMetersThreshold: 15,
    StationarySecondsThreshold: 60
);
#endif
```

Then check the reading in your delegate or via the foreground `GpsReadingReceived` event:

```csharp
gpsManager.GpsReadingReceived += (sender, reading) =>
{
    if (reading.IsStationary)
    {
        // user is stationary
    }
};
```

Rx has been removed from `Shiny.Locations` — `GpsReadingReceived` is a plain C# `event EventHandler<GpsReading>`. Remember to `-=` your handler on disappear/dispose.

## Easier Delegate

The platform mechanics don't always play by the rules for time & distance filters that you may expect especially with a more 'real time' setup.  
To work around these issues, you can use the `GpsDelegate` class which will handle the filtering for you.

### Minimum Filters (AND)

When both `MinimumDistance` and `MinimumTime` are set, **both** conditions must be met before `OnGpsReading` fires. If only one is set, that single condition is used.

```csharp
public class MyGpsDelegate : GpsDelegate
{
    public MyGpsDelegate(ILogger<MyGpsDelegate> logger) : base(logger) 
    { 
        // BOTH of these must be satisfied for OnGpsReading to fire
        this.MinimumDistance = Distance.FromMeters(200);
        this.MinimumTime = TimeSpan.FromMinutes(1);
    }

    
    protected override Task OnGpsReading(GpsReading reading)
    {
        // do something with the filtered reading
        return Task.CompletedTask;
    }
}
```

### Maximum Filters (OR, overrides minimums)

`MaximumDistance` and `MaximumTime` act as safety nets. If **either** maximum threshold is crossed, `OnGpsReading` fires immediately regardless of whether the minimum conditions are met. This ensures readings are never suppressed for too long.

```csharp
public class MyGpsDelegate : GpsDelegate
{
    public MyGpsDelegate(ILogger<MyGpsDelegate> logger) : base(logger) 
    { 
        // Both minimums must be met (AND)
        this.MinimumDistance = Distance.FromMeters(200);
        this.MinimumTime = TimeSpan.FromMinutes(1);

        // Either maximum crossed will always fire (OR), overriding minimums
        this.MaximumDistance = Distance.FromKilometers(2);
        this.MaximumTime = TimeSpan.FromMinutes(10);
    }

    
    protected override Task OnGpsReading(GpsReading reading)
    {
        // do something with the filtered reading
        return Task.CompletedTask;
    }
}
```
