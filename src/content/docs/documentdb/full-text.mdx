---
title: Full-Text Search
---

Full-text search finds documents by **relevance**, not exact substring — tokenized, ranked matching over one or more string properties. The library exposes a single `FullTextSearch` API that runs on each provider's native full-text engine: **FTS5** on SQLite, a generated **`tsvector` + GIN** index on PostgreSQL, a **`FULLTEXT`** index on MySQL, **Oracle Text** (`CTXSYS.CONTEXT`), a **Full-Text Index** on SQL Server, the **`fts`** extension on DuckDB, **full-text search** on Cosmos DB, and a **`$text`** index on MongoDB. LiteDB and IndexedDB have no native engine, so they fall back to an in-memory **TF-IDF** scan — the API works everywhere.

The shape mirrors vector search: register the searchable property/properties with `cfg.MapFullTextProperty(...)`, then query with `store.FullTextSearch<T>("some text")`. Results come back ordered by relevance descending, each with a `Score`.

## Declaring a full-text property

Full-text is **declarative and up-front**: the index is created for you when the store initializes the type, so a type **must be mapped before it can be searched** — there is no ad-hoc full-text over an arbitrary property (unlike `.Where(x => x.Body.Contains(...))`, which works on any field). This is what lets the library create the underlying FTS index, generated/computed column, or `$text` index on your behalf — you never write the DDL.

```csharp
services.AddDocumentStore(opts =>
{
    opts.DatabaseProvider = new SqliteDatabaseProvider("Data Source=app.db");

    // single property
    opts.ConfigureDocument<Article>(cfg => cfg.MapFullTextProperty(a => a.Body));

    // …or several fields combined into one index
    opts.ConfigureDocument<Article>(cfg => cfg.MapFullTextProperty([a => a.Title, a => a.Body]));
});
```

It indexes the **text value extracted at the property's JSON path**, not the raw JSON document. For a collection of strings or a custom projection, use the AOT-safe overload:

```csharp
opts.ConfigureDocument<Article>(cfg => cfg.MapFullTextProperty(
    propertyNames: ["tags"],
    textSelector: a => a.Tags,                 // IEnumerable<string>
    language: FullTextLanguage.English));
```

The `textSelector` is compiled code, so only the in-memory fallback runs it. The relational providers index the **whole value** at each named path, which for a collection of objects means every field of every element. To index one field of each element, use `MapFullTextCollection` (below).

### Indexing one field of each collection element

`MapFullTextCollection` indexes a single string property of every element in a collection, and nothing else from the elements. For a day's schedule, that means searching programme titles without matching their descriptions:

```csharp
opts.ConfigureDocument<Schedule>(cfg => cfg.MapFullTextCollection(
    x => x.Programmes,      // the collection
    p => p.Title));         // the field of each element to index
```

The database extracts the values itself (`json_each` on SQLite, `jsonb_path_query_array` on PostgreSQL, a `[*]` wildcard path on MySQL, MariaDB, Oracle and DuckDB), so the index stays engine-maintained.

| Provider | `MapFullTextCollection` |
|---|---|
| SQLite, PostgreSQL, MySQL, MariaDB, Oracle, DuckDB | ✅ |
| SQL Server, CockroachDB | ❌ throws `NotSupportedException` at table init |

### Substring search with the trigram tokenizer

The default tokenizer indexes whole words, so `"spo"` doesn't find `"Sportsnet"`. For an as-you-type search box, pass `tokenizer: FullTextTokenizer.Trigram`:

```csharp
opts.ConfigureDocument<Channel>(cfg => cfg.MapFullTextProperty(
    x => x.Name,
    tokenizer: FullTextTokenizer.Trigram));

await store.FullTextSearch<Channel>("spo");       // finds "Sportsnet One"
await store.FullTextSearch<Channel>("bbc one");   // both terms must appear
```

- Matching is **case-insensitive** and finds a term **anywhere** in the text.
- The search's whitespace-separated terms are **ANDed** (a word index ORs them).
- Terms shorter than **three characters** are ignored, because a trigram index can't look them up. A search made only of such terms returns nothing.
- `LuceneMatch` / `LuceneScore` work over a trigram index too.

| Provider | Trigram engine |
|---|---|
| **SQLite** | FTS5 `tokenize='trigram'` |
| **PostgreSQL** | `pg_trgm` GIN index (`gin_trgm_ops`) serving `ILIKE`, ranked by `word_similarity`. The store runs `CREATE EXTENSION IF NOT EXISTS pg_trgm`, which needs the privilege to create extensions. |
| **CockroachDB** | built-in trigram index, ranked by `similarity` |
| Everything else | ❌ throws `NotSupportedException` at table init |

### Changing a mapping

The index is built when the store first initializes a table. If you later change a type's full-text mapping (other properties, a collection element, the tokenizer or the language), the next startup **rebuilds that type's index from the stored documents**. It doesn't keep serving the old text. Each relational provider records the definition it indexed: SQLite in a `{table}_fts_meta` table, and the others on the index's backing column (a column comment, or an extended property on SQL Server). An unchanged mapping costs one catalog lookup at startup.

An index built by 14.3 or earlier has no recorded definition, so **it is rebuilt once on the first startup after upgrading**. On PostgreSQL and MySQL, rebuilding a generated column rewrites the table, so allow for that on large tables. DuckDB rebuilds its snapshot index before every query anyway.

Mapping a type onto a table that already holds documents of that type indexes them as well.

### FullTextLanguage

Controls stemming / stop-words where the backend supports it (PostgreSQL `regconfig`, Oracle lexer, DuckDB stemmer, the in-memory fallback). Backends without per-language support ignore everything but the distinction between `Simple` (no stemming) and a stemmed language.

```csharp
public enum FullTextLanguage
{
    Simple, English, Spanish, French, German, Italian, Portuguese, Dutch, Russian
}
```

## Searching

`FullTextSearch` is a terminal operation that returns up to `maxResults` documents ordered by relevance descending. Terms are OR-combined (a document matches if it contains any term); the exact operator grammar is provider-specific.

```csharp
var hits = await store.FullTextSearch<Article>("orleans persistence", maxResults: 20);

foreach (var hit in hits)
    Console.WriteLine($"{hit.Score:F3}  {hit.Document.Title}");
```

### FullTextResult

```csharp
public class FullTextResult<T> where T : class
{
    public required T Document { get; init; }
    public double Score { get; init; }   // higher = more relevant
}
```

`Score` is normalized so **higher always means a better match**, but its absolute scale is provider-specific (BM25 on SQLite/DuckDB, `ts_rank` on PostgreSQL, `MATCH … AGAINST` on MySQL, `textScore` on MongoDB, the in-memory TF-IDF score, and a positional score on Cosmos, whose `FullTextScore` cannot be projected). **Compare scores only within one result set**, never across providers.

### Pre-filtering

Pass a predicate to narrow results alongside the full-text match — for tenant or category scoping. It is pushed into the query where the provider supports it.

```csharp
var techHits = await store.FullTextSearch<Article>(
    "orleans",
    filter: a => a.Category == "tech");
```

### Fluent form

`FullTextMatch` on the query builder bridges to the same engine and folds the query's current `Where` predicates into the pre-filter. `OrderBy`, `GroupBy`, and `Paginate` are ignored — `maxResults` controls the count and results come back ranked.

```csharp
var hits = await store.Query<Article>()
    .Where(a => a.Category == "tech")
    .FullTextMatch("orleans", maxResults: 10);
```

## Composable queries with Lucene syntax

`FullTextSearch`/`FullTextMatch` are *terminal* ranked calls. When you instead want full-text as a **composable predicate** — AND/OR'd with ordinary filters, paged, and sorted alongside everything else — use `DocumentFunctions.LuceneMatch(field, luceneQuery)` in a `Where` and `DocumentFunctions.LuceneScore(field, luceneQuery)` in an `OrderBy`/projection. They translate a Lucene query string to the provider's native full-text engine over the **same `cfg.MapFullTextProperty` index** (so the type must still be mapped). The `field` argument identifies the mapping — pass a mapped property; the search spans the type's whole combined index.

```csharp
// filter + relevance sort + paging in one server-side query
var hits = await store.Query<Article>()
    .Where(a => a.Category == "tech"
             && DocumentFunctions.LuceneMatch(a.Body, "orleans AND grain NOT deprecated"))
    .OrderByDescending(a => DocumentFunctions.LuceneScore(a.Body, "orleans grain"))
    .Skip(0).Take(20)
    .ToList();
```

The same functions are available in the string-expression grammar (AOT-safe), lowering to the identical query:

```csharp
store.Query<Article>().Where("lucenematch(body, 'title:quick AND brown~')");
store.Query<Article>().Where($"lucenematch(body, {userQuery})")
                      .OrderBy("lucenescore(body, 'orleans') desc");
```

### Lucene grammar

| Feature | Example |
|---|---|
| term | `orleans` |
| phrase | `"virtual actor"` |
| boolean | `orleans AND grain`, `a OR b`, `a NOT b`, `+must -mustnot` (also `&&` `\|\|` `!`) |
| grouping | `(quick OR slow) AND fox` |
| prefix | `distrib*` |
| fuzzy | `orlean~` / `orlean~1` |
| proximity | `"quick fox"~5` |
| boost | `orleans^2` (affects ranking only) |

Range queries (`[a TO b]`) and non-trailing wildcards (`te*t`) are rejected with a clear error.

### Provider support for composable queries

Composable queries reuse the same per-type index as `FullTextSearch`, but each engine expresses a different subset of the grammar. **Operators a backend can't express throw `NotSupportedException`** — they never silently degrade to something else.

| Provider | `LuceneMatch` | `LuceneScore` | Advanced operators |
|---|---|---|---|
| **SQLite** (FTS5) | ✅ | ✅ (`bm25`) | prefix, proximity (`NEAR`) |
| **PostgreSQL** (`tsquery`) | ✅ | ✅ (`ts_rank`) | prefix |
| **MySQL** (BOOLEAN MODE) | ✅ | ✅ | prefix, proximity |
| **SQL Server** (`CONTAINS`) | ✅ | ✅ (`CONTAINSTABLE`) | prefix, proximity (`NEAR`) |
| **Oracle Text** (`CONTAINS`) | ✅ | ❌ — use `FullTextSearch` | prefix, fuzzy, proximity |
| **Trigram index** (SQLite, PostgreSQL, CockroachDB) | ✅ (substring tests) | ✅ | prefix, phrase |
| **LiteDB / IndexedDB** (in-memory) | ✅ | ✅ | **all** (incl. fuzzy) |
| **DuckDB / Cosmos DB / MongoDB** | ❌ — use `FullTextSearch` | ❌ | — |

Baseline (terms, phrases, `AND`/`OR`/`NOT`, grouping) works on every provider in the ✅ rows. Notes:

- **Oracle** — `SCORE(n)` requires a co-located `CONTAINS` label in the same statement, so a standalone `LuceneScore` can't be produced; use `store.FullTextSearch<Article>(...)` for ranking on Oracle.
- **DuckDB / Cosmos / MongoDB** — the engine can't express the boolean Lucene grammar inline (DuckDB's index is a rebuild-on-query snapshot; Cosmos/MongoDB full-text is bag-of-words / single top-level clause). Use the terminal `store.FullTextSearch(...)` / `FullTextMatch(...)` on those providers.
- **Field-scoped terms** (`title:foo`) are **not supported in v1** on any provider — the index is a single combined field — and throw. Pass the query without a field prefix; it searches all mapped properties.

## Provider support

The index is maintained automatically by the engine — no write-path bookkeeping — so once a type is mapped, `Insert`/`Update`/`Remove`/`Clear` keep it in sync for free.

| Provider | Engine | Ranking | Notes |
|---|---|---|---|
| **SQLite** | FTS5 virtual table + triggers | BM25 | Always available. Trigram tokenizer. |
| **PostgreSQL** | generated `tsvector` column + GIN | `ts_rank` | Per-language stemming. Trigram via `pg_trgm`. |
| **CockroachDB** | generated `tsvector` column + GIN | `ts_rank` | Built-in trigram. |
| **MySQL** | generated column + `FULLTEXT` (InnoDB) | `MATCH … AGAINST` | Natural-language mode. |
| **Oracle** | `CTXSYS.CONTEXT` (sync on commit) | `SCORE()` | Requires the Oracle Text option. |
| **SQL Server** | Full-Text Index + `FREETEXTTABLE` | `RANK` | Requires the Full-Text Search feature. Each mapped type adds its column to the table's one full-text index. |
| **DuckDB** | `fts` extension (BM25) | BM25 | Snapshot index — rebuilt before each query. |
| **Cosmos DB** | full-text policy + `FullTextScore` | rank order | Newer Cosmos service feature. |
| **MongoDB** | `$text` index | `textScore` | One text index per collection. |
| **LiteDB** | in-memory TF-IDF | TF-IDF | No native engine — scans the collection. |
| **IndexedDB** | in-memory TF-IDF | TF-IDF | No native engine — scans the store. |

### Limitations

- **Map before you query.** A type that hasn't been mapped with `cfg.MapFullTextProperty` cannot be full-text searched — `FullTextSearch`/`FullTextMatch` throw. This is by design (it's how the index gets created).
- **One mapped type per collection** on MongoDB, which allows a single text index per collection.
- **Optional features must be installed.** Oracle Text and SQL Server Full-Text Search are optional server components; if absent, `FullTextSearch` fails at query time. Cosmos full-text requires a service/SDK that supports it.
- **In-memory fallback** (LiteDB, IndexedDB) loads and scans the collection, so it suits modest data sizes — exactly the client-tier scenarios those providers target.
