The `Shiny.DocumentDb.Sqlite` package provides the default SQLite-backed document store. It is the recommended provider for mobile, desktop, embedded, and single-process scenarios — full LINQ-to-SQL translation, JSON indexes, spatial queries via R*Tree, hot backup, and a `ClearAllAsync` shortcut.

<NugetBadge name="Shiny.DocumentDb.Sqlite" showLabel={true} />

## When to Use

- Mobile (.NET MAUI iOS/Android) and desktop apps
- Single-process embedded storage
- Local-first / offline-capable apps
- Blazor WebAssembly when you need full SQL features (paired with `SQLitePCLRaw.bundle_wasm`)

If you need encryption at rest, use [SQLCipher](/documentdb/sqlcipher/) instead. For browser persistence without a native binary, see [IndexedDB](/documentdb/indexeddb/).

## Installation

```bash
dotnet add package Shiny.DocumentDb.Sqlite
```

For **vector / similarity search** (`sqlite-vec`) on iOS, Android, and desktop, also add the companion package — it ships the native binaries and wires them up with one call. See [Vector search › SQLite](/documentdb/vector/#sqlite--sqlite-vec-virtual-table).

```bash
dotnet add package Shiny.DocumentDb.Sqlite.VectorSupport
```

## SQLitePCLRaw version

`Shiny.DocumentDb.Sqlite` uses `Microsoft.Data.Sqlite` 11, which brings SQLitePCLRaw **3.x** and a current SQLite build. Earlier releases stayed on SQLitePCLRaw 2.1.x, because 3.x has no SQLCipher bundle, and restore reported `NU1903` for `SQLitePCLRaw.lib.e_sqlite3` ([CVE-2025-6965](https://github.com/advisories/GHSA-2m69-gcr7-jv3q)). That warning is gone. [SQLCipher](/documentdb/sqlcipher/) now runs on SQLite3 Multiple Ciphers, which is built for SQLitePCLRaw 3.x, so nothing holds the graph back.

An app gets exactly one SQLitePCLRaw core. Don't add SQLitePCLRaw 2.1.x packages (such as `SQLitePCLRaw.bundle_e_sqlcipher` or `bundle_green` 2.x) next to this package.

<Steps>
1. Direct instantiation

   ```csharp
   // Quick setup
   var store = new SqliteDocumentStore("Data Source=mydata.db");

   // Full options
   var store = new SqliteDocumentStore(new DocumentStoreOptions
   {
       DatabaseProvider = new SqliteDatabaseProvider("Data Source=mydata.db")
   });
   ```

2. Dependency injection

   ```csharp
   using Shiny.DocumentDb;
   using Shiny.DocumentDb.Sqlite;

   services.AddDocumentStore(opts =>
   {
       opts.DatabaseProvider = new SqliteDatabaseProvider("Data Source=mydata.db");
   });
   ```
</Steps>

## Concurrent reads

By default every operation shares one connection, so a read waits while a long import holds it. Set
`ConcurrentReads` to run reads on a small pool of read-only connections next to the writer:

```csharp
opts.DatabaseProvider = new SqliteDatabaseProvider("Data Source=app.db")
{
    ConcurrentReads = true
};
```

- Reads are `Get`, the query terminals (`ToList`, `Count`, `Any`, aggregates, cursor pages, projections, grouping,
  joins), streaming, and `FullTextSearch`. Up to 4 read connections are opened as needed.
- Writes, and every read inside a unit of work, stay on the writer, so a unit still reads its own uncommitted changes.
- It only takes effect for a **file database in WAL mode** (the mode this provider sets). `:memory:`,
  `Mode=Memory` and `Cache=Shared` databases keep the single connection. SQLCipher inherits the setting, and its
  read connections use the same password.
- It is **off by default** because it changes one thing: a read outside a unit of work sees the last committed
  state straight away, rather than waiting for another caller's open transaction to finish.

## Storage Layout

```sql
CREATE TABLE IF NOT EXISTS "documents" (
    Id        TEXT NOT NULL,
    TypeName  TEXT NOT NULL,
    Data      TEXT NOT NULL,
    CreatedAt TEXT NOT NULL,
    UpdatedAt TEXT NOT NULL,
    PRIMARY KEY (Id, TypeName)
);
```

The `Data` column stores raw JSON text. Property access translates to `json_extract(Data, '$.path')`. Deep `Upsert` runs server-side via SQLite's `json_patch()` (RFC 7396).

## Backup

`SqliteDocumentStore.Backup(path)` uses the SQLite Online Backup API — the store stays usable during the copy.

```csharp
var store = new SqliteDocumentStore("Data Source=mydata.db");
await store.Backup("/path/to/backup.db");
```

Backup is **not** on the `IDocumentStore` interface — it lives on the concrete `SqliteDocumentStore` type. Marked `[UnsupportedOSPlatform("browser")]` so it produces a compiler warning when called from browser-targeted code.

## Clear All

`SqliteDocumentStore.ClearAllAsync()` deletes every document across every table, including spatial sidecar tables. Useful for tearing down test fixtures or signing a user out of a local-first app.

```csharp
var store = new SqliteDocumentStore("Data Source=mydata.db");
await store.ClearAllAsync();
```

## Spatial Queries

SQLite uses R*Tree virtual tables for `WithinRadius`, `WithinBoundingBox`, and `NearestNeighbors`. Sidecar tables are created and synced automatically on insert/update/upsert/remove/clear. Register the `GeoPoint` property at setup:

```csharp
var options = new DocumentStoreOptions
{
    DatabaseProvider = new SqliteDatabaseProvider("Data Source=mydata.db")
};
options.ConfigureDocument<Restaurant>(cfg => cfg.MapSpatialProperty(r => r.Location));

var store = new SqliteDocumentStore(options);
```

See [Spatial Queries](/documentdb/spatial/) for the full API.

## Blazor WebAssembly

The SQLite provider is WASM-compatible when paired with `SQLitePCLRaw.bundle_wasm`:

- **WAL pragma skipped** on `OperatingSystem.IsBrowser()`
- **Spatial disabled** (R*Tree unavailable in WASM-compiled SQLite)
- **Backup unsupported** in the browser
- Use `Data Source=:memory:` or Emscripten OPFS-mounted paths

For most WASM scenarios, the lighter [IndexedDB provider](/documentdb/indexeddb/) is recommended.

## Indexes

```csharp
await store.CreateIndexAsync<User>(u => u.Name);
// CREATE INDEX IF NOT EXISTS idx_json_User_name
//   ON "documents" (json_extract(Data, '$.name'))
//   WHERE TypeName = 'User';
```

Indexes are **partial** by type so multiple types sharing the same table do not pay for each other's indexes. See [Indexes & Transactions](/documentdb/indexes/).

## Full-text search

Full-text uses FTS5. Word-tokenized types share a `{table}_fts` virtual table; types mapped with
`tokenizer: FullTextTokenizer.Trigram` (case-insensitive substring search) use `{table}_fts_tri`. Each type's
index definition is recorded in `{table}_fts_meta`, so changing the mapping rebuilds that type's rows on the next
startup. See [Full-Text Search](/documentdb/full-text/).

## Notes

- Reader-many / writer-one concurrency model.
- Identifiers are quoted with `"` — types named `Order`, `Group`, `User` work without collision.
- `Upsert` is RFC 7396 deep merge via `json_patch`.
- Raw SQL queries use `json_extract(Data, '$.path')`.
