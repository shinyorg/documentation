The `Shiny.DocumentDb.Sqlite.SqlCipher` package provides an encrypted SQLite provider that reads and writes the [SQLCipher](https://www.zetetic.net/sqlcipher/) 4 file format (AES-256 with HMAC). It runs on [SQLite3 Multiple Ciphers](https://utelle.github.io/SQLite3MultipleCiphers/) (`SQLite3MC.PCLRaw.bundle`), a maintained SQLite build for SQLitePCLRaw 3.x. It shares all query generation, expression translation, and LINQ support with the standard SQLite provider — the only differences are the native engine and encryption-aware backup/rekey support.

## Setup

<Steps>
1. Install the package

   ```bash
   dotnet add package Shiny.DocumentDb.Sqlite.SqlCipher
   ```

   It covers Windows, Linux (glibc and musl), macOS, Mac Catalyst, Android, iOS and Blazor WebAssembly.

2. Pin the engine at startup

   SQLitePCLRaw has one engine per process. Call `SqlCipherEngine.Init()` before anything opens a SQLite connection: it installs SQLite3 Multiple Ciphers and locks it in, so a later `Batteries_V2.Init()` can't swap in the unencrypted `e_sqlite3` engine. Constructing a `SqlCipherDatabaseProvider` or `SqlCipherDocumentStore` calls it for you. The explicit call matters only when something else opens SQLite first, such as a plain `SqliteDatabaseProvider` in the same app, EF Core, or `SqliteVec`. The engine opens unencrypted files too, so plain SQLite stores keep working beside encrypted ones.

   ```csharp
   using Shiny.DocumentDb.Sqlite.SqlCipher;

   SqlCipherEngine.Init(); // first thing in MauiProgram / Program.cs
   ```

   For **vector search** on encrypted databases, also add `Shiny.DocumentDb.Sqlite.VectorSupport` and call `SqliteVec.RegisterAutoExtension()` after `SqlCipherEngine.Init()` — it registers `vec0` against the active `sqlite3mc` engine — then set `VectorExtensionPreloaded = true` on your `SqlCipherDatabaseProvider`. See [Vector search](/documentdb/vector/#sqlite--sqlite-vec-virtual-table).

3. Register with dependency injection

   ```csharp
   using Shiny.DocumentDb;
   using Shiny.DocumentDb.Sqlite.SqlCipher;

   services.AddDocumentStore(opts =>
   {
       opts.DatabaseProvider = new SqlCipherDatabaseProvider("mydata.db", "mySecretKey");
   });
   ```

   Or instantiate directly:

   ```csharp
   // Quick setup
   var store = new SqlCipherDocumentStore("mydata.db", "mySecretKey");

   // Full options
   var store = new SqlCipherDocumentStore(new DocumentStoreOptions
   {
       DatabaseProvider = new SqlCipherDatabaseProvider("mydata.db", "mySecretKey")
   });
   ```
</Steps>

The constructor takes a **file path** and **password** as separate parameters so requirements are explicit. All other `DocumentStoreOptions` (table mapping, AOT, logging, etc.) work identically to the standard SQLite provider.

## File format and existing databases

The provider opens the file as a SQLite URI with `cipher=sqlcipher&legacy=4`, so every database it creates is a standard SQLCipher 4 file (not SQLite3 Multiple Ciphers' ChaCha20 default) that other SQLCipher tools can open. Databases written by earlier versions of this package, which used `SQLitePCLRaw.bundle_e_sqlcipher` (SQLCipher 4.5.2), open unchanged with the same password. No migration is needed.

## Rekeying

Change the encryption key of an existing database using the `RekeyAsync` extension method on `IDocumentStore`. This issues `PRAGMA rekey` with SQL injection protection via SQLite's `quote()` function.

```csharp
using Shiny.DocumentDb.Sqlite.SqlCipher;

await store.RekeyAsync("newPassword");
```

:::caution
After rekeying, the store still holds the old password internally. You must create a new store instance with the new password for subsequent operations.
:::

`RekeyAsync` throws `InvalidOperationException` if the store is not using `SqlCipherDatabaseProvider`.

## Backup

Backup works the same as the standard SQLite provider. The encryption password is automatically propagated to the backup database — the backup file will be encrypted with the same key.

```csharp
await store.Backup("/path/to/backup.db");
```

## Differences from Shiny.DocumentDb.Sqlite

| | `Shiny.DocumentDb.Sqlite` | `Shiny.DocumentDb.Sqlite.SqlCipher` |
|---|---|---|
| **Native engine** | `e_sqlite3` (via `Microsoft.Data.Sqlite`) | `sqlite3mc` (via `SQLite3MC.PCLRaw.bundle`) |
| **Encryption** | Not supported | AES-256, SQLCipher 4 file format |
| **Constructor** | Connection string | File path + password |
| **Backup** | Unencrypted destination | Password propagated to destination |
| **Rekey** | N/A | `store.RekeyAsync("newPassword")` |
| **Query/LINQ** | Full support | Identical — inherits from `SqliteDatabaseProvider` |
| **Package size** | Smaller (no encryption native libs) | Larger (includes SQLCipher native binaries) |

## When to use which

- Use **`Shiny.DocumentDb.Sqlite`** when encryption is not needed — smaller package, simpler setup.
- Use **`Shiny.DocumentDb.Sqlite.SqlCipher`** when the database file must be encrypted at rest (mobile apps with sensitive data, HIPAA/PCI compliance, etc.).
- Use **[field-level encryption](/documentdb/encryption/)** (in the core package) when specific *properties* must be ciphertext — on any provider, not just SQLite. It is complementary: SQLCipher protects the whole file from someone who has the file, field-level encryption protects named values from anyone who can read the database (including a DBA, a replica, or a backup). Use both if you want both.
