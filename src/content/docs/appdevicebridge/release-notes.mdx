## 1.0 TBD

<RN type="feature">**Traffic monitor.** `UseTrafficMonitor()` records every request the server answers: the web app's files, bridge calls, your own endpoints, and the requests the bridge server turns away. `WebAppHostView.ShowTrafficMonitorAsync()` opens `TrafficMonitorPage` over the web app. It lists each request's status, path, size, origin and duration, with a filter, a record switch and Clear, and a tap opens the full headers and text bodies with Copy. Requests are kept in memory only, the newest 300, with text bodies up to 128 KB. Credential headers, cookies and `token` query parameters are always redacted, so the launch token and session cookie never appear. `http.AddTrafficRecorder()` registers the recorder without MAUI. The pages work on every MAUI head: Android, iOS, Mac Catalyst, Windows, macOS (AppKit) and Linux (GTK4). See [Traffic monitor](/appdevicebridge/hosting/#traffic-monitor).</RN>

<RN type="feature">**A Pi camera into any `Stream`, for Bluetooth LE L2CAP.** `ICameraService.StreamToAsync(destination, settings, statistics)` in `Shiny.AppDeviceBridge.RpiCamera` streams a camera into any `System.IO.Stream` as JPEGs, each behind a 28-byte header, for a pipe with no HTTP to carry MJPEG, such as an L2CAP channel from `L2CapTicketBroker` (Shiny.BluetoothLE.Hosting 5.6.5). `RpiCameraStreamSettings` sets the size, quality, a frame rate whose surplus is dropped before encoding, and a `MaxDuration` ceiling. MJPEG from the pipeline passes straight through. The camera session opens when the stream starts and is released when it ends. It returns `RpiCameraStreamEnd`, and `RpiCameraStreamStatistics` counts frames sent and dropped. On the viewer, `ReadFramesAsync` in `Shiny.AppDeviceBridge.RpiCamera.Client` reads the frames back from the stream, such as one from `OpenL2CapTicketChannel` on a phone, and ends cleanly when the stream closes between frames. Linux with the native shim; elsewhere `StreamToAsync` throws `CameraUnavailableException`. `ReadFramesAsync` runs anywhere .NET does. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="enhancement">**The TypeScript clients compile to JavaScript.** `npm run build` in `clients/typescript` produces ES modules with `.d.ts` declarations. The generated modules import each other with `.js` specifiers, so the output loads without a bundler.</RN>

<RN type="feature">**Client variants: several builds of the web app in one package, at the same URLs.** `WebAppHostOptions.Variants("mobile", "desktop")` declares one folder per build in the release zip, and `SelectVariant` picks one for each request, documents and assets alike, typically from a cookie, `Sec-CH-UA-Mobile` and the `User-Agent`. The variants share one app id, one version and one update check. A package missing any variant's entry document is refused. Responses carry `Vary: User-Agent, Sec-CH-UA-Mobile, Cookie`, and a selector that returns nothing, an unknown name or throws serves the first variant. All platforms. See [Client variants](/appdevicebridge/hosting/#client-variants).</RN>

<RN type="feature">**Moving the server at runtime is covered.** Stopping the app's server, changing its address or port and starting it again carries the WebView's session, `Origin` and an open tunnel across with no extra code. There is now an integration test for it and a section in [Hosting](/appdevicebridge/hosting/#moving-the-server-at-runtime). All platforms.</RN>

<RN type="feature">**Your own cache policy and content types for the web app.** `WebAppHostOptions.OnPrepareResponse` runs for every file the host serves, after its own `no-cache` on the entry document, so an app serving its pages over a LAN or a tunnel can cache fingerprinted assets for a year. `ContentTypeOverrides` adds content types by extension for files the built-in map doesn't know, such as pdf.js's `.bcmap` and `.pfb`. All platforms.</RN>

<RN type="feature">**`ServeWebAppLocally` serves the pages to a browser on the device itself.** Off by default. In a release build a caller on this device without the WebView's launch session, such as a desktop browser opening the loopback address, got `403` for the web app's pages. With the option on it gets them. **Security:** this widens who gets the pages, not the bridges. The bridges still require `AppDeviceBridgePolicies.Bridges`, and a tunneled caller is never local, whatever address it arrives from. All platforms.</RN>

<RN type="feature">**Shiny.AppDeviceBridge.** Ship a web app — Blazor WebAssembly, React, Vue, anything that builds to static files — inside a .NET MAUI app, served straight out of its zip by a loopback Shiny.Net.HttpServer, updated over the air from a signed release server, and calling native device features through bridges. Android, iOS, Mac Catalyst and Windows, plus the maui-labs macOS (AppKit) and Linux (GTK4) heads. Formerly developed as WebAppHost; the packages are now `Shiny.AppDeviceBridge.*` and the bridge packages drop their `.Bridge` segment (`Shiny.AppDeviceBridge.Wifi`).</RN>

<RN type="feature">**Every bridge has a typed client, in C# and TypeScript.** Each bridge ships a `Shiny.AppDeviceBridge.{Bridge}.Client` package holding its request and response contracts and a `[BridgeClient]` interface — `ICalendarBridge`, `IWifiBridge`, `IPhotosBridge` — implemented by a source generator, registered with `Add{Name}BridgeClient()`. The native bridge serializes the very same contracts, so the page and the device cannot disagree about a shape, and a page no longer builds routes or JSON objects by hand. Failures throw `BridgeException` with the status, the bridge's error `code` and `IsNotSupported`; events are methods returning a subscription. The same clients are generated into TypeScript (`@shinyorg/appdevicebridge`, in `clients/typescript`) from the same assemblies, with a test that fails when the committed output falls behind. See [Typed clients](/appdevicebridge/clients/).</RN>

<RN type="feature">**Your own bridges get typed clients too.** Declare the API once with `[BridgeGet]`, `[BridgePost]`, `[BridgePut]`, `[BridgeDelete]` and `[BridgeEvent]` on an interface in a plain `net10.0` project; route tokens, bodies and query parameters bind by convention, and anything the generator cannot turn into a request is build error `ADB001` rather than a runtime surprise.</RN>

<RN type="feature">**Photos bridge — `Shiny.AppDeviceBridge.Photos`.** `AddPhotosBridge()` adds the system photo picker, which needs no permission and works on every head, and browsing the photo library newest first with thumbnails and full-size exports — PhotoKit on Apple platforms, MediaStore on Android, the Pictures folder on Windows. Photos reach the page as files in a file root. The library answers `501` on Linux, which has none. See [Photos](/appdevicebridge/storage/#photos).</RN>

<RN type="feature">**Folders bridge — `Shiny.AppDeviceBridge.Folders`.** `AddFoldersBridge()` shows the platform's own folder picker and turns the chosen folder into a file root the page reads and writes through the files bridge, remembered across launches: a security-scoped bookmark on Apple platforms, a persisted Storage Access Framework grant on Android, the path on Windows and Linux (GTK's file dialog). See [Picked folders](/appdevicebridge/storage/#picked-folders).</RN>

<RN type="feature">**File roots can be added while the app runs — folders the app maps, and shares.** `FolderRoots` (`Shiny.AppDeviceBridge.Folders`) keeps a folder the app decides on as a file root across launches: `Add(root, path, displayName)` for a folder chosen in the app's own dialog or a share an administrator publishes, `Forget(root)`, and `All` with whether each still opens. It works on every platform, not only where there is a folder picker; on Apple platforms a folder the app holds security-scoped access to is kept as a bookmark. The page never names a path, but hears every change as the `files.roots` event (`IFilesBridge.OnRootsChangedAsync`, `FilesBridge.onRootsChanged`). Underneath, `WebAppFileRoots` holds every root and raises `Changed`; `WebAppFileRoot` is the directory-on-disk store, requires an absolute path, and a store that is not a directory — an Android Storage Access Framework tree — implements the same operations. Bridges that need a path on disk (sharing, transfers, notification images, tray icons) resolve through `WebAppFileRoots.TryResolve` and refuse a root that has none. See [Settings and files](/appdevicebridge/storage/#settings-and-files).</RN>

<RN type="feature">**Desktop bridges — `Shiny.AppDeviceBridge.Desktop`.** `AddTrayIconBridge()` puts a system tray or menu bar icon — menus, badges, notifications, animation — under the web app's control, with clicks and menu choices handed back to the page or `background.js`. `AddQuickEntryBridge()` adds quick entry: a prompt window that opens over other applications from a global hotkey, with suggestions, a busy state, a response area and a screen-edge glow, whose submissions reach the page or `background.js`. Windows, macOS (AppKit and Catalyst) and Linux; `501` on Android and iOS. Launch at login is part of the app bridge (`/_bridge/app/startup`), over Shiny.Extensions.MauiHosting's `IStartupService`. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="feature">**Device camera bridge — `Shiny.AppDeviceBridge.Camera`.** `AddCameraBridge()` puts the device's own camera under the control of a page anywhere — a laptop driving a phone on a mount: a live MJPEG viewfinder an `<img>` plays (encoded only while someone watches), full-resolution photos and video filed into a file root, photo and video modes, front/back or a pinned camera, zoom, torch and effects as a patch, and the whole state on `camera.status`. `POST camera/open` asks the device to show its camera: the bridge pushes its own `CameraBridgePage` over the web app unless the app handles `CameraBridgeSession.OpenRequested` and shows its own `CameraBridgeView`. With no camera screen open commands answer `409 camera_not_open`; `ICameraCaptureStore` files captures elsewhere. Android, iOS, Mac Catalyst, macOS and Windows; `501` on Linux. Separate from the Raspberry Pi camera bridge. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="feature">**Sensors bridge.** `AddAppSupportBridge()` now also adds `/_bridge/sensors`: the accelerometer, gyroscope, magnetometer, compass, barometer and orientation sensor over .NET MAUI Essentials, plus shake detection. The page starts a sensor with a speed and a minimum interval between readings, and gets readings as events (`sensors.compass`, …) through `ISensorsBridge` / `SensorsBridge`. Every sensor stops when the page's last event stream closes. Android, iOS, Mac Catalyst and Windows, for the sensors the device has; `501` otherwise, including the macOS (AppKit) and Linux (GTK4) heads. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="enhancement">**Only the entry document is marked `no-cache`.** The web app host no longer sends `Cache-Control: no-cache` on every file it serves — only on the entry document (and the SPA fallback that answers with it), whose URL never changes across updates. Other files carry no cache header from the host. All platforms.</RN>

<RN type="fix">**Two update installs committing at once could fail.** A background update and one the page applied could both write the install state through the same temporary file, and one would fail with `FileNotFoundException`. On Windows, even with separate files, the second move onto the state file failed with `UnauthorizedAccessException`. Commits now run one at a time, each through its own temporary file. All platforms.</RN>

<RN type="feature">**Raspberry Pi camera bridge — `Shiny.AppDeviceBridge.RpiCamera`.** `http.AddRpiCameraBridge()` brings Raspberry Pi cameras to the bridge server through libcamera and a small native shim, with no `rpicam-apps` process: the cameras attached, JPEG snapshots encoded on the device, photographs written into a file root, sensor controls, and a live MJPEG stream an `<img>` plays, shared by every viewer of a camera. It registers on the server's builder, so a headless Pi runs it without MAUI. Linux only; elsewhere the status says why there is no camera and every other route answers `501`. Moved from the ShinyRpi appliance framework, with its native shim under `native/shinyrpi-camera`. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="feature">**The bridges live on your app's own Shiny.Net.HttpServer, with or without a WebView.** `http.AddAppDeviceBridge(o => …)` puts them on the `ShinyHttpServerBuilder` you configure the server with — address, port, TLS, limits, authentication and endpoints of your own all stay Shiny.Net.HttpServer's — and `http.AddWebAppBridge<T>()` adds a bridge with no MAUI dependency. `UseAppDeviceBridge` (`Shiny.AppDeviceBridge.Maui`) calls `AddShinyHttpServer` for you, listens on loopback port 5780 unless you give the server a port of your own, starts it with the app and restarts it on resume. The WebView, over-the-air updates, the dev server proxy, the launch session and `background.js` are in `Shiny.AppDeviceBridge.WebView` (`UseWebAppHost`, or `http.AddWebAppHost`), so an app that only needs the bridges doesn't carry them. Requires Shiny.Net.HttpServer 1.2. See [Hosting](/appdevicebridge/hosting/).</RN>

<RN type="feature">**You decide who may call the bridges.** Every bridge route requires one authorization policy, `AppDeviceBridgePolicies.Bridges`, which the bridges enforce themselves — protected whether or not, and wherever, the app puts `UseAuthentication` and `UseAuthorization` in its pipeline. By default it admits callers on this device only — a loopback connection that did not come through a tunnel, a loopback `Host`, no foreign `Origin` — plus, with the WebView host, the app's own launch session. `AuthorizeBridges` replaces it with any policy over any scheme added to the server's builder, and `BridgeCallers` has the checks the default uses. The bridges guard only what they mount: the app's own endpoints, authentication and fallback policy are the app's, the WebView's session is one more scheme they can require (`WebAppPolicies.Session`), and an app route under the bridge prefix is guarded as a bridge. `AllowedHosts` names the hosts accepted besides loopback and IP addresses. `BasePath` and `BridgePrefix` move the web app and the bridges independently, and pages discover them from `_host/config`. See [Security](/appdevicebridge/security/).</RN>

<RN type="feature">**Tunnels — `Shiny.AppDeviceBridge.Tunnel`.** `http.AddAppDeviceBridgeTunnel()` gives the server a public HTTPS address that the app opens and closes while it runs: `AppDeviceBridgeTunnel.StartAsync(token)` and `StopAsync()`, with `State`, `PublicUrl` and `LastError` to bind to as a free tunnel reconnects at new addresses. It is an SSH reverse forward to a public host (Pinggy by default), in managed code, so it runs on Android and iOS as well as the desktop heads; it serves straight into the server's pipeline without starting the local listener. There are no routes — the switch belongs to the app's own UI or endpoints. Everything arriving through it is a remote caller: never on the device, never the WebView's session, not let in by the debug allowance, the web app's pages only with `ServeWebAppRemotely`, and accepted only under the tunnel's own host. Implement `IAppDeviceBridgeTunnel` to put the server behind a tunnel of your own. See [Through a tunnel](/appdevicebridge/security/#through-a-tunnel).</RN>

<RN type="enhancement">**`MaxFileWriteBytes` raises the server's body limit whichever bridges are registered.** It used to apply only with the files bridge, so an app with its own upload endpoint and the files bridge off was held to Shiny.Net.HttpServer's 30 MB. A limit the app set higher, or turned off, still stands; with files off, the server now accepts bodies up to `MaxFileWriteBytes` (256 MB by default) — set it lower to keep a smaller limit.</RN>

<RN type="breaking">**Security change: debug builds let any caller reach the bridges.** In a debug build — a debugger attached, or an entry assembly built with JIT tracking — the default bridge policy admits any caller not arriving through a tunnel, launch session or not, so a browser, a script or another device (with the server bound past loopback) can drive the bridges while you develop. Release builds are unaffected. Set `AllowAnyCallerInDebug = false` to keep the release rules in debug, or `IsDebug` where detection isn't reliable; a policy from `AuthorizeBridges` applies in every build.</RN>

<RN type="breaking">**Security change: a tunnel is never "this device".** A tunnel hands the server its requests from 127.0.0.1, so a check on the remote address alone counted anyone on the internet as a caller on the device, and a forged `Host: 127.0.0.1` passed the loopback-name check too. `BridgeCallers.IsOnDevice`, the WebView's launch session, its session scheme and the debug allowance now all refuse a tunneled connection, and a tunneled request must carry the tunnel's own host (`421` otherwise). Use the new `BridgeCallers.IsLocalConnection(context)` in a policy of your own; `IsLocal(IPAddress)` remains an address test only.</RN>

<RN type="breaking">**Hosting split into the bridge server and the WebView host, on the app's own server.** `UseWebAppHost`, `WebAppHostView`, `WebAppHostPage` and `AllowWebPermissions` moved to `Shiny.AppDeviceBridge.WebView` (namespace `Shiny.AppDeviceBridge.WebView`). `AppId`, `HostVersion`, `Platform`, `AllowPortFallback`, `BasePath`, `BridgePrefix`, `EnableSettings`, `EnableFiles`, `FileRoots`, `MaxFileWriteBytes`, `PageAcceptTimeout` and `PageInvocationTimeout` moved from `WebAppHostOptions` to `AppDeviceBridgeOptions`; `InstallDirectory` defaults to its `DataDirectory`. There is no private server: `Port` and every other server setting are the server builder's `Options`, and `AddWebAppEndpoints`, `AddWebAppAuthentication` and `AddWebAppAuthorization` are the builder's own `Configure`, `AddAuthentication` and `AddAuthorization`. `services.AddAppDeviceBridge`, `services.AddWebAppHost` and `services.AddRpiCameraBridge` are `http.AddAppDeviceBridge`, `http.AddWebAppHost` and `http.AddRpiCameraBridge` on `ShinyHttpServerBuilder`. The app's own endpoints are no longer authenticated by default or moved under `BasePath` — set a fallback policy on the builder, and map them where they should be served. `IAppDeviceBridgeServerExtension` lost `ConfigureAuthentication`, `ConfigureAuthorization` and `ConfigureDefaultBridgePolicy` (an extension registers schemes and policies on the builder, and answers `AdmitsBridgeCaller`), and `AppDeviceBridgeServer.AllowsAnyCaller` takes the `HttpContext`. `RemoteAccess` is gone: bind with the server's `Options.Address`, accept names with `AllowedHosts`, serve pages with `ServeWebAppRemotely`, and open bridges with `AuthorizeBridges`. A bridge call refused by the policy answers `401` (anonymous) or `403`, not `403 remote_denied`. `Shiny.AppDeviceBridge.TrayIcon` is now `Shiny.AppDeviceBridge.Desktop`, with its client in `Shiny.AppDeviceBridge.Desktop.Client`; the TypeScript module is `desktop`.</RN>

<RN type="feature">**Typed native calls in Blazor.** `WebAppNativeCalls.HandleAsync` takes the payload's `JsonTypeInfo` — `GpsReading`, `PushPayload`, `TransferInfo`, `JobRun` — and, for calls that answer, the result's, so a page handles background work with the same contracts as everything else.</RN>

<RN type="fix">**A Blazor page delivered each event once per visit.** `WebAppEvents` told its script listeners apart by the `DotNetObjectReference`, but Blazor hands the script a new object for that reference on every interop call, so unsubscribing never found the listener it was meant to remove: visiting a page three times and firing one event ran its handler three times, and the listeners — with everything they captured — were never released. Listeners are now keyed by an id the client owns, so leaving a page removes exactly its own.</RN>

<RN type="breaking">**Untyped bridge calls are gone from the Blazor client.** `WebAppBridge.GetAsync(path)`, `PostAsync(path, JsonNode)`, `PutAsync`, `DeleteAsync` and `GetStringAsync` returned `JsonElement` and took `JsonObject` bodies; use the bridge's typed client. `WebAppBridge` remains for endpoints of your own, typed through your `JsonTypeInfo`. `WebAppNativeCalls.HandleAsync` no longer takes `JsonElement` handlers returning `JsonNode`.</RN>

<RN type="breaking">**Wire changes that came with the contracts.** The OBD bridge's raw requests moved from `POST obd/command` with `raw` to `POST obd/raw`, since the two answer different shapes. `speech.ended` reports `Stopped`, `PageClosed` or `Error`, and `POST speech/speak` with `"wait": false` answers `204` instead of `202`. Settings scopes are also accepted as `Local` and `Secure`. Built-in contract types were renamed along the way — `WebAppHostInfo` is `HostInfo`, `WebAppLink` is `AppLink`, `WebAppFileEntry` is `FileEntry`, `WebAppSettingsList` is `SettingsList` — and `WebAppFileRoots.TryResolve` is an instance method on the registered service.</RN>

<RN type="breaking">**File paths refuse the same characters on every platform.** A path segment containing `< > " | ? *`, a colon or a control character is refused everywhere, not only where the file system happens to reject it, so a path means the same thing on Linux as it does on Windows.</RN>
