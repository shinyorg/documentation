## 1.0 TBD

<RN type="feature">**Maps and directions.** `Shiny.AppDeviceBridge.Maps` (`bridge.AddMapsBridge()`) adds `/_bridge/maps` and `/_bridge/directions`. Vector tiles come from a region the user downloaded when one covers them, from tiles already seen online, and otherwise from your online source — a PMTiles archive read a range at a time, or a `{z}/{x}/{y}` service — with the glyphs and sprites the map draws with kept for offline use. Regions come from a catalog the release server publishes with `MapMapPacks()` (`Shiny.AppDeviceBridge.AspNetCore`): each part is signed with ECDSA P-256 over its hash, size, region id and bounds, under a scheme that can't pass for a web app release, and is discarded if it doesn't match; downloads resume after an interruption or a connection that goes quiet, report `maps.download`, update only the parts that changed, and stay out of iCloud backups. Directions go to a Valhalla server — yours, or a hosted one such as Stadia Maps — or, with `Shiny.AppDeviceBridge.Maps.Valhalla` (`AddOnDeviceDirections()`), run on the phone over a region's downloaded road network; `Auto` picks the device when a network covers every stop. The online router's address and key never reach the page. `Shiny.AppDeviceBridge.Maps.Blazor` adds `<BridgeMap>` — MapLibre GL JS bundled so it draws offline — with pins, lines, areas, circles, click-to-draw, routes and snapshots, and `shiny-map-packs` (`Shiny.AppDeviceBridge.MapPacks`) builds regions. Typed clients: `Shiny.AppDeviceBridge.Maps.Client` (`AddMapsBridgeClient()`, `AddDirectionsBridgeClient()`) and `MapsBridge`/`DirectionsBridge` in TypeScript; the simulator serves both. Tiles, regions and online directions on every platform; on-device directions on Android and iOS, online elsewhere. See [Maps & Directions](/appdevicebridge/maps/).</RN>

<RN type="feature">**The simulator in a browser.** `shiny-bridge-sim --web` replaces the terminal UI with a control panel at `/_sim/` on the simulator's own origin — bridges, route answers, sequences and errors, events, the platform, trails, traffic, activity and scenarios — and prints a link carrying its token. The panel drives `POST /_sim/api/{operation}`, which takes the MCP tool names with their arguments as a JSON object, so the same control is scriptable with `curl`. Changes from the panel are logged as `panel`, apart from an agent's. The API admits callers on this device holding the token, and a browser only from the simulator's own origin; the panel keeps its token in its own tab and cannot be framed, so the page under test cannot reach it. `--web-token` fixes the token. Runs wherever the simulator does. See [Simulator](/appdevicebridge/simulator/#the-web-panel).</RN>

<RN type="enhancement">**`TrafficRecorderOptions.Skip` leaves requests out of the recorder.** A predicate on the request; a skipped request passes straight through as if recording were off. The simulator uses it to keep its own control traffic — the web panel and MCP — out of **Traffic**. All platforms.</RN>

<RN type="fix">**Simulator: MCP works with `--dev-server`.** Requests to `/_sim/mcp` were forwarded to the dev server instead of being answered by the simulator, so an agent could not connect while a dev server was being served.</RN>

<RN type="feature">**The simulator answers to an AI agent.** `shiny-bridge-sim --mcp` puts a Model Context Protocol server on the simulator's own origin, so a coding agent can drive the same simulator you are watching: `get_route` hands it a generated sample of a bridge's contract, `set_route` and the new `set_route_sequence` decide what the page gets, `fire_event` raises events and reports how many page streams it reached, trails and scenarios load and play, and `get_traffic`, `wait_for_request` and `wait_for_quiet` let it see what the page actually did rather than guess. Values an agent sets are checked against the bridge's contract exactly as typed ones are, and every change is written to the Activity tab beside yours. `--mcp-stdio` speaks the protocol on stdin/stdout for an agent that starts the simulator itself. The endpoint is off unless asked for, refuses callers that are not on this device, requires the token printed at startup, and refuses any request carrying an `Origin` header — which is what stops the page it is serving from rewriting its own device answers. Runs wherever the simulator does. See [Simulator](/appdevicebridge/simulator/#driving-it-from-an-ai-agent).</RN>

<RN type="feature">**A route can answer a sequence of values.** One per call, the last repeating once they run out — the shape of a page that polls a status: queued, then running, then done. Every value is checked against the contract when the sequence is set, not when the page reaches it. Scenarios and trail steps write it as `values` instead of `value`, so a captured setup replays it faithfully, and the terminal UI shows how far through a route has got.</RN>

<RN type="feature">**Wearables bridge.** `Shiny.AppDeviceBridge.Wearables` (`bridge.AddWearablesBridge()`) connects the web app to its companion app on a paired Apple Watch or Wear OS device, through Shiny.Wearables 5.8. It covers status, live messages with replies, shared context, queued transfers, and file transfers through the file roots. What the watch sends goes to `wearables.*` handlers in the page or `background.js`, and a `wearables.message` handler's return value is the reply. Payloads are JSON, and non-JSON arrives as base64 with `binary: true`. Typed clients: `Shiny.AppDeviceBridge.Wearables.Client` (`AddWearablesBridgeClient()`) and `WearablesBridge` in TypeScript. iOS and Android; every other platform answers `501`. See [Wearables](/appdevicebridge/wearables/).</RN>

<RN type="breaking">**Bridges register on a bridge builder.** Every bridge is now added to an `AppDeviceBridgeBuilder` (`Shiny.AppDeviceBridge`), not to `MauiAppBuilder` or `ShinyHttpServerBuilder`. A MAUI app gets a `MauiAppDeviceBridgeBuilder` (`Shiny.AppDeviceBridge.Maui`, adding `Maui`) from `UseAppDeviceBridge(bridge => …, webApp => …)` or `UseAppDeviceBridge(bridge => …)`, which also call `UseShiny()` (once) and supply the app's UI thread: `bridge.Configure(o => o.AppId = "field-app").AddAppSupportBridge().AddLocationBridges()`. `UseWebAppHost` and `http.AddWebAppHost` are renamed `UseAppDeviceBridge(bridge, webApp)` and `http.AddAppDeviceBridge(bridge, webApp)` (`Shiny.AppDeviceBridge.WebView`), bridge delegate first. `UseAppDeviceBridge` and `http.AddAppDeviceBridge` take `Action<…Builder>` instead of `Action<AppDeviceBridgeOptions>`, with `Configure` for the options, and calling `UseAppDeviceBridge` again adds to the same server. BluetoothLE, Obd, Discovery, Wifi, HttpTransfers, Locations, Notifications, Push, Speech, Calendar, Contacts, Health and Jobs (now `net10.0` only) no longer reference MAUI and run without it; like RpiCamera and Tunnel, their extensions take either builder. AppSupport, AppSupport.Linux, AppLinks, Camera, Photos, Folders and Desktop depend on `Shiny.AppDeviceBridge.Maui` and do their own MAUI registration. `http.AddWebAppBridge<T>()` is replaced by `bridge.AddBridge<T>()`, `AddAppDeviceBridgeTunnel` is renamed `AddTunnel`, and `AddNotificationsBridge<TDelegate>()` is `AddNotificationsBridge(o => o.UseDelegate<TDelegate>())`. New: `IWebAppMainThread`, which bridges use for permission prompts instead of MAUI's dispatcher, and `IAppDeviceBridgeServerExtension.Initialize(IServiceProvider)`, called once before any request. `AllowWebPermissions`, `UseTrafficMonitor` and `AddTrafficRecorder` are unchanged. All platforms. See [Hosting](/appdevicebridge/hosting/).</RN>

<RN type="feature">**Simulator: `shiny-bridge-sim`.** A .NET tool (`Shiny.AppDeviceBridge.Simulator`) with a terminal UI that stands in for the native app. It runs the real bridge server on Shiny.Net.HttpServer and replaces every device bridge with one built from its `[BridgeClient]` interface, so it answers exactly what the typed clients send. For each route you set the answer: a value checked against the contract, a `204` null, or any error the bridges use (`501 not_supported`, `403 access_denied`, …), with an optional delay. You can fire any event at the page, switch whole bridges off, and pick the platform the host reports. Trails are timed scripts of those steps: a `.gpx` file plays as a GPS walk at its recorded pace, and what you do can be recorded as a trail. A Traffic tab shows the same recorder as the MAUI traffic monitor, and `"$now"`/`"$uuid"` placeholders keep values current. The page is served on the bridges' origin from `--app` or a `--dev-server`, and needs no changes. Scenario files save the whole setup, and `--headless` runs it in CI. Loopback only, same bridge policy as a release build. Runs wherever .NET 10 does. See [Simulator](/appdevicebridge/simulator/).</RN>

<RN type="fix">**`ToIndentedJson()` shows text as written.** The Blazor helper escaped every non-ASCII character and `<`, `>`, `&` and `'`, so a network called "Café" showed as `Caf\u00E9`. It now writes them as they are. The output is for display, which Blazor HTML-encodes, so it's still safe.</RN>

<RN type="enhancement">**`TrafficText` formats recorded traffic.** Sizes, durations, status lines, headers, bodies, the filter and a whole exchange as text moved from the MAUI traffic pages into `Shiny.AppDeviceBridge` as the public `TrafficText`, so every traffic monitor reads the same. The MAUI pages look and behave as before.</RN>

<RN type="fix">**`Shiny.AppDeviceBridge.Wifi` builds against Shiny.Net.Wifi 5.7.0.** That release declares `AddWifi()` only on its platform targets, so the bridge's plain `net10.0` build, which served the macOS (AppKit) head, no longer compiled. The bridge now has a `net10.0-macos` build of its own that registers Shiny's macOS Wi-Fi service. Its `net10.0` build registers NetworkManager on Linux and nothing elsewhere, where every call answers `501`. macOS and Linux; the other heads are unchanged.</RN>

<RN type="feature">**Battery on the macOS and Linux heads.** The app bridge reads the battery from the `IBattery` in the container when there is one, falling back to `Battery.Default`, so the maui-labs Essentials implementations are used. The new `Shiny.AppDeviceBridge.AppSupport.Linux` package, `bridge.AddAppSupportLinux()` on the GTK4 head, supplies an Essentials `IBattery` over D-Bus: UPower for charge, state and power source, power-profiles-daemon for energy saver, raising `app.battery` and `app.energysaver` as they change. It replaces the maui-labs GTK4 battery, which never raises its change events. On macOS (AppKit), `AddMacOSEssentials()` supplies the battery; energy saver always reads `Off` there. Linux via the new package; macOS via maui-labs; other heads unchanged.</RN>

<RN type="feature">**Events are async streams that unhook themselves.** Each event is an `IAsyncEnumerable<T>` a bridge maps with `routes.MapEvent(name, source, typeInfo)`. The page's one Server-Sent Events stream names the events it wants (`GET /_bridge/events?topics=…`, changed later with `PUT /_bridge/events/{id}` using the id from the first `bridge.stream` event), and the host runs each source only while a stream names it. When the page drops an event, disconnects or the source throws, the enumeration ends and its `finally` unhooks the native event, so nothing stays attached to a singleton for a page that's gone. A failed source is reported as `bridge.error` and dropped from that stream alone. `WebAppEventStream.FromEvent` wraps a .NET event, and `WebAppEventSource<T>` carries values your own code raises, with `ListenAsync(stopped, ct)` telling a bridge when its last listener leaves. BLE scans and notifications, Health listeners, the OBD monitor, Discovery browses and dictation now need a listener for their result event (`409 not_listening` otherwise) and stop once it has none; each sensor stops once its own event has none. Idle streams write a heartbeat every `AppDeviceBridgeOptions.EventStreamHeartbeat` (15 s) so a page that vanished is noticed. `WebAppEventHub.Publish`, `HasSubscribers` and `SubscribersChanged` are gone, bridges no longer take the hub in their constructors, and the TypeScript clients' `on…` methods return a promise of the unsubscribe function, resolved once the host is delivering the event. All platforms. See [Events](/appdevicebridge/bridges/#events).</RN>

<RN type="enhancement">**Wait for a recorded request.** `TrafficRecorder.WaitForAsync(match, ct)` returns the newest request matching `match` once it's recorded, and `WaitUntilAsync(condition, ct)` waits for the whole list to satisfy a condition. The recorder adds a request after its response has gone out, so a client can have the response before the request shows up in `Snapshot()`. These give tests and tools something to wait on instead. All platforms.</RN>

<RN type="feature">**Traffic monitor.** `UseTrafficMonitor()` records every request the server answers: the web app's files, bridge calls, your own endpoints, and the requests the bridge server turns away. `WebAppHostView.ShowTrafficMonitorAsync()` opens `TrafficMonitorPage` over the web app. It lists each request's status, path, size, origin and duration, with a filter, a record switch and Clear, and a tap opens the full headers and text bodies with Copy. Requests are kept in memory only, the newest 300, with text bodies up to 128 KB. Credential headers, cookies and `token` query parameters are always redacted, so the launch token and session cookie never appear. `http.AddTrafficRecorder()` registers the recorder without MAUI. The pages work on every MAUI head: Android, iOS, Mac Catalyst, Windows, macOS (AppKit) and Linux (GTK4). See [Traffic monitor](/appdevicebridge/hosting/#traffic-monitor).</RN>

<RN type="feature">**A Pi camera into any `Stream`, for Bluetooth LE L2CAP.** `ICameraService.StreamToAsync(destination, settings, statistics)` in `Shiny.AppDeviceBridge.RpiCamera` streams a camera into any `System.IO.Stream` as JPEGs, each behind a 28-byte header, for a pipe with no HTTP to carry MJPEG, such as an L2CAP channel from `L2CapTicketBroker` (Shiny.BluetoothLE.Hosting 5.6.5). `RpiCameraStreamSettings` sets the size, quality, a frame rate whose surplus is dropped before encoding, and a `MaxDuration` ceiling. MJPEG from the pipeline passes straight through. The camera session opens when the stream starts and is released when it ends. It returns `RpiCameraStreamEnd`, and `RpiCameraStreamStatistics` counts frames sent and dropped. On the viewer, `ReadFramesAsync` in `Shiny.AppDeviceBridge.RpiCamera.Client` reads the frames back from the stream, such as one from `OpenL2CapTicketChannel` on a phone, and ends cleanly when the stream closes between frames. Linux with the native shim; elsewhere `StreamToAsync` throws `CameraUnavailableException`. `ReadFramesAsync` runs anywhere .NET does. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="enhancement">**The TypeScript clients compile to JavaScript.** `npm run build` in `clients/typescript` produces ES modules with `.d.ts` declarations. The generated modules import each other with `.js` specifiers, so the output loads without a bundler.</RN>

<RN type="feature">**Client variants: several builds of the web app in one package, at the same URLs.** `WebAppHostOptions.Variants("mobile", "desktop")` declares one folder per build in the release zip, and `SelectVariant` picks one for each request, documents and assets alike, typically from a cookie, `Sec-CH-UA-Mobile` and the `User-Agent`. The variants share one app id, one version and one update check. A package missing any variant's entry document is refused. Responses carry `Vary: User-Agent, Sec-CH-UA-Mobile, Cookie`, and a selector that returns nothing, an unknown name or throws serves the first variant. All platforms. See [Client variants](/appdevicebridge/hosting/#client-variants).</RN>

<RN type="feature">**Moving the server at runtime is covered.** Stopping the app's server, changing its address or port and starting it again carries the WebView's session, `Origin` and an open tunnel across with no extra code. There is now an integration test for it and a section in [Hosting](/appdevicebridge/hosting/#moving-the-server-at-runtime). All platforms.</RN>

<RN type="feature">**Your own cache policy and content types for the web app.** `WebAppHostOptions.OnPrepareResponse` runs for every file the host serves, after its own `no-cache` on the entry document, so an app serving its pages over a LAN or a tunnel can cache fingerprinted assets for a year. `ContentTypeOverrides` adds content types by extension for files the built-in map doesn't know, such as pdf.js's `.bcmap` and `.pfb`. All platforms.</RN>

<RN type="feature">**`ServeWebAppLocally` serves the pages to a browser on the device itself.** Off by default. In a release build a caller on this device without the WebView's launch session, such as a desktop browser opening the loopback address, got `403` for the web app's pages. With the option on it gets them. **Security:** this widens who gets the pages, not the bridges. The bridges still require `AppDeviceBridgePolicies.Bridges`, and a tunneled caller is never local, whatever address it arrives from. All platforms.</RN>

<RN type="feature">**Shiny.AppDeviceBridge.** Ship a web app — Blazor WebAssembly, React, Vue, anything that builds to static files — inside a .NET MAUI app, served straight out of its zip by a loopback Shiny.Net.HttpServer, updated over the air from a signed release server, and calling native device features through bridges. Android, iOS, Mac Catalyst and Windows, plus the maui-labs macOS (AppKit) and Linux (GTK4) heads. Formerly developed as WebAppHost; the packages are now `Shiny.AppDeviceBridge.*` and the bridge packages drop their `.Bridge` segment (`Shiny.AppDeviceBridge.Wifi`).</RN>

<RN type="feature">**Every bridge has a typed client, in C# and TypeScript.** Each bridge ships a `Shiny.AppDeviceBridge.{Bridge}.Client` package holding its request and response contracts and a `[BridgeClient]` interface — `ICalendarBridge`, `IWifiBridge`, `IPhotosBridge` — implemented by a source generator, registered with `Add{Name}BridgeClient()`. The native bridge serializes the very same contracts, so the page and the device cannot disagree about a shape, and a page no longer builds routes or JSON objects by hand. Failures throw `BridgeException` with the status, the bridge's error `code` and `IsNotSupported`; events are methods returning a subscription. The same clients are generated into TypeScript (`@shinyorg/appdevicebridge`, in `clients/typescript`) from the same assemblies, with a test that fails when the committed output falls behind. See [Typed clients](/appdevicebridge/clients/).</RN>

<RN type="feature">**Your own bridges get typed clients too.** Declare the API once with `[BridgeGet]`, `[BridgePost]`, `[BridgePut]`, `[BridgeDelete]` and `[BridgeEvent]` on an interface in a plain `net10.0` project; route tokens, bodies and query parameters bind by convention, and anything the generator cannot turn into a request is build error `ADB001` rather than a runtime surprise.</RN>

<RN type="feature">**Photos bridge — `Shiny.AppDeviceBridge.Photos`.** `AddPhotosBridge()` adds the system photo picker, which needs no permission and works on every head, and browsing the photo library newest first with thumbnails and full-size exports — PhotoKit on Apple platforms, MediaStore on Android, the Pictures folder on Windows. Photos reach the page as files in a file root. The library answers `501` on Linux, which has none. See [Photos](/appdevicebridge/storage/#photos).</RN>

<RN type="feature">**Folders bridge — `Shiny.AppDeviceBridge.Folders`.** `AddFoldersBridge()` shows the platform's own folder picker and turns the chosen folder into a file root the page reads and writes through the files bridge, remembered across launches: a security-scoped bookmark on Apple platforms, a persisted Storage Access Framework grant on Android, the path on Windows and Linux (GTK's file dialog). See [Picked folders](/appdevicebridge/storage/#picked-folders).</RN>

<RN type="feature">**File roots can be added while the app runs — folders the app maps, and shares.** `FolderRoots` (`Shiny.AppDeviceBridge.Folders`) keeps a folder the app decides on as a file root across launches: `Add(root, path, displayName)` for a folder chosen in the app's own dialog or a share an administrator publishes, `Forget(root)`, and `All` with whether each still opens. It works on every platform, not only where there is a folder picker; on Apple platforms a folder the app holds security-scoped access to is kept as a bookmark. The page never names a path, but hears every change as the `files.roots` event (`IFilesBridge.OnRootsChangedAsync`, `FilesBridge.onRootsChanged`). Underneath, `WebAppFileRoots` holds every root and raises `Changed`; `WebAppFileRoot` is the directory-on-disk store, requires an absolute path, and a store that is not a directory — an Android Storage Access Framework tree — implements the same operations. Bridges that need a path on disk (sharing, transfers, notification images, tray icons) resolve through `WebAppFileRoots.TryResolve` and refuse a root that has none. See [Settings and files](/appdevicebridge/storage/#settings-and-files).</RN>

<RN type="feature">**Desktop bridges — `Shiny.AppDeviceBridge.Desktop`.** `AddTrayIconBridge()` puts a system tray or menu bar icon — menus, badges, notifications, animation — under the web app's control, with clicks and menu choices handed back to the page or `background.js`. `AddQuickEntryBridge()` adds quick entry: a prompt window that opens over other applications from a global hotkey, with suggestions, a busy state, a response area and a screen-edge glow, whose submissions reach the page or `background.js`. Windows, macOS (AppKit and Catalyst) and Linux; `501` on Android and iOS. Launch at login is part of the app bridge (`/_bridge/app/startup`), over Shiny.Extensions.MauiHosting's `IStartupService`. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="feature">**Device camera bridge — `Shiny.AppDeviceBridge.Camera`.** `AddCameraBridge()` puts the device's own camera under the control of a page anywhere — a laptop driving a phone on a mount: a live MJPEG viewfinder an `<img>` plays (encoded only while someone watches), full-resolution photos and video filed into a file root, photo and video modes, front/back or a pinned camera, zoom, torch and effects as a patch, and the whole state on `camera.status`. `POST camera/open` asks the device to show its camera: the bridge pushes its own `CameraBridgePage` over the web app unless the app handles `CameraBridgeSession.OpenRequested` and shows its own `CameraBridgeView`. With no camera screen open commands answer `409 camera_not_open`; `ICameraCaptureStore` files captures elsewhere. Android, iOS, Mac Catalyst, macOS and Windows; `501` on Linux. Separate from the Raspberry Pi camera bridge. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="feature">**Sensors bridge.** `AddAppSupportBridge()` now also adds `/_bridge/sensors`: the accelerometer, gyroscope, magnetometer, compass, barometer and orientation sensor over .NET MAUI Essentials, plus shake detection. The page starts a sensor with a speed and a minimum interval between readings, and gets readings as events (`sensors.compass`, …) through `ISensorsBridge` / `SensorsBridge`. A sensor stops once nothing listens to its event. Android, iOS, Mac Catalyst and Windows, for the sensors the device has; `501` otherwise, including the macOS (AppKit) and Linux (GTK4) heads. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="enhancement">**Only the entry document is marked `no-cache`.** The web app host no longer sends `Cache-Control: no-cache` on every file it serves — only on the entry document (and the SPA fallback that answers with it), whose URL never changes across updates. Other files carry no cache header from the host. All platforms.</RN>

<RN type="fix">**Two update installs committing at once could fail.** A background update and one the page applied could both write the install state through the same temporary file, and one would fail with `FileNotFoundException`. On Windows, even with separate files, the second move onto the state file failed with `UnauthorizedAccessException`. Commits now run one at a time, each through its own temporary file. All platforms.</RN>

<RN type="feature">**Raspberry Pi camera bridge — `Shiny.AppDeviceBridge.RpiCamera`.** `bridge.AddRpiCameraBridge()` brings Raspberry Pi cameras to the bridge server through libcamera and a small native shim, with no `rpicam-apps` process: the cameras attached, JPEG snapshots encoded on the device, photographs written into a file root, sensor controls, and a live MJPEG stream an `<img>` plays, shared by every viewer of a camera. It takes any bridge builder, so a headless Pi runs it without MAUI. Linux only; elsewhere the status says why there is no camera and every other route answers `501`. Moved from the ShinyRpi appliance framework, with its native shim under `native/shinyrpi-camera`. See [Bridges](/appdevicebridge/bridges/).</RN>

<RN type="feature">**The bridges live on your app's own Shiny.Net.HttpServer, with or without a WebView.** `http.AddAppDeviceBridge(bridge => …)` puts them on the `ShinyHttpServerBuilder` you configure the server with — address, port, TLS, limits, authentication and endpoints of your own all stay Shiny.Net.HttpServer's — and `bridge.AddBridge<T>()` adds a bridge of your own. `UseAppDeviceBridge` (`Shiny.AppDeviceBridge.Maui`) calls `AddShinyHttpServer` for you, listens on loopback port 5780 unless you give the server a port of your own, starts it with the app and restarts it on resume. The WebView, over-the-air updates, the dev server proxy, the launch session and `background.js` are in `Shiny.AppDeviceBridge.WebView` (`UseAppDeviceBridge(bridge => …, webApp => …)`, or `http.AddAppDeviceBridge(bridge => …, webApp => …)`), so an app that only needs the bridges doesn't carry them. Requires Shiny.Net.HttpServer 1.2. See [Hosting](/appdevicebridge/hosting/).</RN>

<RN type="feature">**You decide who may call the bridges.** Every bridge route requires one authorization policy, `AppDeviceBridgePolicies.Bridges`, which the bridges enforce themselves — protected whether or not, and wherever, the app puts `UseAuthentication` and `UseAuthorization` in its pipeline. By default it admits callers on this device only — a loopback connection that did not come through a tunnel, a loopback `Host`, no foreign `Origin` — plus, with the WebView host, the app's own launch session. `AuthorizeBridges` replaces it with any policy over any scheme added to the server's builder, and `BridgeCallers` has the checks the default uses. The bridges guard only what they mount: the app's own endpoints, authentication and fallback policy are the app's, the WebView's session is one more scheme they can require (`WebAppPolicies.Session`), and an app route under the bridge prefix is guarded as a bridge. `AllowedHosts` names the hosts accepted besides loopback and IP addresses. `BasePath` and `BridgePrefix` move the web app and the bridges independently, and pages discover them from `_host/config`. See [Security](/appdevicebridge/security/).</RN>

<RN type="feature">**Tunnels — `Shiny.AppDeviceBridge.Tunnel`.** `bridge.AddTunnel()` gives the server a public HTTPS address that the app opens and closes while it runs: `AppDeviceBridgeTunnel.StartAsync(token)` and `StopAsync()`, with `State`, `PublicUrl` and `LastError` to bind to as a free tunnel reconnects at new addresses. It is an SSH reverse forward to a public host (Pinggy by default), in managed code, so it runs on Android and iOS as well as the desktop heads; it serves straight into the server's pipeline without starting the local listener. There are no routes — the switch belongs to the app's own UI or endpoints. Everything arriving through it is a remote caller: never on the device, never the WebView's session, not let in by the debug allowance, the web app's pages only with `ServeWebAppRemotely`, and accepted only under the tunnel's own host. Implement `IAppDeviceBridgeTunnel` to put the server behind a tunnel of your own. See [Through a tunnel](/appdevicebridge/security/#through-a-tunnel).</RN>

<RN type="enhancement">**`MaxFileWriteBytes` raises the server's body limit whichever bridges are registered.** It used to apply only with the files bridge, so an app with its own upload endpoint and the files bridge off was held to Shiny.Net.HttpServer's 30 MB. A limit the app set higher, or turned off, still stands; with files off, the server now accepts bodies up to `MaxFileWriteBytes` (256 MB by default) — set it lower to keep a smaller limit.</RN>

<RN type="breaking">**Security change: debug builds let any caller reach the bridges.** In a debug build — a debugger attached, or an entry assembly built with JIT tracking — the default bridge policy admits any caller not arriving through a tunnel, launch session or not, so a browser, a script or another device (with the server bound past loopback) can drive the bridges while you develop. Release builds are unaffected. Set `AllowAnyCallerInDebug = false` to keep the release rules in debug, or `IsDebug` where detection isn't reliable; a policy from `AuthorizeBridges` applies in every build.</RN>

<RN type="breaking">**Security change: a tunnel is never "this device".** A tunnel hands the server its requests from 127.0.0.1, so a check on the remote address alone counted anyone on the internet as a caller on the device, and a forged `Host: 127.0.0.1` passed the loopback-name check too. `BridgeCallers.IsOnDevice`, the WebView's launch session, its session scheme and the debug allowance now all refuse a tunneled connection, and a tunneled request must carry the tunnel's own host (`421` otherwise). Use the new `BridgeCallers.IsLocalConnection(context)` in a policy of your own; `IsLocal(IPAddress)` remains an address test only.</RN>

<RN type="breaking">**Hosting split into the bridge server and the WebView host, on the app's own server.** The web app overload of `UseAppDeviceBridge`, `WebAppHostView`, `WebAppHostPage` and `AllowWebPermissions` moved to `Shiny.AppDeviceBridge.WebView` (namespace `Shiny.AppDeviceBridge.WebView`). `AppId`, `HostVersion`, `Platform`, `AllowPortFallback`, `BasePath`, `BridgePrefix`, `EnableSettings`, `EnableFiles`, `FileRoots`, `MaxFileWriteBytes`, `PageAcceptTimeout` and `PageInvocationTimeout` moved from `WebAppHostOptions` to `AppDeviceBridgeOptions`; `InstallDirectory` defaults to its `DataDirectory`. There is no private server: `Port` and every other server setting are the server builder's `Options`, and `AddWebAppEndpoints`, `AddWebAppAuthentication` and `AddWebAppAuthorization` are the builder's own `Configure`, `AddAuthentication` and `AddAuthorization`. `services.AddAppDeviceBridge` and `services.AddWebAppHost` are `http.AddAppDeviceBridge(bridge => …)` and `http.AddAppDeviceBridge(bridge => …, webApp => …)` on `ShinyHttpServerBuilder`, and `services.AddRpiCameraBridge` is `bridge.AddRpiCameraBridge` on the bridge builder. The app's own endpoints are no longer authenticated by default or moved under `BasePath` — set a fallback policy on the builder, and map them where they should be served. `IAppDeviceBridgeServerExtension` lost `ConfigureAuthentication`, `ConfigureAuthorization` and `ConfigureDefaultBridgePolicy` (an extension registers schemes and policies on the builder, and answers `AdmitsBridgeCaller`), and `AppDeviceBridgeServer.AllowsAnyCaller` takes the `HttpContext`. `RemoteAccess` is gone: bind with the server's `Options.Address`, accept names with `AllowedHosts`, serve pages with `ServeWebAppRemotely`, and open bridges with `AuthorizeBridges`. A bridge call refused by the policy answers `401` (anonymous) or `403`, not `403 remote_denied`. `Shiny.AppDeviceBridge.TrayIcon` is now `Shiny.AppDeviceBridge.Desktop`, with its client in `Shiny.AppDeviceBridge.Desktop.Client`; the TypeScript module is `desktop`.</RN>

<RN type="feature">**Typed native calls in Blazor.** `WebAppNativeCalls.HandleAsync` takes the payload's `JsonTypeInfo` — `GpsReading`, `PushPayload`, `TransferInfo`, `JobRun` — and, for calls that answer, the result's, so a page handles background work with the same contracts as everything else.</RN>

<RN type="fix">**A Blazor page delivered each event once per visit.** `WebAppEvents` told its script listeners apart by the `DotNetObjectReference`, but Blazor hands the script a new object for that reference on every interop call, so unsubscribing never found the listener it was meant to remove: visiting a page three times and firing one event ran its handler three times, and the listeners — with everything they captured — were never released. Listeners are now keyed by an id the client owns, so leaving a page removes exactly its own.</RN>

<RN type="breaking">**Untyped bridge calls are gone from the Blazor client.** `WebAppBridge.GetAsync(path)`, `PostAsync(path, JsonNode)`, `PutAsync`, `DeleteAsync` and `GetStringAsync` returned `JsonElement` and took `JsonObject` bodies; use the bridge's typed client. `WebAppBridge` remains for endpoints of your own, typed through your `JsonTypeInfo`. `WebAppNativeCalls.HandleAsync` no longer takes `JsonElement` handlers returning `JsonNode`.</RN>

<RN type="breaking">**Wire changes that came with the contracts.** The OBD bridge's raw requests moved from `POST obd/command` with `raw` to `POST obd/raw`, since the two answer different shapes. `speech.ended` reports `Stopped`, `PageClosed` or `Error`, and `POST speech/speak` with `"wait": false` answers `204` instead of `202`. Settings scopes are also accepted as `Local` and `Secure`. Built-in contract types were renamed along the way — `WebAppHostInfo` is `HostInfo`, `WebAppLink` is `AppLink`, `WebAppFileEntry` is `FileEntry`, `WebAppSettingsList` is `SettingsList` — and `WebAppFileRoots.TryResolve` is an instance method on the registered service.</RN>

<RN type="breaking">**File paths refuse the same characters on every platform.** A path segment containing `< > " | ? *`, a colon or a control character is refused everywhere, not only where the file system happens to reject it, so a path means the same thing on Linux as it does on Windows.</RN>
